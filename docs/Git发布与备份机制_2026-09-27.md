## 一、现状盘点（实测）

```
git branch -a   →  * main                       （仅单线开发）
git remote -v   →  （空，无远端）
git tag         →  （空，无标签）
git log -1      →  2f72185  checkpoint: v1.9.100 主系统锚定2104后全量备份
git status -s   →  （干净，checkpoint 已提交全部改动）
```

风险点（补机制前的状态）：
- 每次发版**没有可追溯的版本锚点**——出了事只能翻 `git log` 找 checkpoint 提交，无法一句话定位"线上 v1.9.99 对应哪次提交"。
- 无发布分支 → 线上热修只能直接在 main 上改，易把未发布开发混进发版。
- 无远端 → 单点故障（本机磁盘坏 = 代码+历史全丢）。

## 二、代码备份机制（已具备 + 本轮加固）

### 2.1 双线 checkpoint（核心备份动作）
`checkpoint.py` 一次执行完成两件事：
1. **产品线**：`docs/` + `README.md` 一起提交；
2. **研发线**：`core/ web/ config.yaml` 等源码一起提交；
3. **DB 快照**：`data/jproperty.db` 拷到 `.backups/db/jproperty_<ts>_<md5[:8]>.db`（保留 20 份、内容相同不重复存）。

用法：`python checkpoint.py "说明"`。**铁律：动代码前必先 checkpoint。**

### 2.2 .gitignore 安全性（已验证，不会误提交敏感物）
排除项：`/data/` `/.backups/` `config.local.yaml`（`*.local.yaml`）`tools/_*.py`。
⇒ 数据库快照、本地凭据、一次性诊断脚本**天然不入库**。本轮新增的 `tools/_dump_emp_online.py`（`_` 前缀）同样不入库，但已用于导出线上员工库全量 JSON 留底。

## 三、版本发布机制（本轮新建）

### 3.1 版本号唯一源
`core/version.py::VERSION`（当前 `1.9.100`）是**唯一**版本号出口。前端静态走 `?v={{version}}`；改前端（JS/CSS/模板）**必须抬版本号**否则浏览器沿用旧文件（经典"点了没反应"根因，见 INC-05）。

### 3.2 Tag 规范（语义化 vX.Y.Z）
- 每次发版打 **annotated tag**：`git tag -a vX.Y.Z -m "发布说明"`。
- 命名：主版本.次版本.修订（如 `v1.9.100`）。破坏性/架构变更升 X，功能新增升 Y，bug 修复升 Z。
- **本轮已打**：`v1.9.100` @ `2f72185`（发布说明见 §五）。

### 3.3 分支策略（main / release / hotfix）
```
main              ← 日常开发，所有提交收这里
release/X.Y.Z     ← 发版基线（从 main 拉，永不回并 main）
hotfix/X.Y.Z.Z    ← 线上紧急修复，从 release 分支 cherry-pick 修复后打新 tag
```
- **发布动作**：发版前从 main 拉 `release/1.9.100` → 在该分支打 tag → 走发版 SOP。
- **线上热修**：在 `release/1.9.100` 上 `cherry-pick` 修复提交 → 打 `v1.9.100.1` → 重新 deploy。
- **本轮已建**：`release/1.9.100` 分支（锚定 `2f72185`），演示完整模式。

### 3.4 Commit 规范
- 统一走 `checkpoint.py`（双线提交），提交信息带版本号 + 改动摘要。
- 紧急小修可 `git commit -m "vX.Y.Z 修 XXX"`，但**必须随后补 checkpoint** 保证两条线一致。

### 3.5 发版 SOP（8 步，永久）
```
① 改代码（本地 osaka-mvp）→ 抬 core/version.py 版本号（改前端必抬）
② checkpoint.py "vX.Y.Z 说明"        # 双线提交 + DB 快照
③ git tag -a vX.Y.Z -m "..."         # 版本锚点
④ sync_to_publish.py                 # 必做！否则账号种子/代码不同步→全员密码错误
⑤ deploy（同目录，不传 appId）        # 平台复用沙箱、子域不变
⑥ 必要时 POST /api/admin/selfrestart  # running_version 未变时刷新代码
⑦ 验证：selfcheck 版本号 + 数据通道 + 守卫 + 不泄漏（带 cache-buster）
⑧ 写 incident-log / 日报，收尾给「已做/现状/可选下一步」
```
**禁做（违反即记事故）**：绝不删应用 / 绝不换子域 / 绝不甩破坏性 UI 给用户 / 绝不未读文档就信旧结论。

### 3.6 回滚规范
- **代码回滚**：`git checkout release/旧版本` → 重新 `sync_to_publish` + `deploy`（同目录，子域不变）。
- **数据回滚**：`.backups/db/` 取对应时间戳快照 → 拷回 `data/` → `force_full_push.py` 重传（数据上线唯一通道 = `/api/ingest`）。
- **零删除切换**：永远不靠"删应用"回滚（会丢员工库 + 换地址）。

## 四、远端仓库建议（何时加、怎么 push）
- **何时加**：当勇哥确认"需要异地容灾 / 团队协作 / 公开审计"时再加 private remote。
- **怎么 push**：加好后 `git remote add origin <url>` → `git push -u main` → `git push --tags`（tag 必须显式推，不会随分支自动推）。
- **注意**：`config.local.yaml` / `.backups/` / `data/` 已被 `.gitignore` 排除，**不会**随 push 泄漏凭据或数据库。
