## 0. 怎么读这份文档

- **用户原话**用引号直接引用；只能还原要点的地方写「要点」，不逐字编造。
- **PM 判断**里凡是"查了库/查了日志/查了代码"的，都写明依据——这是 PM 和"猜"的区别。
- 未闭环的事项标 **⏳**，闭环后标 ✅ 并注明版本。
- 「落地」写的是**版本号 / 文件**，便于从文档反查代码。

## 3. 2026-09-11：本地版 MVP 从 0 到可用

> 这一天的节奏是"用户点一下就报一个问题，PM 当场定位+修+写进 PRD"。

### 3.1 账号管理 + 操作台（用户要求）

- **用户原话（要点）**：要 ① 账号管理（录入账号密码、支持清空/显示密码）；② 测试与操作按钮（登录 / 测试登录 / 测试查询 / 测试下载数据 / 真实下载数据）。
- **落地**：账号管理页（Fernet 加密存 `data/credentials.json`，密钥 `data/.cred_key`）+ 仪表盘「操作台」四按钮（测试登录 / 测试查询 / 测试下载 / 真实下载）。
- **红线（PM 主动设的，用户未反对）**：程序**绝不代输账号密码、不重试登录、不识别验证码、不换 IP**；密码只用于本账号自动登录。

### 3.2 「测试登录」报 `TypeError: Failed to fetch`（用户报）

- **PM 查到**：**不是接口逻辑错，是服务进程已退出**——用户看到的页面是服务还活着时渲染的，点按钮时 8765 已无监听，浏览器在网络层就失败了。
- **结论**：先让用户把账号**保存**（截图显示填了但没点保存）再点测试登录；同时前端把 `Failed to fetch` 这类英文报错**中文化**，并加"服务已停止"红色横幅（每 4 秒心跳，服务恢复自动消失）。
- **产品启示（写进 PRD 的坑）**：这条横幅后来成了救命功能——用户分不清"我操作错了"和"服务死了"。

### 3.3 账号页 v2：账号名称 + 网站地址 + 全站版本号

- **用户以 PM/SA 视角提**：① 保存账号至少要含「账号名称」「网站名称」两项；② **全站页脚加版本号 + 更新日期时间**。
- **落地**：账号页加两个输入框；`base.html` 页脚加 `版本 v{{version}} ｜ 更新于 {{build_at}}`（单一来源 `core/version.py`）。
- **PM 自己犯的错并纠正（记在案）**：验证新增字段时误用测试密码覆盖了用户的真实账号 → 已清空并请用户重新录入。
  **教训**：验证要用不同的 `member_id`，绝不动用户的真实数据。

### 3.4 登录根因真机定位 + 三视角重整页面

- **用户报**：后台不能正常登录。
- **PM 查到**：8765 无监听（WinError 10061）→ **服务已死**，非登录逻辑问题；用同一逻辑重新拉起服务。
- **同时**：用户发 **11 张真实 REINS 操作截图**（红框＝必用元素）→ 按真机校准选择器。

### 3.5 真机探查検索页 + 抓取全链路跑通

- 用户反馈"卡死/不需要做选择" → 实为 REINS 弹「**保存条件を読み込みますか？**」确认框 → 改成**自动点 はい**。
- 用户要求：点详情页 + 下载 PDF，模拟速度 **2–3 秒/房源**。
- PM 主动确认未擅自改的项：图片下载仍关闭（`download.images=False`），是否开启等用户答复。
- **桌面启动 BAT** 两次故障：① 旧 BAT 用 `netstat -ano|findstr` 在**中文 Windows GBK 下解析失败** → 端口清不掉 → 双击闪退；② 修复后重写为 `serve.py` 端口自愈。

### 3.6 提速：间隔 2–3 秒 → 1–2 秒

- **用户原话（要点）**：「获取详情页内容 + 下载 PDF 后，返回下一次操作的间隔最好在 **1 秒左右**，不断循环把信息更新完」；模拟与真实都要更快；并要求**在产品说明文档里清晰标识这个逻辑**。
- **落地**：`crawl.delay_range_seconds` 由 `[2.0,3.0]` → `[1.0,2.0]`（试跑分支同步改，保持一致）；间隔加在"详情+PDF 拉完"之后、下一条之前；README 写明。

### 3.7 查询页内联全量详情 + 概览定时刷新

- **用户要求**：① 下载后点查询，能把**检索+详情**全部信息查出来；② 默认当天数据、可选任意一天；③ 概览**每 1 分钟自动刷新** + 手动刷新按钮。

## 4. 2026-09-12：功能深化（v1.1.4 → v1.1.12）

### 4.1 指定日期下载（"问题二"）实机验证与修复闭环

- **用户诉求**：能按**指定日期**（如"9 月 5 日登录的公寓"）下载数据。
- **PM 查到的根因（非显然）**：REINS 手动指定日期查询时，「検索要求」并非「物件種別 / 所在地 / 沿線」任一 → **必须先套用「保存した検索条件」再叠加筛选**；控件位置在 `div.p-label` 的**相邻兄弟**里，不是后代。
- **落地**：前端 `/specified` 手动选项 → ①「确定」= 预览（不落库）→ ②「下载」= 独占执行（暂停当天下载、跑完自动恢复），产物＝数据 + 図面 PDF + Excel + 按天页。

### 4.2 i18n 全页铺页收尾（"诉求 C"）

- 四语言切换从"只有框架"铺到全部页面；建立**键覆盖审计**做法（合并字典两段赋值再比对模板用到的 key）。
- **遗留**：模板改动需用户重启一次服务才生效（静态 JS 已热重载）。

### 4.3 降价比例（→ v1.1.4）

- **用户要求**：在查询列表行、详情页头、对比表价格单元格显示**降价比例百分比**。
- **口径（PM 定，用户认可）**：公式＝**降价額 ÷ 修改前金額**（分母取"修改前"，不是修改后）；仅在降价时显示，形如 `↓3.2%`。

### 4.4 降价比例的位置与样式（→ v1.1.5）

- **用户追加要求（原话要点）**：比例要放在**降价金額与当前金額中间**，且**颜色/字体与降价金額一致**。
- **落地**：三处统一为 `↓ 170 万円` → `↓ 1.9%` → `8,680 万円`；样式改为同款**绿底胶囊**。
- **顺手修**：详情页降价徽标漏单位（`↓ 3,280` → `↓ 3,280 万円`）。

### 4.5 「下载文件清单（条件 × 文件 矩阵）」（→ v1.1.6，用户诉求 B）

- **用户要求**：说清楚**哪个入口、什么条件、会落哪些文件**。
- **PM 用 AskUserQuestion 确认口径**：「条件 × 文件 矩阵」+ 覆盖全部 4 个入口（测试下载 / 真实下载 / 每天自动抓取 / 指定日期下载）。
- **落地**：PRD v1.1.6 新增 8.3 节；并把**尚无的能力**如实列出（首次全量按钮、按条件分包 Excel、照片下载）。

### 4.6 下载速度排查（用户反馈 24 秒/条）

- **PM 查到**：仅砍等待只能压到 ~15–18 秒；就是否并发向用户提问。
- **用户澄清核心目的（关键转折）**：之前"想要快"的真实目的是**尽可能像人操作、不被平台判违规** → **不能并发**（并发最像机器、易限流封号），也不能均匀 5 秒（太快太规律＝机器）。

### 5.11 运行中报错澄清：「未处理异常 UndefinedError: today_changed」

- **用户附截图问**：「是什么原因导致的问题？刚才不知道你是不是改了代码之类的。」
- **PM 查证（直接读日志调用栈，不猜）**：
  `web/app.py:134 in index` → `render_template` → `index.html:18` → `num(stats.today_changed)` → `UndefinedError`。
- **根因＝"新模板 ＋ 旧后端"**：v1.2.6 把 `today_changed` / `today_total` 加进了 `core/store.py`，
  但 `.py` 不会热重载（用户尚未重启），而 `index.html` **模板已经热重载**成新版 → 概览页一渲染就炸。
- **影响面（重要）**：**只影响页面渲染，不影响下载**。日志显示报错同一时段（16:54:05）仍在正常落库。
  20 分钟内出现 12 次，全部是页面请求。
- **PM 顺手全站排查，又抓出一颗同类雷**：`detail.html` 调用了 v1.2.5 才新增的 Jinja 全局 `wareki_to_ad`，
  旧后端里没有 → **详情页一打开也会崩**。
- **修法（模板向后兼容，热重载即生效、不用重启）**：
  新 stat 键 → `stats.get('today_changed', 0)`；新 Jinja 全局 → `{% if wareki_to_ad is defined %}` 降级。
- **验证方式（值得复用）**：写脚本**模拟旧后端**——故意不注入 `wareki_to_ad`、`stats` 里不放新键，
  渲染 概览/详情/查询/对比 4 个页面 → **全部 PASS**；并**反向验证**旧写法确实会抛出与用户截图一致的错误。
- **沉淀**：写入 `03_版本管理与回滚.md` §4.1「热重载契约」，防止同类问题再犯。

### 5.12 用户就"重启"提出产品结构质疑（本轮最重要）

- **用户原话**：
  > 「你说 v1.2.6 版本需要重启后才能生效，我有一个疑问：我现在有可能正在下载这些信息，如果重启之后，是不是能够衔接上去，让它自动继续下载？**如果不能的话，我认为这里面需要重新思考你的产品结构**。我的想法是：**1. 要么你可以让我重启，但必须能够续上下载；2. 要么就不需要让我重启。**」
- **PM 核查结论：现状两条都不满足** ——
  | 问题 | 事实 |
  |---|---|
  | 本轮进度在哪 | crawler 线程**内存**里，没有持久化游标 |
  | 重启能续上吗 | **不能**（进程一结束，本轮循环消失） |
  | 已抓的会丢吗 | **不丢**（v1.2.2 边抓边落库，每 5 条一次） |
  | 剩下的会补吗 | **会补，但要重新翻页**（新一轮重跑同一范围，`pick_queue` 跳过已有详情的房源）→ 额外请求，与"模拟人工"目标冲突 |
- **PM 方案**：
  - **A（推荐）安全重启 ＋ 断点续跑**：安全点选在**组与组之间**（那里本来就有 6–14 秒随机停顿）；
    重启前写断点（`run_id` / 已完成组 / 已处理番号），重启后从下一组继续；不重登、不重复抓。
  - **B 不建议**：运行时热替换 Python 模块——容易"新旧代码混跑"，比要重启更危险。
  - **C 已做**：模板向后兼容兜底（本次事故的止血与长期防线）。
- **落地**：新建 `docs/PRD/04_更新生效与重启策略.md`（三方案对比 / 设计 / EARS 需求 / 验收标准 / 待拍板 4 项）。
- **临时建议**：在 A 落地前，**先让当前这轮跑完再重启**（本轮已跑很久，白跑可惜）。

### 5.14 用户给出完整规格：实时更新 / 灵活匹配 / 确定性存储 / 受限并发 / 真人化（17:36）

**这是本项目到目前最完整、最产品化的一段需求，原话要点如下（按用户编号）**：

1. **并发**：「做**受限并发**最大在途，如果是 2 的话，就用 2。」
2. **数据测试与调整**：「按你的说法去看**埋点数据**，需要在**近期一直测试**，理解它的反馈情况。
   如果出现了一些**模拟非人为操作造成的问题**，需要及时调整。」
3. **操作模拟要求**：
   - (a) **真实性**：操作看上去要和**真实有人点鼠标完全一样**；
   - (b) **速度控制**：不能过于快、也不能太慢，以免影响查看和下载的时间；
   - (c) **下载顺序**：「在一个页面内下载时，**没有强制要求必须按特定顺序**一直下来，中间可以偶尔跳过一两个；
     但总的还是需要**全部都下载**。」停顿 2~5 秒随机 + 偶尔长停顿（**概率可以大于 5% 一些**，比例与时间由 PM 把握）；
   - 补正：「**这个页面必须是全存储**，但它的存储顺序可以有一些在前、有一些在后，不是按照完全的列表顺序去完成。」
4. **实时更新**：「不管是哪一种方式的启动，它存储的**列表、详情和文件**等在**第一时间**就能够被更新到我的后台里面。」
5. **灵活且确定性的断点续传与本地存储**：
   - (a) **灵活匹配**：「重新去点的时候，它要对**历史上已经下载的东西做一次匹配**。如果有的页面或 PDF 已经有了，
     就**不用重复下载**。这个能力必须**非常灵活**。」
   - (b) **确定性存储**：「系统必须具备**确定性**。如果发生中断，**最多只允许当前这一次的详情页没有下载或存储**；
     **上一个浏览的详情页，以及所有已经下载的 PDF**，都必须存在我的本地，或者存在确定下载位置。」

**PM 的落地（v1.3.0）**：

| 用户条款 | 实现 |
|---|---|
| 4 实时更新 | `flush_every: 5 → 1`（每抓一条立即落库）；PDF 下完立即 `set_pdf()` 记账 |
| 5(a) 灵活匹配 | **详情 / PDF 分开判断**：`_pdf_exists()` 以**磁盘为准**；详情已有只补 PDF（用库里 `pdf_url`，不重开详情页）；新增 `pdf_url` 列 |
| 5(b) 确定性存储 | PDF **原子落盘**（`.part` → `os.replace()`）；最多丢"当前这一条" |
| 1 受限并发 | `_PdfWorker` 后台线程池，`pdf_max_inflight: 2`；拿不到直链自动退回同步方式 |
| 3(a) 真实性 | 保留逐行详情 + 独立新标签；PDF 走"浏览器式后台下载" |
| 3(b) 速度 | `[2,5]` 秒随机 + 8% 长停顿 `[15,30]` |
| 3(c) 顺序 | 每页约 12% 概率把 1~2 条挪到**本页末尾**（乱序但**一条不少**） |
| 2 持续测试 | 日志输出 PDF 耗时/成功失败；`05` §8.4 列了观察清单与**降级开关** |

**PM 的一个主动修正（与用户口述的差异）**：用户提的"断点续传"在 PM 原方案里是一个 **`round_state.json` 游标文件**；
但用户的表述（"对历史上已经下载的东西做一次匹配"）**本质上更好** —— 所以 PM **推翻了自己的游标设计**，
改为 **以「已完成物」为游标**：进度＝"库里有没有详情 / 磁盘上有没有 PDF"，**不存任何进度文件**。
好处：不会出现"断点文件与事实不一致"，手工删掉某个 PDF 也会被自动补回。详见 `04` §八。

**验证**：离线 **10/10 通过**（后台并发下载/原子落盘/不重复下载/失败不留半个文件/老库补列/配置取值）。
**仍需真机验证**：`_fetch_detail` 里"点击开详情 + 取 PDF 直链"这一段，建议用「**试跑**」（1 轮 / 最多 3 条）首次确认。

## 6. PM 观察：这个项目反复出现的沟通模式

写给下一个接手的人（也包括我自己）：

1. **用户报的是现象，问题常在别处。**「登录失败」＝服务死了；「下载成功但没数据」＝没落库；「新增带降价」＝分类口径错。**先查证再动手**，不要按字面改 UI。
2. **用户的字面目标 ≠ 真实目标。**「要更快」的真实目标是"别被平台判违规"→ 结论是**不能并发**。要问出真实目标。
3. **用户对"数字对不上"极其敏感**，而且**业务上是专业的**——他给的例子（9/1 新增 1000 万 → 9/11 降价 800 万）在库里真实存在。**他的直觉常常先于数据被发现**。
4. **口径必须写在文档里，不能只存在代码里。** 同一个词（新增/变更/降价/总数）在本项目有多套口径，写清楚比改样式重要。
5. **用户希望 PM 主动交流**：「将来如果遇到需要交互的事情，我需要产品经理来跟我进行交流」→ 遇到取舍要**主动给结论 + 选项**请他拍板，而不是等他提问。
6. **红线从不放开**：不代输账号密码、不识别验证码、不换 IP、会话失效即停机、凭证永不出本机、永不上传。
