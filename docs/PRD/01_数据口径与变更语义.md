## 一、背景

业务方（房产销售）反复遇到"**数字对不上 / 标签看着矛盾**"的问题，三次提出来：

1. 列表行标「新增」却带「↓降价」徽标 —— v1.2.4 澄清；
2. 「在我这儿是新增，在平台是降价」的房源本质应是「变更」，并追问"**上一次的数据是什么时候**" —— v1.2.5 澄清；
3. 「本地 345 / 今日新盘 63」与线上 406 差这么多，是不是我没下全 —— v1.2.6 澄清。

三次都指向同一个根因：**同一个词（新增 / 变更 / 降价 / 总数）在本系统里有多套口径，但没有写清楚**。本文件是这些口径的**唯一定义处**。

## 二、目标

| # | 目标 | 衡量 |
|---|---|---|
| G1 | 任何一个数字都能追溯到唯一的计算口径 | 本文件覆盖 KPI 卡与列表标签的全部数字 |
| G2 | 标签与业务直觉一致：销售看「新增/变更」能对上平台的"这套房动没动过" | 首抓带平台改价的房源标「变更」 |
| G3 | 明确"我方视角"与"平台视角"的边界，并让界面能区分 | 降价分「平台历史」与「本系统监测」两类 |

## 三、术语与口径（核心）

### 3.1 两个视角

| 视角 | 回答 | 数据来源 | 本系统现状 |
|---|---|---|---|
| **平台视角** | 这套房在 REINS 上"动没动过" | REINS「変更年月日」+「変更前価格」 | 已有（`change_date` / `previous_price`） |
| **我方视角** | 这套房"我们认识它多久、我方监测到它变了几次" | 本机 `changes` 表 | 已有，但**从不重抓已知房源** → 我方监测到的价格变动目前恒为 0 |

### 3.2 口径定义表

| 名词 | 定义 | 依据 |
|---|---|---|
| **新增** | 本机**首次入库**、且**平台也没有改价史**（`previous_price` 为空或与现价相等）的房源 | `changes.change_type='new'` + `properties.previous_price` |
| **变更** | ① 本机已跟踪且价格/指纹有变动；**或**② 首次入库时**平台已改过价**（`previous_price ≠ price`） | `differ.classify()` 双信号判定（v1.2.5） |
| **平台历史降价** | REINS 自己记录的"上一跳"降幅 = `previous_price − price`，**发生在我方下载之前** | `previous_price`（REINS 変更前価格） |
| **本系统监测降价** | 我方两次抓取之间观察到的降价 = 本次 `price` ＜ 上次 `price` | `snapshots` / `changes`（`price_down`）。**当前不产生**：系统不重抓已知房源 |
| **单步降幅 vs 累计降幅** | 徽标显示的是**单步**（REINS 的上一跳）；累计降幅只在本机 `changes`/`snapshots` 里 | v1.1.8 澄清 |
| **变更日期** | REINS「変更年月日」转公元年（和暦→AD，`core/wareki.py`） | 展示为 `2026-09-12` 形式 |
| **本地房源总数** | `properties` 表**累计入库量**（不是"线上现存数"） | `SELECT COUNT(*) FROM properties` |
| **线上总数** | REINS 当前检索结果的**现存总数快照**，同一条件会浮动（实测 447～500） | 抓取日志「結果 N 件」。**未落库** ⏳ |
| **今日更新** | 当天 `changes` 记录，按 `property_no` 去重后的**套数**，分「新增」与「变更」两类，二者之和＝合计 | v1.2.6 |
| **当日归类规则** | 一套房当天**只归一类**：只要有任何变更类记录（`modified` / `price_down` / `price_up`）就算「**变更**」，**哪怕它同时是当天首次入库** | v1.2.6 拍板 |

### 3.3 判定优先级（必须按此顺序，否则数字会互相矛盾）

```
对每一套房、每一天：
  if 当天存在 modified / price_down / price_up 记录   → 计为「变更」
  elif 当天存在 new 记录                              → 计为「新增」
  else                                                → 不计入当日统计
```

对应实现：列表行标签在 `web/app.py` 的 `api_query` 中**「变更」优先于「新增」**。

### 3.4 双信号判定（首抓时怎么定标签）

| 条件 | 判定 | 写入的 `change_type` |
|---|---|---|
| 本机已有该房源 | 走增量比对（价格/指纹） | `price_down` / `price_up` / `modified` / 无 |
| 本机首次入库 + `previous_price` 为空 | **新增** | `new` |
| 本机首次入库 + `previous_price` == `price` | **新增** | `new` |
| 本机首次入库 + `previous_price` > `price` | **变更** | `price_down` |
| 本机首次入库 + `previous_price` < `price` | **变更** | `price_up` |

**用户拍板（2026-09-13）**：降价与涨价**都算变更**；存量"伪新增"**一次性回填**。

## 四、需求（EARS 表述）

**R1（Ubiquitous）** 系统应始终以 `properties.previous_price` 与 `change_date` 作为"平台是否改过价、何时改的"的唯一依据，不得以我方入库时间代替。

**R2（Event-driven）** When 一套房源首次入库且 `previous_price` 与 `price` 存在差异, the system shall 将其判定为「变更」，并写入 `price_down` 或 `price_up`，变更时间取平台「変更年月日」（缺省时回退我方首见日）。

**R3（Event-driven）** When 统计"今日更新", the system shall 按 `property_no` 去重，并按 §3.3 的优先级把每套房归入「新增」或「变更」之一，二者之和等于合计。

**R4（Ubiquitous）** 系统应在所有展示降价的位置（查询列表 / 房源详情 / 房源对比）标注降价的**来源**与**变更日期**，使"平台历史降价"与"本系统监测降价"可被一眼区分。

**R5（State-driven）** While 展示"平台历史降价", the system shall 使用蓝底「平台」样式；绿底样式保留给"本系统监测降价"。

**R6（Unwanted）** If 回填历史变更记录, then the system shall **不得**把回填记录的 `detected_at` 写成当天（否则会把陈年平台改价计成"今日变更"）；应使用我方首见日，兜底用平台変更年月日。

**R7（Unwanted）** If `change_date` 为和暦（令和/平成/昭和）, then the system shall 转换为公元年展示，且转换逻辑全项目**只有一个实现**（`core/wareki.py`）。

**R8（Optional）** Where 需要回答"我方有没有下全", the system shall 提供「线上覆盖」指标（线上总数 vs 本地累计）。
**✅ 已实现（v1.2.7，2026-09-13）** —— 概览页新增「线上覆盖」KPI：**线上 X ／ 本地 Y ／ 覆盖 Z%**。

> **R8 的最终口径（v1.2.7 实现，务必以此为准）**
> - **采集**：每次检索后读页面上的「結果 N 件」（`selectors.result_total`），按**组**写入新表
>   `online_stats(captured_at, run_id, kind, label, subtypes, online_total)`；建表用 `CREATE TABLE IF NOT EXISTS` ⇒ **免迁移**。
>   解析取**最后一个** `N件`（文案形如 `1～50件 ／ 138件`，前面是当前页范围、后面才是总数）；取不到就**不记**（不猜）。
> - **online** = 当天**每个组最近一次**的线上总数**之和**（同组多次只取最新，避免重复累加）。
> - **local** = 本机库里**物件種目落在这些组覆盖范围内**的条数（累计，按 REINS 種目原值精确匹配）。
> - **pct** = local ÷ online。**>100% 是正常的**——说明累计抓到过的比"现在还在架"的多（房已成交下架）。
> - **没有数据时显示「—」而不是 0**（0 会被误读成"一条都没抓到"）。
> - ⚠️ 覆盖范围只含**本次抓取的这几组種目**，与"全站房源"不是同一口径——展示时须与"本地房源总数"分开理解。

## 五、边界与异常

| 场景 | 处理 |
|---|---|
| 平台多次降价（阶梯） | 本机只保留**上一跳**（`previous_price` 是单值）；中间阶梯不保留 ⏳（议题 3 的延伸） |
| 「仅刷新列表字段」不回详情页 | `previous_price` 不更新；列表网格本身无「変更前価格」列 |
| 同一套房既首抓又改价 | 归「变更」（§3.3） |
| 和暦年份跨界（昭和→平成→令和） | 由 `core/wareki.py` 统一换算，不做近似 |
| 线上总数与本地总数的差 | **差值＝尚未抓到的量**，不是"新增量"（v1.2.6 澄清的正是这一点） |

## 六、验收标准

| # | 验收项 | 判定 |
|---|---|---|
| A1 | 首抓带平台改价的房源，列表标「变更」而非「新增」 | 样例 `300134565829`（现价 7980万/前价 8180万/変更日 2026-09-12）标「变更」 |
| A2 | 平台降价标带「平台」字样与变更日 | 查询列表 / 详情 / 对比三处均可见 |
| A3 | 涨价同样归「变更」，箭头为 ↑ | 构造 `previous_price < price` 用例通过 |
| A4 | 「今日更新」大数字 = `新增 / 变更`，下方合计 = 两者之和 | 抽取任意一天核对 |
| A5 | 重启后不出现"今日变更"暴涨（回填不灌今天） | 回填后当天 `price_down/price_up` 只含我方当天首见的房源 |
| A6 | 和暦转换正确 | 令和8年9月12日 → `2026-09-12` |
| A7 | 口径可在文档内自洽推导 | 本文件 §3 与界面数字一致 |
