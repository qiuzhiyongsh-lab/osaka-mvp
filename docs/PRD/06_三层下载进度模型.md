# 06 · 三层下载进度模型（可交付 PRD · 供研发实现）

> 版本：v0.1 ｜ 提出：2026-09-13（用户口述）｜ 状态：⏳ 待排期实现（不破坏现有下载，纯增量）
> 关联文档：`05_抓取节奏与风控.md`、`04_更新生效与重启策略.md`、`01_数据口径与变更语义.md`
> 一句话：**把"下载"从黑盒动作拆成三个可度量、可续传的层，并在"我的页面"用进度面板告诉用户"本轮下到哪了"。**

---

## 1. 背景与问题

当前下载是一个整体动作：用户点"开始"后，黑窗口刷日志，页面上只能看到**累计**数字（本地总量、今日新增/变更）。
用户**看不到"这一轮任务"的进度**——列表刷了几页、详情读了几条、PDF 下了几个、还差多少。

这带来两个痛点：
1. **不确定性焦虑**：下载跑了很久，用户不知道是"卡住了"还是"在正常推进"。
2. **无法判断"下全了没有"**：累计数 ≠ 本轮覆盖数；中断后续跑也看不出"上次差的那 50 条补上了没"。

用户原话（三层模型）：
> ① 下载列表页：比如总共 130 篇，只要刷 3 下就能把这 3 个页面的全部信息拉下来，获取基本信息。
> ② 下载详情页和 PDF：每个列表页里每个文件都要读一遍详情，读的时候把对应的 PDF 下载下来；
>    产品页读完但详情页没读完，只要把详情页内容更新掉就行；**需要在"我的页面"显示本次下载进度**：
>    列表页总数 / 新增的详细列表页数量 / 实际已下载多少。
> ③ 下载 PDF：完整下载列表页之后，再下载详情页、PDF、照片数量，完成最基础采集。
>    列表页总共 130 篇、已下 80 篇、还 50 篇没下 → 下次找剩下的 50 篇继续下。

## 2. 三层模型定义（精确口径）

| 层 | 名称 | 动作 | 分母（目标） | 分子（已完成） | 剩余 |
|---|---|---|---|---|---|
| **L1 列表层** | 拉基本信息 | 翻列表页（每页 50），解析物件番号/地址/价格/種目/登録日/変更日等**列表字段** | `online_total`：本轮所覆盖种目组在 REINS 上的「結果 N 件」合计 | `scanned`：已翻到的列表行数 | `online_total − scanned` |
| **L2 详情层** | 读全字段 | 对每条开详情页（新标签）读全字段 → `detail_json` | = L1 分子 `scanned`（列表里每条都要读详情） | `fetched`：已落库详情的条数（`detail_json` 非空） | `scanned − fetched` |
| **L3 文件层** | 下 PDF/照片 | 详情页读时并行下 PDF（后台，最大在途 2）；缺失照片数记 `image_count` | = L2 分子 `fetched`（每条应有 1 个 PDF） | `pdf_saved`：磁盘已有 `data/attachments/<no>.pdf` 的条数 | `fetched − pdf_saved` |

**关键关系（天然自洽，可作校验）**：
```
L1:  scanned   ≤ online_total
L2:  fetched   ≤ scanned
L3:  pdf_saved ≤ fetched
剩余详情 = scanned − fetched      剩余PDF = fetched − pdf_saved
"已读详情" ≈ L2 分子；"新增详情" = 本轮 new_count（首次入库的那批）
"实际已下载" = L3 分子 pdf_saved
```

**对应用户原话的映射**：
- "列表页总数" → **L1 分母 `online_total`**
- "新增的详细列表页数量" → **L2 分子 `fetched`（本轮已读详情页）**，其中纯新增 = `new_count`
- "实际已经下载了多少" → **L3 分子 `pdf_saved`（已下 PDF 数）**
- "130 已下 80、剩 50 续下" → **L2 的 `scanned=130 / fetched=80 / 剩余=50`**，续传即重跑跳已完成

## 3. 现有基础 vs 缺口（研发必读，避免重复造轮子）

**已有（v1.3.0 及之前）**：
- `runs` 表已有 `scanned`（L1 分子）、`fetched`（L2 分子）、`new_count`、`change_count`。
- `_BatchSink.stats` 已有 `scanned/fetched/new/changed/pdf_saved/errors/ms_pdf/n_pdf`，每次 `flush` 调 `progress_run()` 写 `runs`。
- `online_stats` 表已存每组「結果 N 件」（`add_online_stat`），`online_coverage()` 可给出 `online_total` 分母。
- 断点续传范式已具备：**以"已完成物"为游标**（库有 `detail_json` / 磁盘有 PDF 即跳过），不存进度文件。
- 确定性存储：`flush_every=1` + PDF 原子落盘 ⇒ 中断最多丢当前 1 条。

**缺口（本次要补）**：
1. `runs` 表**没有 `online_total`（L1 分母）和 `pdf_saved`（L3 分子）的持久列** → 进度面板无从取值。
2. **没有 per-run 进度 API**（`/api/overview` 只有累计 stats，没有"当前轮进度"）。
3. **没有进度面板 UI**（用户要的"我的页面"展示）。
4. `image_count`（照片数）已在 `properties` 表，但**未在进度里体现**，L3 可扩展"照片覆盖"。

## 4. 数据模型变更（增量、免迁移）

### 4.1 `runs` 表加列（复用 `Store._ensure_columns()` 模式，幂等 ALTER）
```sql
ALTER TABLE runs ADD COLUMN online_total INTEGER DEFAULT 0;   -- L1 分母
ALTER TABLE runs ADD COLUMN pdf_saved   INTEGER DEFAULT 0;   -- L3 分子（持久化）
-- 可选：ALTER TABLE runs ADD COLUMN img_covered INTEGER DEFAULT 0;  -- L3 照片覆盖分子
```

### 4.2 `start_run(trigger, online_total=0)`
- run 开始时，从 `online_stats`（当日各组最近一次 `online_total`）求和传入 `online_total`，落 `runs.online_total`。
- 若当日无 `online_stats`（老库/首跑），`online_total=0` → 面板显示"—"而非 0（与 `online_coverage` 一致）。

### 4.3 `progress_run(run_id, scanned, fetched, new_count, change_count, pdf_saved)`
- 现有签名补 `pdf_saved`（来自 `_BatchSink.stats.pdf_saved`），一并写入 `runs`。

### 4.4 新增 `Store.run_progress(run_id) -> dict`
返回三层口径（供 API/UI 直接消费）：
```python
{
  "online_total": int,   # L1 分母（可能为 0 → 前端显示 —）
  "scanned":      int,   # L1 分子
  "fetched":      int,   # L2 分子
  "pdf_saved":    int,   # L3 分子
  "detail_remain": int,  # scanned - fetched
  "pdf_remain":    int,  # fetched - pdf_saved
  "new_count":    int,   # 本轮新增详情
  "pct": {"list": x, "detail": y, "pdf": z},   # 各层百分比（分母为 0 时 None）
}
```

## 5. 行为规格（三层各自怎么跑）

### L1 列表层
- **When**：每翻一页列表，解析全部行 → `scanned += 本页行数`；`progress_run` 实时写。
- **速度**：只解析列表 DOM，不开详情页，**最快**（符合用户"刷 3 下就拿全 130 条基本信息"）。
- **分母捕获**：进组时读 `結果 N 件`（已有 `_parse_total()`）→ 累计进 `online_total`。

### L2 详情层
- **When**：对 L1 每条，开详情页读全字段 → `detail_json` 落库即 `fetched += 1`。
- **部分完成处理（用户明说）**："产品页读完但详情页没读完，只要把详情页内容更新掉" →
  详情落库与 PDF 下载**解耦**：详情先落（`fetched++`），PDF 后台继续；PDF 失败/未完不影响详情已存。
- **真人化**：保留 v1.3.0 的页内乱序（12% 挪 1~2 条到页尾），一条不少。

### L3 文件层
- **When**：详情读时并行下 PDF（后台 `_PdfWorker`，最大在途 2）；下完 `pdf_saved += 1`。
- **照片数**：详情页解析 `image_count` → 落 `properties.image_count`（已有列）。
- **补全触发**：本轮结束前扫" `fetched` 已落但 `pdf_path` 空"的条目，补下 PDF（复用游标逻辑，不重复开详情）。

### 续传（跨轮，用户"剩 50 续下"）
- 重跑同条件时：列表层 `scanned` 重新累计；详情层**已有 `detail_json` 的跳过**（`_fetch_detail` 现有逻辑）；
  文件层**磁盘已有 PDF 的跳过**（v1.3.0 `_pdf_exists` 以磁盘为准）。
- ⇒ 自然实现"130 已下 80 → 下次只补剩 50"，且**进度面板能精确显示剩余**。

## 6. 进度面板 UI 设计（"我的页面"）

### 6.1 位置
概览页（首页 `/`）KPI 区下方，新增「**本轮下载进度**」卡片（常驻、最显眼）。
collect 页"正在抓取"区块也复用同一组件。

### 6.2 形态（三层各一行）
```
┌─ 本轮下载进度 ───────────────────────────────┐
│ 列表层   130 / 130  ✓            剩余 0      │  ▓▓▓▓▓▓▓▓▓▓ 100%
│ 详情层    80 / 130   (新增 12)    剩余 50     │  ▓▓▓▓▓▓▓░░░  62%
│ 文件层    75 /  80               剩余 5      │  ▓▓▓▓▓▓░░░░  94%
│ 本轮状态：进行中（自动更新 · 预计 19:22 下一轮） │
└──────────────────────────────────────────────┘
```
- 每行：标签 + 「分子 / 分母」+ （新增 N）+ 剩余 N + 进度条 + 百分比。
- `online_total=0`（无线上数据）时：列表层显示"— / —"，不画条。
- 无进行中轮次：显示**最近一轮完成态** + 提示「续传就绪：剩 N 个 PDF / N 条详情」。

### 6.3 刷新
- 复用现有 60s 轮询（`/api/ping` 顺带返回 `progress`，或新增 `GET /api/progress` 返回 `run_progress(最近进行中或最近一轮)`）。
- 进行中轮次 `busy=true` 时实时刷新；空闲时显示最近一轮快照。

### 6.4 i18n
新增键（四语言，沿用 `xf.*` 自家译名，禁照抄 REINS）：
`prog.title`=本轮下载进度 / `prog.list`=列表层 / `prog.detail`=详情层 / `prog.file`=文件层
`prog.remain`=剩余 / `prog.new`=新增 / `prog.resume_ready`=续传就绪 / `prog.idle`=本轮空闲

## 7. 需求（EARS 表述）

- **R1（列表分母）** The system shall 在每轮开始时，把本轮覆盖种目组在 REINS 上的「結果 N 件」合计记入 `runs.online_total`，作为 L1 分母。
- **R2（实时进度）** The system shall 在每批落库时把 `scanned/fetched/pdf_saved` 写入 `runs`，使进度面板能反映"进行中"的实时状态。
- **R3（进度 API）** Where 前端请求进度， the system shall 返回 `run_progress()` 的三层口径（含剩余与百分比）。
- **R4（面板展示）** The system shall 在概览页展示三层进度条（标签/分子分母/剩余/百分比），`online_total=0` 时显示"—"。
- **R5（部分完成解耦）** Where 详情已落库但 PDF 未下完， the system shall 保留详情、继续补 PDF，不回滚详情。
- **R6（续传对齐）** Where 重跑同条件， the system shall 跳过 `detail_json` 非空与磁盘已有 PDF 的条目，只补剩余，且进度面板精确显示剩余。
- **R7（确定性）** If 中断发生， the system shall 至多丢失当前正在处理的 1 条（沿用 v1.3.0 `flush_every=1` + 原子落盘）。

## 8. 验收标准

| # | 验收项 | 通过条件 |
|---|---|---|
| 1 | L1 分母正确 | 跑一轮后 `runs.online_total` = 当日 `online_stats` 各组 `online_total` 之和 |
| 2 | 三层分子自洽 | `scanned ≤ online_total`、`fetched ≤ scanned`、`pdf_saved ≤ fetched` 恒成立 |
| 3 | 面板实时 | 进行中轮次，进度条随落库增长（非等结束才跳） |
| 4 | 部分完成 | 构造"详情落、PDF 失败"→ `fetched++` 且 `pdf_saved` 不增、详情不丢 |
| 5 | 续传 | 中断后重跑同条件：`scanned` 重置但 `fetched/pdf_saved` 不因已存在而重复增长；面板剩余递减到 0 |
| 6 | 确定性 | 模拟中途 kill：重启后 `properties` 缺的仅"被杀时正在处理的 1 条" |
| 7 | 无线上数据 | `online_total=0` 时面板列表层显示"—"，不画假 100% |

## 9. 实现建议（给研发的落地顺序）

1. **数据层**：`runs` 加 `online_total`/`pdf_saved`（`_ensure_columns` 幂等）；`start_run` 接 `online_total`；`progress_run` 补 `pdf_saved`；`run_progress()` 新函数。
2. **爬虫层**：`start_run` 调用处传入 `online_stats` 合计；`_BatchSink.flush` 已写 `pdf_saved`，只需透传。
3. **接口层**：`/api/overview` 加 `progress=STORE.run_progress(当前/最近轮)`；或独立 `/api/progress`。
4. **前端层**：概览页加进度卡片组件 + i18n；60s 轮询带进度。
5. **验证**：写 `_verify_v131.py` 用临时库 + 构造 runs 断言三层自洽 + 模拟旧后端渲染面板不崩（热重载契约）。

> ⚠️ **热重载契约**：进度卡片模板引用 `progress` 新键 → 必须用 `progress.get('k', …)` 兜底；新 Jinja/stat 不硬依赖。验证姿势同 `05`：模拟旧后端渲染全 PASS。

## 10. 范围与不做项

- **做**：三层进度模型 + 进度面板 + 续传可视化。
- **不做（本次）**：指定日期下载路径（`_collect_from_results`）的 L3 后台 PDF 仍同步（v1.3.0 已知 ⏳，另案处理）；照片覆盖进度默认不展示（数据已采，面板可后续加）。
- **依赖**：v1.3.0 的确定性存储 + 断点续传范式（必须先落地，本 PRD 在其上增量）。
- **生效**：改 `.py` + 模板 → **需重启 `start_mvp.bat`**（页脚变对应版本才生效）。
