## 0. 背景与一句话结论

系统定位：面向大阪不动产中介客户的 REINS 房源爬虫（osaka-mvp）。
本轮对话由用户的 5 个关注点推进：**① 详情页 20s 是不是大陆访问日本的锅？② 三个界面问题 + 变更差异怎么看？③ 范围拍板。④ 重新定义下载核心模型＝两阶段。⑤ 追加 UI 需求并授权直接做到 v1.4.0。**

## 1. 风控根因探讨（对话 A）—— 已订正结论

用户原疑问：详情页 ~20–22s 是否因「上海/大陆访问日本服务器」？在日本实际访问是否更快？能否模拟在日本运行让对方觉得是真人在操作？并要求验证「REINS 风控三句话」（会话有效 / 节奏像人 / 真浏览器）是否属实且全覆盖。

**验证结论（已订正，推翻了早先几处误判）：**
- 详情页已用 `domcontentloaded`（非 `networkidle`），故「等整页资源」假设**错**。
- **20s 根因 = REINS 服务端渲染慢**（连 DCL 都 ~20s），与地理/IP 无关。
- 在日本本地实际访问**仅省 1–2s**；放机房 IP 更不像真人（**负贡献**，且可能更易被风控）。
- 风控三句话（会话有效 / 节奏像人 / 真浏览器）**基本覆盖且已具备**；当前真实缺口只有一处：**`navigator.webdriver` 屏蔽**（Playwright 默认会被识别），属风控加固零副作用项，待补。
- 用户最初设想的「先返回空壳、再 JS 填充 → 只抓空壳提速」方案：**对 REINS 不成立**（REINS 是服务端渲染，没有空壳+异步填充的提速空间）。

**风控加固待办（零副作用，建议随 v1.4.0 顺带补）：** 隐藏 `navigator.webdriver`（`context.add_init_script` 注入 `Object.defineProperty(navigator,'webdriver',{get:()=>undefined})`）。

## 2. 三个界面问题 + 变更差异流程（对话 B）

用户截图提出三点 + 一条变更差异流程：

### 2.1 KPI 卡点进去进对应查询列表页
- 现状：概览页 KPI 卡（本地房源总数 / 今日更新 / 今日降价 / 已存盘 PDF / 最近一次更新）是静态数字。
- 需求：**点卡片跳到对应查询列表页**（如「今日降价」→ 查询页带降价筛选）。
- 决策：**做**（纯前端热重载，不碰 .py）。

### 2.2 为什么有三个「进行中」
- 现象：概览页显示三个 run 同时「进行中」。
- 根因（显示 bug）：进程被 kill（用户多次手动重启）时 `finish_run` 未执行，`runs` 表行永远卡 `running`。
- 修复：**服务启动扫一遍 `runs` 表，`status='running' AND finished_at IS NULL` 的行统一标 `interrupted`**。

### 2.3 变更信息与上一次变更的差异
用户给的三步流程：
1. 找到上一次变更的时间并查出来；
2. 与现在对比找差异；
3. 记录差异（金额写金额、其他写内容）。

**可行性判定（关键）：**
- `changes` 表目前只有 79 套带 `previous_price` 有 old/new 可比，其余仅 `new` 无「上一次」—— 因为 `differ.pick_queue()` 对已有 `detail_json` 的房源跳过，从不重抓 → 系统自己检测不到后续变更。
- **正确做法 = 本地 `property_history` 快照表**（每轮抓前对全量房源存一份快照，差异靠本地比对，不回线上查，避免风控）。
- **用户当时未拍板**（「这一段我还不是特别确认」）—— 见 §8 待决。

### 2.4 历史查询 & 查询时机
- 历史查询：**先查本地历史库，有就用；没有再去线上查**。
- 查询时机：**所有内容下载完后再查历史**（避免下载中途库不完整导致误判）。

## 4. 重新定义下载核心模型：两阶段（对话 D）← 本轮核心

用户重新框定：「查询到当前页面多少页，就该把该页内容下载到查询页，让两者一致；再去查详情页和 PDF。」明确分两次操作：

### 4.1 阶段1 · 快速同步查询信息
- 快速调用检索结果（只解析列表行 `_parse_list_row`，**不开关详情页**），确保后台查询页与 REINS 检索页一致。
- 很快完成，完成后**告知实际数据多少**（如「REINS 检索页 130 件 / 后台已同步 130 件」）。

### 4.2 阶段2 · 逐步查询详情页
- 同步完成后，慢慢查详情页（`_fetch_detail`，~20s/条，后台持续），并接后台 PDF 下载（v1.3.0 的 `_PdfWorker`，最大在途 2）。
- 始终在跑，不阻塞阶段1的同步结果展示。

### 4.3 明确数据同步情况（同步状态面板）
- 概览/查询页显示：「**REINS 检索页数据** vs **软件后台查询页数据**」各多少条（**尤其当天**），保持相对一致。
- 这是 §2.2 之外另一个「进行中」错觉的治本：用户能直接看到两边条数差，判断要不要等。

### 4.4 核心目的与权衡
- **让查询页快速及时与平台基础数据同步**，可**牺牲单个详情/PDF 下载速度**（详情/PDF 慢补不影响列表一致性）。

### 4.5 技术可行性（已用代码证据确认）
- 列表行字段（`price`/`layout`/`line_station`/`address`/`exclusive_area` 等）由 `LIST_FIELD_MAP` 网格坐标解析，**不需要开详情页**。
- `_BatchSink.add(rec)` 可仅列表即落库（`flush_every:1` 每条即时落）。
- ⇒ 阶段1「只列表」在技术上完全可行，无需重开详情页。

### 10.2 两个「非显然」的坑（写错就静默失效，务必记住）

1. **阶段2 不能用 `sink.add()`。** `_BatchSink.seen` 在阶段1 已记下该物件番号，阶段2 再 `add` 会被当「轮内重复」直接 `return False`，详情**永远写不进库且不报错**。所以阶段2 直连 `pipeline.ingest([rec], ...)`，再把统计并回 `sink.stats`。
2. **阶段2 必须在 `with _sync_playwright()` 内**（`browser.close()` 之前）——它靠 `ctx.new_page()` 打开详情页，浏览器关了就打不开。当前阶段2 位于 `if worker is not None:` 收尾之前，正确。

### 10.3 顺手修掉的两个既有缺陷

- **潜伏 NameError**：`_live_items` 里误用 `self.stats["ms_delay"]`（模块级函数没有 `self`），v1.3.1 埋点引入。因服务一直没重启尚未发作，**一旦重启会在第一条需抓详情的房源上炸掉整组**。已改为 `sink.stats`。

### 12.1 「今日降价」这数据不对 —— 算法解释 + 悬浮说明

**PM 原话**：「今日降价 这个数据应该也不对啊？你的算法是什么？对应在鼠标悬浮的时候显示。」

**旧算法（错的）**：
```
今日降价 = changes 表里 change_type='price_down' 且 detected_at 落在今天的房源数
```
`detected_at` 是"我方把这条变更写进流水的时间"。而 `price_down` 流水是**我方第一次抓到这套房源**时写的（首抓分支看 `previous_price>price` 就记 price_down），所以 `detected_at` 实际≈这套房的 `first_seen_at`。
⇒ 后果：「**今天才抓到、但平台上周就降过价**」的房源，会被算成"今日降价"。数字虚高。

**新算法（v1.4.4 落地）**：以 REINS 平台自身盖的章为准——
```
今日降价 = properties 表中 previous_price > price（确凿降价）
          且 REINS「変更年月日」(change_date 和暦) 转公元年 == 今天
```
只有"平台**今天**确凿降价"的房源才算今日降价；首抓即已打折的（变更日在过去）不计入。

**实测对账**（活库 2026-09-14）：
| 日期 | 平台标注降价数 |
|------|------|
| 09-11 | 61 |
| 09-12 | 31 |
| 09-13 | 40 |
| **09-14** | **0** |

⇒ 09-14 卡片由虚高 **1**（一条伪降价）修正为正确 **0**。今天显示 0 **不是 bug**：表示"没有平台在今天盖戳降价的房源"，已打折但早于今天的房源不计入。

**悬浮说明（已加到 KPI 卡片，鼠标悬停即见，四语言）**：
> 今日降价 = REINS 平台标注「変更年月日」为今天、且挂牌价低于变更前价的房源数。以平台自身降价的官方日期为准，避免把"今天才抓到、但前几天就已降价"的房源算进来。今天若显示 0，表示没有平台在今天盖戳降价的房源（已打折但早于今天的房源不计入）。
