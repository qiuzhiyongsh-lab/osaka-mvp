## 2. 数据分层（把你的想法落到可执行的三层）

你原话里的分类我整理成下面三层，并补上每层的**判定规则**、**存储介质**、**保留期**和**降级动作**。

| 层 | 你的描述 | 内容 | 实测体积 | 时效性 | 介质 | 保留 |
|---|---|---|---|---|---|---|
| **L1 大对象** | 第一类：大型 PDF / JPG | 房源図面 PDF、截图 | 405 MB（99%） | 高→**随时间快速衰减** | 本地 SSD（热）→ 对象存储（温/冷） | 见 §5 |
| **L2 日常数据** | 第二类：每天产生的数据 | SQLite 主库、变更流水、运行日志、导出 Excel、按天页 | ~2.5 MB | 中，需长期可查 | 本地 SSD + 异地备份 | 长期 |
| **L3 派生数据** | 第三类：AI 分析 / 按条件生成 / 个性化 | AI 生成的房源解读、打标结果、发布文案、个人配置 | 目前几乎为 0（尚未产生） | **短期高、长期低** | 小服务器 / 对象存储，弹性空间 | 短期 |

**关键判断**：L1 和 L2/L3 的体量差 **160 倍**。所以——
- L2、L3 随便放，怎么放都不是问题；
- **架构复杂度应该全部花在 L1 上**，L2/L3 越简单越好。

## 3. 需求描述（EARS 格式）

### L1 大对象
- **R1.1（Ubiquitous）** 系统应始终把「最近 90 天」的 PDF 保留在本地 SSD，保证详情页/查询页点开即用（无等待）。
- **R1.2（Event-driven）** 当某份 PDF 的最后访问时间早于 90 天时，系统应将其标记为「待降冷」，并在下一次归档任务中上传至对象存储。
- **R1.3（Unwanted）** 若归档上传失败，系统应保留本地副本并在下一轮重试，**不得**在未确认上传成功前删除本地文件（防丢数据）。
- **R1.4（State-driven）** 当房源被删除或标记为无效时，其 PDF 应进入「待清理」队列，30 天后才真正删除（留出反悔窗口）。

### L2 日常数据
- **R2.1（Ubiquitous）** 系统应每日将 `jproperty.db` 以 SQL 文本形式（`.dump`）导出一份，保留最近 30 份。
- **R2.2（Event-driven）** 每轮抓取结束后，系统应将当轮统计写入 `runs` 表并落盘（已实现）。
- **R2.3（Unwanted）** 若备份目标不可达，系统应记录告警并继续运行，**不得**阻塞抓取主流程。

### L3 派生数据
- **R3.1（Optional）** 若启用 AI 分析功能，其结果应写入独立存储区，与 L1/L2 物理隔离，便于单独清理。
- **R3.2（Event-driven）** 当用户执行「清理派生数据」时，系统应删除全部 L3 数据且**不得**影响 L1/L2。

## 4. 架构方案

```
┌──────────────────────── 本地（重庆，抓取专用）────────────────────────┐
│                                                                      │
│  start_mvp.bat  →  Flask 8765  ←  REINS 抓取（Playwright + Edge）      │
│        │                                                             │
│        ├─ L1 热 PDF（近 90 天）  data/attachments/     ~1.3 GB        │
│        ├─ L2 结构化              data/jproperty.db      ~几十 MB      │
│        └─ L3 派生（AI 生成）      data/derived/          ~百 MB        │
│                                                                      │
│  每日：SQLite → .dump → 对象存储（版本化）                             │
│  每 90 天：L1 冷 PDF → 对象存储（低频/归档），本地留占位                │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ 单向推送（本地 → 云）
                               ▼
┌──────────────────────── 云端（可选，展示与分析）──────────────────────┐
│                                                                      │
│  轻量应用服务器 2C2G / 40GB SSD                                       │
│    ├─ 只读查询页 / 概览（从本地同步的 L2 快照）                        │
│    ├─ AI 分析与内容生成（L3）                                         │
│    └─ 微博发布器（你设想的功能）                                       │
│                                                                      │
│  对象存储桶                                                            │
│    ├─ /db-backup/    每日 SQL dump（版本化，可回滚到任意天）            │
│    ├─ /pdf-cold/     90 天前的 PDF（低频）                             │
│    └─ /pdf-archive/  1 年前的 PDF（归档）                              │
│                                                                      │
│  ⛔ 不部署：REINS 抓取任务（风控红线，见 §6）                           │
└──────────────────────────────────────────────────────────────────────┘
```

**设计原则**：
1. **抓取留在本地**——这是风控要求，也是性能现实（见 §6）。
2. **本地 → 云单向推送**——云端永远不回写本地，避免双向同步的一致性地狱。
3. **L2 用文本 dump 而非二进制备份**——SQL 文本可 diff、可 Git 版本化、可精确回滚到某一天（见 §5.3）。

## 5. 各层落地策略

### 5.1 L1 大对象（PDF）——重点

**分层时间表**

| 层 | 判定 | 介质 | 取回延迟 | 相对成本 |
|---|---|---|---|---|
| 热 | 90 天内 | 本地 SSD | 即时 | 基准 |
| 温 | 90 天 ~ 1 年 | 对象存储·低频 | 即时（毫秒级） | 约为标准的 1/2 |
| 冷 | 1 年以上 | 对象存储·归档 | 需解冻（分钟级） | 约为标准的 1/5 ~ 1/10 |

**成本实测换算**（按当前 405 MB、稳态月增 ~440 MB 估算）

| 时点 | PDF 总量 | 对象存储月费（量级） |
|---|---:|---:|
| 现在 | 0.4 GB | 约 0.05 元/月 |
| 1 年后 | ~5 GB | 约 0.6 元/月 |
| 3 年后 | ~16 GB | 约 2 元/月 |

> 价格取自国内主流对象存储常见档位，**仅为量级参考，实际以官网当时报价为准**。

### 5.2 ⚠️ 一个重要纠正：「3 个月降冷」省的不是钱

你设想"每隔 3 个月用更低成本方式保存备份"——方向对，但**动机要修正**：

按上表，3 年后全部 PDF 放标准存储也才约 2 元/月。**降冷省下的钱可以忽略不计。**

降冷的**真实价值**是这三条：
1. **本地磁盘不爆**——笔记本/台式机 SSD 宝贵，1 GB 变 16 GB 时本地体验会明显下降；
2. **备份窗口变短**——要备份 400 MB 和备份 16 GB 是两个量级，后者会让每日备份变得不现实；
3. **检索与索引更快**——文件数从几万降到几千，目录枚举和同步都更快。

**结论**：做，但按"运维收益"立项，不要按"省钱"立项——否则你会觉得这事不值得做而一直拖着。

### 5.3 L2 日常数据——用 SQL 文本备份，别直接拷二进制

`jproperty.db` 只有 1.46 MB，非常小。但**不要**简单地把 `.db` 文件拷去备份，原因：
- SQLite 二进制文件**无法 diff**，看不出今天改了什么；
- 直接拷贝可能拷到"写入中途"的损坏快照（虽有 WAL，但不保险）；
- 无法精确回滚到"某一天"。

**推荐做法**：
```bash
sqlite3 data/jproperty.db .dump > backup/jproperty_$(date +%Y%m%d).sql
```
- 输出是**纯文本**，可 diff、可 Git 版本化、可压缩（文本压缩率很高）；
- 1.46 MB 的库 dump 出来约几 MB，压缩后更小；
- 每天一份，保留 30 份，成本几乎为零。

**进阶（可选）**：若将来要求"秒级 RPO"，可上 [Litestream](https://litestream.io) 做 SQLite 流式复制，但对当前规模属于过度设计，**不建议现在做**。

### 5.4 L3 派生数据

目前尚未产生。按你的描述"数据量不会大于实际下载数据，除掉图片几个月顶天几百兆"——与实测吻合（L2 才 1.46 MB，L3 即使大 100 倍也才百 MB 级）。

**策略**：
- 与 L1/L2 **物理隔离**（单独目录/前缀），便于一键清理；
- 放小服务器即可，无需为它单独规划容量；
- **可随时重建**是它的定位——真丢了重新跑一遍 AI 即可，所以备份优先级最低。

## 6. ⛔ 红线：REINS 抓取不要上云

你设想 (c)1"源代码可以在上面跑"。这一点必须**按负载拆开看**：

| 负载 | 能否上云 | 原因 |
|---|---|---|
| REINS 抓取（Playwright） | **绝对不要** | ① 云服务器 IP 段是风控重点照顾对象，**更像机器**，反而更容易被封（PRD 05 已定论）；② 详情页 ~20s 是 REINS **服务端渲染慢**，换机房不提速（日本本地也只省 1–2s）；③ 抓取需要真实浏览器 + 已登录会话，云端无头环境更难伪装 |
| 查询 / 概览展示 | ✅ 可以 | 纯读本地数据副本 |
| AI 分析 / 内容生成 | ✅ 可以 | 调云端大模型，与 REINS 无关 |
| 微博发布器 | ✅ 可以 | 与 REINS 无关 |

**这是本 PRD 最重要的一条结论**：你之前的想法里隐含有"把东西都搬上云跑"的倾向，但对本项目的抓取部分，上云是**负收益**。

## 7. 代码管理与分发（你设想的 (c)3）

完全可行，而且是业界标准做法。

```
本地开发  →  git commit  →  Git 仓库（单一事实来源）
                                │
                                ├─ 本地：git pull → 继续开发
                                └─ 服务器：git pull → 重启服务 → 完成部署
```

**要点**：
1. **凭据绝不入库**——`data/` 下的 `session.json`、`credentials.json`、`.cred_key` 必须在 `.gitignore` 里（本项目已排除 ✅）。
2. **配置文件单独放**——`config.yaml` 入不入库取决于是否含敏感信息；建议提交一份 `config.example.yaml`，真实配置在服务器上单独维护或用环境变量覆盖。
3. **版本标记**——每次发布打 `git tag v1.4.1`，与 `core/version.py` 保持一致（本项目已有 `version.py` 作为单一来源 ✅）。
4. **回滚**——出问题时服务器 `git checkout v1.4.0` 即可，与本项目 `checkpoint.py` 的回滚能力互补。
