## 1. 需求 1 · 更新方式：默认关闭

### 1.1 需求描述（EARS）

- **R1.1（Ubiquitous）** 系统应把「自动更新」开关的**默认值设为关闭**——未经用户显式开启，不得自动发起任何抓取轮次。
- **R1.2（State-driven）** 当自动更新处于关闭状态时，系统仍应保留完整的间隔配置（110–130 分钟随机、07:00–23:00 窗口）并在界面上显示，供用户随时开启。
- **R1.3（Event-driven）** 当用户显式开启自动更新后，系统应在 07:00–23:00 窗口内、按 110–130 分钟随机间隔发起轮次；窗口外不发车。
- **R1.4（Unwanted）** 若用户从未开启过自动更新，系统不得因服务重启、配置重载等原因自行启动调度。

### 1.2 现状与改动

| 项 | 现状 | 目标 |
|---|---|---|
| `config.yaml` → `schedule.enabled` | `true` | **`false`** |
| 界面「自动更新」状态 | 显示「运行中」 | 显示「已停止」 |
| 110–130 分钟 / 07:00–23:00 | 已配置 | 保留不变，仅作为"开启后的规则"展示 |

### 1.3 ⚠️ 口径待你确认

你原话是「当前规则：随机间隔 110–130 分钟（07:00–23:00 内）**到默认平台是关闭的**，我们默认这个时段不做更新」。
我理解为：**自动更新默认关闭，不开就不跑**；110–130 分钟和 07:00–23:00 是"开启后才生效"的规则，配置要保留、只是默认不启用。

如果这个理解有偏差（比如你是想说"07:00–23:00 这段时间内一律不更新，只在别的时间更新"），请告诉我，这条改动方向完全不同。

## 2. 需求 2 · 关键词字段缩短

### 2.1 问题

查询页关键词的标签当前是：

> 关键词（地址 / 楼名 / 物件番号 / 駅・沿線 / 間取り … 模糊匹配，含即命中）

这一长串把输入框的可用宽度挤掉很多，导致右侧的区、日期等字段被压到下一行，整行看起来松垮。

### 2.2 需求描述（EARS）

- **R2.1（Ubiquitous）** 关键词字段的**可见标签应简化为「关键词」两字**。
- **R2.2（Ubiquitous）** 系统应保留"支持哪些字段、怎么匹配"的完整说明，但**改为悬停提示**，不占版面。
- **R2.3（State-driven）** 标签缩短后，同行其余字段应能自然上移/并排，使整行更紧凑。

### 2.3 方案

| 位置 | 现在 | 改为 |
|---|---|---|
| 标签 | 关键词（地址 / 楼名 / 物件番号 / 駅・沿線 / 間取り … 模糊匹配，含即命中） | **关键词** |
| 悬停 | 无 | 提示：「地址 / 楼名 / 物件番号 / 駅・沿線 / 間取り，模糊匹配，含即命中；空格分隔多词＝都要命中」 |
| 占位符 | 例：中之島 / グランドメゾン / 天下茶屋 / 3001407 | 保留 |

四语言同步：新增 `search.q.tip` 键（中/繁/英/日）。

## 3. 需求 3 · 运行记录字段悬停说明

### 3.1 需求描述（EARS）

- **R3.1（Ubiquitous）** 运行记录表的**每一个表头**都应带悬停提示，说明该字段的**含义**与**使用规则**。
- **R3.2（Ubiquitous）** 提示内容应覆盖：字段是什么、怎么算出来的、看这个数时要注意什么。
- **R3.3（State-driven）** 概览页与运行日志页的同一字段，提示文案应保持一致。

### 3.2 字段释义表（将作为悬停文案落地）

| 表头 | 含义 | 使用规则 / 注意事项 |
|---|---|---|
| **#** | 轮次唯一编号（自增） | 越大越新；报错时按这个号去日志里定位 |
| **触发** | 本轮由什么发起 | `manual`＝手动点「手动更新」；`random`/`interval`＝调度器自动；`startup`＝服务启动即跑；`specified-download`＝指定日期下载；`test-download`/`real-download`＝测试/真实下载。**用它区分"人为的还是自动的"** |
| **开始** | 本轮开始时间（本机时区） | — |
| **结束** | 本轮结束时间 | 为空＝还没结束（进行中）；若被标 `interrupted`，说明上次进程被直接关掉、没正常收尾（v1.4.0 起启动会自动补状态） |
| **扫描** | 本轮从列表页读到的房源条数（**列表层**） | v1.4.0 起与「落库」分离：**只刷新了列表字段的轮次，扫描>0 而落库=0 是正常的**，不是没跑 |
| **落库** | 本轮真正写入/更新详情的条数（**详情层**） | 两阶段下载中，这一项在阶段2（补详情）才会增长 |
| **新盘** | 本轮**首次**进入本地库的房源数 | 注意：平台早已改过价、我方才第一次抓到的，算**变更**不算新盘（见 PRD 6.11） |
| **变更** | 本轮识别到的变更条数（改价 / 信息变动） | 按条数计，非去重套数；同一套房可能有多条 |
| **状态** | 本轮结果 | `ok`成功 ／ `running`进行中 ／ `error`失败 ／ `interrupted`被中断 |
| **备注** | 失败原因或补充说明 | 最多显示 70 字符，完整内容见服务日志 `data/logs/server.log` |

### 3.3 实现要点

- 表头加 `title` 属性（原生悬停，零依赖、移动端不踩坑）；
- 文案走 i18n 新键 `runs.tip.*`，四语言同步；
- 概览页「最近运行」表头同样加上。

## 4. 需求 4 · AI 提取 PDF 内容（v1.4.2，**本期仅 PRD**）

> 你的要求：(a) 开发放 1.4.2；(b) 先出 PRD 稿，把**页面设计**和**逻辑规则**写清楚供你审核。

### 4.1 功能一句话

选某一天（或自动对新 PDF），把每份房源図面 PDF 的关键内容用 AI 抽出来，结构化后写进该房源的详情页。

### 4.2 页面设计

**入口 A：房源详情页新增「AI 解读」卡片**

```
┌─ AI 解读 ────────────────────────────────┐
│ 状态：已生成 · 模型 xxx · 2026-09-14 01:20 │
│                                            │
│ 間取り   3LDK                              │
│ 専有面積 76.85 ㎡                           │
│ 築年月   2019年3月                          │
│ 最寄駅   大阪メトロ谷町線 田辺 徒歩8分       │
│ 備考    ペット相談可／南向き                │
│                                            │
│ [重新生成]  [编辑]  [查看原始PDF]           │
└──────────────────────────────────────────┘
```

**入口 B：批量（按天）— 「数据抓取设置 → AI 功能」**

```
AI 功能
  开关    [ 启用 ]
  模型    [ 下拉：供应商 + 模型 ]
  提示词  [ 文本框，可保存多套模板 ]
  触发    ( ) 手动选一天   ( ) 自动：每天对新落盘的 PDF
  每日上限 [ 200 ] 份           ← 成本控制，超出顺延到次日
  最近任务 [ 表格：日期 / 份数 / 成功 / 失败 / 状态 ]
```

### 4.3 逻辑规则

| 规则 | 说明 |
|---|---|
| **前置条件** | 只处理**已落盘**的 PDF（磁盘上文件存在且 >0 字节）；没有 PDF 的房源直接跳过 |
| **去重** | 同一份 PDF（按文件哈希）**不重复跑**；PDF 未变化则复用上次结果 |
| **状态机** | `pending → running → ok / failed`；`failed` 可手动重试 |
| **不覆盖人工** | 若用户手改过某字段，后续自动重跑**不得覆盖**该字段（人工优先） |
| **成本控制** | 每日处理上限；到达上限后剩余任务顺延次日，并写通知 |
| **失败处理** | 单份失败不影响整批；失败原因写 `notifications`；连续失败 N 次暂停任务并告警 |
| **可追溯** | 每次提取记录：模型名、提示词版本、PDF 哈希、耗时、原始返回（便于复盘和换模型对比） |

### 4.4 数据存储（v1.4.2 时定）

建议**独立表** `ai_extractions`，不直接改 `properties`：
`id / property_no / pdf_hash / model / prompt_version / result_json / status / cost_ms / error / created_at / updated_by`

理由（与 PRD 08 的 L3 派生数据分层一致）：
- AI 结果属于**派生数据**，与 L1/L2 物理隔离，便于一键清理；
- 换模型重跑时能保留历史版本做对比；
- 丢了可重建，备份优先级最低。

### 4.5 待你审核的决策点

- **Q1**：AI 解读结果展示为「结构化字段表」还是「一段自然语言摘要」？（我建议**先结构化**，摘要后续再加）
- **Q2**：自动触发的时机——是"PDF 落盘后立刻"还是"每天固定时间批量跑"？（建议后者，便于限流）
- **Q3**：每日上限定多少？
- **Q4**：是否需要中日双语输出？
