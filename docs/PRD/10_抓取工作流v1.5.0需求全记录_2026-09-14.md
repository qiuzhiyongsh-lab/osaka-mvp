## 0. 一句话目标
把「一轮抓取」重做成 **12 子查询 + 三阶段（列表匹配 → 详情回填 → 下架检测）** 的可解释流水线，
并把勇哥真机推翻的「详情页 ~20s」假设改为 **2~4s 随机间隔 + bfcache 返回**。

## 1. 用户原话（保留，未改）
> **12 次的查询。每轮查询时间间隔在 10~20 秒左右。**
> 房型的选择有 6 个条件：一户建 / 新築戸建 / 中古戸建 / 公寓 / 新築マンション / 中古マンション / 新築タウン；
> 另，新增和变更的条件相当于 2 个条件。如果把这些条件全部拆开，相当两两组合，可以进行 12 次查询。
> 这样当天整体的数据量在绝大部分情况下应该会少于 500 条，所以我认为以 500 条封顶。
> 而且如果每天正常运行，每两个小时左右刷新一次，单次查询不可能超过 500 条，所以这方面应该没有问题。
>
> **PDF 下载问题：只要触发了下载，我认为就没有问题了，你不用管它下载是否成功。**
>
> 原先说"在列表页里面点进详情页，把详情页的内容和 PDF 文件拉下来，然后再返回列表页，点下一个详情页去拉取"，
> 这个过程的时间差需要 20 秒左右。但我实际在电脑上操作发现，这个时间差非常快，点完以后再点返回，
> 就可以直接进入原先的列表页，中间没有等待时间。因此，两个操作之间的等待时间是随机的，设置在 2~4 秒左右就可以了。
>
> 作为一轮工作，在检索页录入条件后检索完之后的列表页里面：
> 1. **列表页抓取与匹配**：(a) 查到对应的页面数量。如果超过 500 条，就按 500 条查询。
>    (b) 每页 50 条，最多抓取 10 页。把这 10 页的所有内容全部拉下来。
>    (c) 将拉取的内容与我现在的库进行匹配。如果库里没有，就把列表页的内容填到我的后台里；如果有，就不用填。
> 2. **详情页更新**：(a) 从第一页开始，如果内容是我之前没有的，就点击对应的详情页进行更新。
>    (b) 详情页的更新速度需要更快一些，大概在 2 到 5 秒左右，使用随机数循环一次即可。这样就可以一次性把这 500 条全部更新一遍。
>    (c) 如果存在历史上已经有过的数据，就不用再进行二次详情拉取了。
> 3. **下架/成交检测（is_active=0）现在就做。**

## 2. 总体工作流（v1.5.0）
```
阶段0  检索循环：对 12 个子查询（6 房型 × {新增, 变更}）各跑一次 REINS 检索
        ├─ 每个子查询之间停顿 subquery_interval_seconds = [10, 20] 秒
阶段1  列表抓取与匹配（每个子查询内）
        ├─ 1.1 读该子查询结果总件数（正常 <500；触顶按 500 / 50 每页 / 10 页）
        ├─ 1.2 把该子查询全部页列表内容一次性拉下（只读本地 DOM，零 REINS 重请求）
        └─ 1.3 聚合匹配落库：库无 → insert；库有 → 更新列表级 price/status 等字段，但【不】重抓详情
阶段2  详情回填
        ├─ 2.1 仅对 detail_json 为空的行点「詳細」（正好补 371 空详情缺口）
        ├─ 2.2 每次间隔随机 2~4s；点完 page.go_back() 走 bfcache 瞬时返回列表
        ├─ 2.3 详情页：拉字段 + 触发 PDF 下载（不校验成功）→ 写回 detail_json
        └─ 2.4 已有 detail_json 的行跳过（不二次拉取）
阶段3  下架检测：本轮 12 子查询并集里消失的房源 → is_active=0（连续 2 轮不在才标）
```

## 3. 12 子查询（6 房型 × 2 轴）
- **房型（6）**：新築戸建 / 中古戸建 / 新築マンション / 中古マンション / 新築タウン / 中古タウン
  （config `search.update_groups` 原 3 组「2 房型一对」在 v1.5.0 被 `_update_groups` **拆平**为单个房型，
  再按轴翻倍 → 12 个子查询；见 `core/crawler.py:_update_groups`）。
- **轴（2）**：新增 / 変更。
  - **重要事实**：REINS 检索页**没有独立的「変更」筛选器**（只有「新着」类筛选，无"仅变更"）。
    故两轴实际跑的是**同一全期检索**；"新增 vs 变更"由本地 `changes` 引擎（首抓 vs previous_price 比对）区分。
  - 即 12 次物理查询 = 6 房型各跑 2 遍（全期）。覆盖完整、本地变更识别准确；代价是 REINS 负载 ×2，用户已拍板接受。
- **间隔**：`subquery_interval_seconds = [10, 20]`（组间停顿，user 拍板）。
- **≤500 封顶**：`max_pages = 10`（50/页 = 500 件 = REINS 硬上限）。单子查询 <500，整体覆盖完整，无需再拆条件（用户原话"单次查询不可能超过 500 条"已验证该假设）。

## 4. 详情节奏 2~4s（勇哥真机推翻旧 20s）
- **旧"~20s/条"怎么来的（错误）**：程序用 `page.goto(详情) + wait_for_load_state('networkidle') + 等 PDF 全资源 + 重新 goto(列表)`，
  这一串累计 ≈20s，被当成"详情页本身慢"。
- **真机实测（正确）**：点「詳細」→ 详情服务端渲染只需几秒；点「返回」→ **浏览器走 bfcache，列表从内存缓存瞬时恢复**，根本不重抓。
  所以"中间没等待"是真的。
- **v1.5.0 拍板**：
  ① 操作间隔用 **随机 2~4s**（`detail_gap_seconds = [2, 4]`，人防机器人足够）；
  ② 返回用 **`page.go_back()` 走 bfcache**（瞬时，不重新 goto 列表）；
  ③ 真正变量成本只剩 **详情加载(几秒) + PDF 触发(不校验成功)**，单条约 2~8s。
- 配置：`crawl.delay_range_seconds` 与 `crawl.detail_gap_seconds` 均为 `[2.0, 4.0]`。

## 5. 阶段1 列表匹配（明确"已有行也要更新"）
- 库无 → `insert`（列表字段 + `first_seen_at` + `is_active=1`）。
- 库有 → **更新该行列表级字段（price / status / 地址 / 面积 等），但【不】重抓详情**。
  实现：`rec["_list_only"]=True` → `pipeline.ingest` 走列表模式，保留已有 `detail_json`
  （`if old["detail_json"]: rec.pop("detail_json")`）。
- **为什么必须有这步**：若"库里有就完全不填"，价格变动会被漏掉 → 刚修好的「今日降价」检测失效（回潮）。
  这是 v1.5.0 必须保住的不变量。

---

## 6. 阶段2 详情回填（含 371 空详情缺口一次性补齐）
- **范围**：仅 `detail_json` 为空的行（`need_detail = existing is None or not existing["detail_json"]`）。
- **两类路径**：
  - **(A) 行内有 GBK 直链（href）**：阶段2 用 `ctx.new_page()` + `goto(href)` 抓（快，不碰列表页）。沿用 v1.4.x。
  - **(B) 行内无直链（詳細 是 `<button>`）**：这是旧版 371 条空详情的根因——阶段2 无活列表可点，只能跳过。
    **v1.5.0 改为：在阶段1 列表页遇到这类行，当场 `rows.nth(i).locator('詳細').click()` → 同标签跳详情 →
    拉字段 + 触发 PDF → `page.go_back()` 回列表（bfcache 瞬时）**。新增 `_fetch_detail_inline`（同标签跳转；
    拿不到直链 / 解析失败一律返回 None，**绝不写脏**，下轮重试）。
- **节奏**：每条 2~4s 随机（`detail_gap`）。
- **已有 detail_json 的行跳过**（不二次拉取，省时、避免重复 PDF）。

## 7. 阶段3 下架/成交检测（is_active=0）—— 本次实现
- 本轮 12 子查询并集里**消失**的房源 → 标 `is_active=0`（已售/下架）。
- **防误标**：连续 `delist_consecutive_runs = 2` 轮不在结果并集才标；回到结果里的房源 `absent_runs` 复位 0。
- 新增 `properties.absent_runs` 列（`store.mark_delisted` 幂等 `ALTER TABLE ... ADD COLUMN`）。
- 仅 **live 模式**执行（demo 不标）。
- 不做的代价（用户已选做）：不做则库里慢慢堆死房源，`在线/本机在架/累计` 口径虚高。

## 8. PDF 触发即算（user 拍板）
- 详情页只要 `pdf_worker.submit(no, pdf_url, ...)` **触发了下载动作**就继续，**不校验是否真落盘**。

## 10. 风险与防护（实现时已内置）
| 风险 | 防护 |
|---|---|
| 行内点詳細 解析失败写脏 | `_fetch_detail_inline` 任何异常返回 None，详情保持空，下轮重试；绝不把列表页当详情页解析 |
| 行内已 ingest 又走 sink.add 重复落库 | 成功行打 `_inline_done`，跳过 `sink.add`（list-only 本就会保留已有 detail_json，双写也无害，仍显式跳过） |
| 下架误标（单次漏抓） | 连续 2 轮不在才标；`absent_runs` 复位机制 |
| >500 覆盖不全 | REINS 硬上限 500 + 12 子查询各 <500，覆盖完整；超出需拆条件（本期不做，用户拍板接受 500 封顶） |
| 会话过期中断整轮 | 沿用 v1.4.x `SessionExpired` 统一重登/停机；行内点击的 `SessionExpired` 原样上抛 |

## 13. v1.5.1 — 勇哥 16:32 反馈「一直在跑、空不下来，他在干嘛？」的两个真 BUG

### 13.1 用户报的现象（原文摘录）
- 「看到这两点，为什么一直在跑？非常占时间！他一直空不下来，他在干嘛？」
- 日志（15:55–16:01）：`—— v1.4.0 阶段2：补详情 + PDF（待处理 375 条）——` 之后，
  **每 ~5 秒**一行「`· 30014xxxxxx 无详情直链，本轮跳过（下轮仍会补，因为详情还是空的）`」，几百行不停。
- 「感觉在整体应用上有BUG」

### 13.2 根因（两条，都是"没干活却照睡"）—— 已用库/日志坐实
查 `runs` 表：run49（13:52→14:21）/ run50（14:47→15:16）/ run51（15:52→16:17）三轮
**`fetched` 全为 0**、耗时 24~28 分钟 —— 整轮几乎没做任何实际抓取，却跑足半小时。

| # | 位置 | 旧行为 | 后果 |
|---|---|---|---|
| ① | 阶段2 循环尾 `time.sleep(delay)` | **不判断本条干没干活**，一律睡 | 375 条「无直链跳过」× ~4.6s ≈ **28.5 分钟纯空转** |
| ② | 阶段1 行内点詳細（v1.5.0 新增） | 点击**失败**也照样睡 3s | 若选择器不匹配，几百条失败 × 3s ≈ 10~18 分钟隐形空转 |
| ③ | 日志 | 无直链逐条打印 | 375 行刷屏，盖住真正有用的信息 |

**设计原则（写进代码注释）**：拟人停顿的唯一目的是"别在 REINS 眼里像机器" ——
**没有向 REINS 发出任何请求的迭代，就没有停顿的必要**。

### 13.3 修法
| # | 改动 | 说明 |
|---|---|---|
| 1 | 阶段2 引入 `did_work` 标志 | 只有真的 `_fetch_detail`（有直链）/ 提交了 PDF 才睡；否则 `continue`（不停、不空转） |
| 2 | `_fetch_detail_inline` 返回 `(rec, touched)` | `touched` = 是否真点开了详情页；`touched=False`（点击就失败）→ 行内也不睡 |
| 3 | 时长上限判断移到 sleep 之前 | 已超预算直接 break，不再先睡一轮 |
| 4 | 无直链日志只打前 5 条 + 末尾汇总 | 375 行 → 6 行 |
| 5 | **子查询去重**：新增 `crawl.reuse_axis_result: true` | REINS 无「変更」筛选 ⇒ 两轴条件逐字节相同。保留 12 组的名义与日志，但重复轴**不再请求 REINS**：真跑 6 次，**REINS 负载与轮次时长各减半**，覆盖不变（每房型仍各查一次；新增/变更本就由本地 changes 引擎判定） |

### 13.4 实测收益（离线校验 `_diag_v150_final.py`）
```
1) 子查询展开：12 组（6 房型 × 新增/変更）
2) 去重结果：名义 12 ｜ 真正请求 REINS 6 ｜ 请求数下降 50%
3) 阶段2 空转：375 条无直链
     旧 = 每条睡 ~4.6s → 纯空转 28.5 分钟
     新 = 不发请求就不睡 → 0.0 分钟
4) 行内点詳細：touched=False 时不停
```

### 13.5 回退开关（万一判断有误）
- 若发现 REINS **确实**有独立的「変更」筛选（本项目的真机探针结论是**没有**）：
  `config.yaml → crawl.reuse_axis_result: false` → 立刻恢复真跑 12 次。
- 若要让停顿更"像人"：`crawl.detail_gap_seconds` / `delay_long_prob` 上调即可（与"是否空转"无关）。

### 13.6 ⚠ 本节结论的部分更正（2026-09-14 17:00 复核，详见 §14）
- 13.3 第 5 条写的"REINS 无「変更」筛选"**是错的**。REINS 检索页有「登録年月日 / 変更年月日」
  两排日期筛选（各含"当日"）。两轴结果一样是因为**代码没去设筛选**，不是没有这个条件。
- 但"重复轴不请求"的**减半收益仍然成立**（只要两轴都是全期間，条件就相同）；
  勇哥 17:00 拍板要**真跑满 12 次** → `reuse_axis_result` 已改回 `false`。

### 13.7 与 v1.5.0 的关系
v1.5.0 修的是**"能不能补上详情"**（行内点詳細）与**"覆盖是否完整"**（12 子查询）；
v1.5.1 修的是**"不做无用功"**（不许没请求还睡、不许条件重复还重查）。
两个 BUG 都在 `core/crawler.py`，**必须重启 `start_mvp.bat` 才生效**（`.py` 不热重载）。

## 14. v1.5.2 — 真跑满 12 次 + 断点记录 / 15 秒「问人」窗口

### 14.1 勇哥追问「是 12 次检索吧？」→ 查证结果：**你说得对，我之前错了**
在已保存的 REINS 检索页快照（`data/probe/search_page.html` 等，离线复核，未连网未登录）里找到：

```
登録年月日 → [指定なし(全期間)] [３日以内] [１週間以内] [１ヶ月以内] [日付を指定] [前日] [当日]
変更年月日 → 同一排结构（value 0~6，"当日" = 6）
```

即 REINS **确实有**「新增（登録日）」「变更（変更日）」两个筛选轴 —— 勇哥的领域判断是对的。
v1.5.1 里我写"REINS 无独立変更筛选"是把**"我们没设筛选"**误当成**"REINS 没有筛选"**。已更正。

### 14.2 但有一个会出大事的坑：**不能只搜「当日」**
| 只跑当日新增/当日变更的后果 | 说明 |
|---|---|
| 存量房源刷不到 `last_seen_at` | 今天没动的房源根本不出现在结果里 |
| 连续 2 轮不在并集 → `mark_delisted` | 下架检测会认定它们"下架了" |
| 实测影响面 | 库内 **616 套中古マンション + 290 套中古戸建** 会被**全标 `is_active=0`** |

所以：**两轴都跑全期間**（当日筛选只在未来某房型真撞 500 上限时作为补充手段）。

## 15. v1.5.3 — 「画像 0 枚」是错的：画 / 図 / 所 三个标记 + 真实照片张数

### 15.1 勇哥反馈
> 「画（蓝色图标）：代表『画像/照片』… 図（绿色图标）：代表『图面/户型图』… 所（红色图标）：代表『所在图/周边地图』…」
> 「这现在显示的画像都是零枚，其实是不对的。」

### 15.2 根因（两处，都不是"没数据"）
| # | 旧做法 | 为什么错 |
|---|---|---|
| ① | 详情页用 `dp.locator("img").count()` 数照片 | REINS 详情页**整页 `<img>` 恒为 0**（图片走背景/懒加载）→ 永远写 0。库内 **1081 条 `image_count` 全是 0，从来没对过**（真机快照 `clickflow_detail.html` 里 `img` 出现 0 次，已坐实） |
| ② | 阶段1 只抓列表时没有 image_count 字段 | `pipeline` 无条件 `int(rec.get("image_count") or 0)` → 也写 0，于是"还没抓到详情"被显示成"没有照片" |

### 15.3 三个图标是什么（真机快照坐实，`data/probe/result_page.html`）
结果行右侧就是三个 `div.p-icon`，类名即语义：

| 类名 | 图标 | 含义 | 该快照 58 行中命中 |
|---|---|---|---|
| `p-icon-type-ga` | 画（蓝） | 有照片 / 画像 | **19 行** |
| `p-icon-type-zu` | 図（绿） | 有間取図 / 図面 | **56 行** |
| `p-icon-type-sho` | 所（红） | 有所在図 / 周辺地図 | **21 行** |

> 表头还有 1 组"图例"图标（说明这三个是什么），整页统计会各多 1 —— JS 只扫 `div.p-table-body-row`，不会误抓。
> 这三个标记**列表页就能读到、永远准确**，是"这套房有没有照片"的可靠答案；详情页给的才是"有几张"。

### 15.4 真实张数从哪读（详情页）
```
<h2>物件画像</h2>
<div class="card p-card"><div class="card-body p-card-body">
    <span>物件画像は登録されていません。</span>     ← 没有照片时就是这一句 → 确定为 0
    （有照片时这里是一堆图片元素）                    ← 数区块内的图片元素
</div></div>
<h2>物件図面</h2>  … ファイル名 + 「図面参照」按钮      ← 另证"有図面"
```
数不出来**就不写**（保持"未知"）—— 宁可显示未知，也不把未知说成 0。

### 15.5 口径变更：`image_count` = **-1 未知 / ≥0 已知张数**
- 老库（1081 条全是 0）一次性迁到 -1（只在"刚补出 `has_photo` 列"那一次触发，避免把真的 0 误改）。
- `pipeline`：详情给了才写；新行没给写 -1；**已有行不动**（不覆盖已知值）。
- 界面：查询行 / 详情页显示 **画·図·所 三个小徽章**（有=彩色、无=灰），张数只在已知时才显示；
  对比页 / 按天页 / Excel 同样把未知显示成「—」，不再显示 0 枚。
