- 状态：✅ 已根治（BUG-1 修繕積立金 → v1.7.3 值域闸门 + 迁列；2026-09-19 核实销号）

### R20 · 查询结果**排序功能**（勇哥 2026-09-16 01:11 提，PM 细化）

**目标**：查询结果能按"决策相关"的指标排序，帮同事快速挑出「便宜 / 大 / 单价低 / 刚降价」的房子。

**排序字段设计**（PM 定，默认正序 + 可切倒序）：

| # | 排序字段 | 方向 | 为什么要有 |
|---|---|---|---|
| 1 | **平台更新日**（默认） | 新 → 旧 | 同事最关心"今天有什么新的" |
| 2 | **房价** | 高→低 / 低→高 | 最基本诉求 |
| 3 | **面积**（専有/土地/建物） | 大→小 / 小→大 | 按用途自动选専有或土地 |
| 4 | **单价**（㎡単価，可切坪単価） | 低→高 / 高→低 | **跨户型比价唯一公平的口径** |
| 5 | **降价金额**（前価 − 现价） | 降得多 → 少 | 找"房东松口"的房 |
| 6 | **降价比例**（降幅 %） | 降得多 → 少 | 大额房降 100 万 ≠ 小额房降 100 万 |
| 7 | **降价发生日** | 近 → 远 | 刚降价的谈判窗口最大 |
| 8 | **建筑年份** | 新 → 旧 | 新房偏好 |
| 9 | **房源番号** | 升序 | 兜底稳定排序（避免同值乱跳） |
| — | 车站距离 / 关注度 | — | **暂不做**：库里没有可靠字段，宁缺毋滥 |

**交互设计**：

```
结果区顶部工具条：
  [排序：平台更新日 ▾]  [↓ 倒序]  [清除排序]        共 195 条 · 每页 50 条
                        ↑ 排序按钮        ↑ 取消按钮
```

- **排序按钮**：下拉选字段；右侧箭头按钮一键切正/倒序（不用回下拉里再选一次）。
- **取消按钮**：`清除排序` → 回到默认（平台更新日倒序），并清掉 URL 上的排序参数。
- **状态可见**：按钮上直接显示当前排序（如「单价 ↑」），不点开也知道现在按什么排。
- **可分享**：排序写进 URL（`?sort=unit_price_asc`），刷新/发给同事条件不丢。

**⚠ 技术要点（这条不写清一定会做错）**

1. **排序必须放服务端 SQL 做**。现在是「全库分页 + 每页 50 条」，如果在浏览器里排，只会排当前这一页 —— 页 1 排对了、页 2 就乱，同事会以为数据错了。
2. **空值统一排最后**（无价格 / 无面积 / 无前価的行），不能让它们跑到最前。
3. 排序表达式要在 SQL 里算，例如降价额 `COALESCE(previous_price,0) - COALESCE(price,0)`，不能依赖前端算。
4. 加**次级排序键**（番号）保证同值行顺序稳定，否则翻页会重复/漏。

**涉及文件**：`web/app.py`（`/api/query` 加 `sort` / `order`）、`core/store.py`（`search()` 增排序参数 + 白名单防注入）、`web/templates/search.html` + `web/static/app.js`（工具条 UI）。

状态：✅ 已实现（R20 排序 → v1.8.1 服务端 SQL；2026-09-19 核实销号）

### 2.5.1 三句话结论（没时间就看这三句）

1. **产品定位缺一句话**：这到底是"给勇哥自己用的采集工具"，还是"给大阪同业 + 港澳/大陆销售用的看房产品"？现在 PRD 里两套诉求混着写，导致"结果区要大"（销售要）和"更新开关要在首页"（勇哥要）互相打架。**先定这句话，后面 80% 的争论会自动消失。**
2. **数据可信度是生死线，必须先修 BUG-1**。修繕積立金取成坪単価（1,645,000 円 vs 实际 4,400 円）这种错，勇哥自己看一眼能反应过来；但**港澳销售看不出来**，会直接拿去给客户报价 —— 一次就砸招牌。所有排序、筛选、分析都建在数据上，数据错了，R20 排序做得再漂亮都是"把垃圾排整齐"。
3. **现在只有"查询"，没有"分析"**。勇哥的目标写的是"供他们查看实时情况，**并基于此做出房产分析**"。目前系统只做到前半句。真正让销售愿意每天打开的不是"能搜"，而是"**告诉我今天该盯哪几套**"。

---

### 2.5.2 最关键的一个发现：其实是两类用户，两套需求

现在 PRD 把它们当成一类人在写，这是所有纠结的根源。

| | **用户 A：大阪房产专业人士**（梓榮/J Property 侧） | **用户 B：港澳 / 大陆销售人员** |
|---|---|---|
| 他要什么 | 精准、完整、日文、可追溯（登録/変更日、専有面積、修繕積立金、管理費） | 快、看得懂、中文、**能直接转发给客户** |
| 他怎么用 | 一套一套点开细看，做专业判断 | 扫一眼列表，挑 3~5 套，发给客户 |
| 最在意 | **数据准不准、是不是最新的** | **这套值不值、能不能马上发给客户** |
| 最不能忍 | 字段取错、口径不清 | 全是日文看不懂、手机上排版乱、不知道数据是几点的 |
| 对应要做的事 | BUG-1、口径字典、平台日期可见 | 中文默认 + 语言记忆、手机适配、**数据新鲜度提示**、一键分享/导出 |

**PM 建议**：把 PRD 里每条需求都打上 `A / B / 两边` 的标签。以后吵架时看标签，不再靠感觉。
（例：R22 结果区最大化 = **B**；R2 物件番号検索 = **A**；BUG-1 = **两边，且 A 优先**。）

### 2.5.3 现有 PRD 稿件本身的 10 个问题（先修稿，再修产品）

| # | 问题 | 为什么是问题 | 怎么改 |

### 2.5.7 给 PM 小白的名词表（读这份稿不卡壳）

| 名词 | 人话 |
|---|---|
| 口径 | 同一个词到底按什么算。例："降价"是指比上次便宜，还是比房东最初挂牌便宜？定下来就是"口径" |
| 验收标准（AC） | "做完"的尺子。没有它，开发说做完了、你说没做完，谁也说不清 |
| 非功能需求 | 不是"做什么"，是"做得多好"：多快、几个人用、挂了怎么办 |
| 空状态 | 没查到东西时页面上显示什么。别让用户对着一片空白怀疑是不是坏了 |
| 埋点 | 悄悄记下用户点了什么，用来判断功能有没有人用 |
| 服务端排序 | 在数据库里排完再发给页面。否则只排了当前这一页，翻页就乱 |
| 存量清洗 | 老数据里的错值，要一次性改回来，不能只修"以后新增的" |

## 4. 约定与铁律（写代码前必看）

1. **日期口径** = REINS 平台登録/変更日（`reg_date_iso` / `chg_date_iso`），绝不用 `first_seen_at`。
2. **PDF 三处入口一律不上云**；`/download/*` 在对外模式直接 404。
3. **线上不改数据**：对外模式只有只读查询；写数据只能走带令牌的 `/api/ingest`。
4. **改页面后的上线流程**：改本地 → `python tools/sync_to_publish.py` → 本地冒烟 → 发布。
5. **数据更新不需要发布**：每轮抓完自动推；只有**改页面/改功能**才需要重新发布（会有 1~2 分钟空窗）。
