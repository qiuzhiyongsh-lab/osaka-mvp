## 0. 来源与原话还原（PM 据录音总结，未逐字编造）

录音核心是一段关于「指定日期下载」的过程描述，勇哥边想边说，要点还原如下（按时间轴）：

- **列表预取（第一步）**：正式检索后得出若干页（1 页或 10 页都算），**每一页的数据都要预取出来**，直接写进「房源查询」页 → 这时就能查出现在有多少页、多少条。
  但列表数据**没有详情页**，需第二步补齐。
- **详情补齐（第二步）**：后台在列表查询完后，**逐条点「详情」+「下载 PDF」**，把信息补齐。这是两步操作：先列表、后详情。
- **概览实时进度**：概览页「实施进度」里，平台日期同步之后显示「列表查询与下载」；对应某日期/某信息显示「**查询已完成 / 下载中**」。
  举例：**中古一户建的「登录登记」下载与完成**、**中古一户建的「变更」下载与完成**，分别写「下载多少条 / 变更多少条」。
- **四步状态机**（勇哥口述的步骤）：
  1. 列表查询（预取全部页，写查询页）；
  2. 列表查询去下载（逐条详情 + PDF）；
  3. 实时更新详情页多少条（如待下载 30 条、已下 2–3 条）→ **以平台数据为准**对比库：库里有了就不写、没有才写并更新；接着补没下的详情页和 PDF；
  4. 导出预收尾 → 整体结束。
- **房源查询页即时态**：下载「9 月 7 号」时，查询页应即时显示「**9 月 7 号，共 X 条，本页 50 条**」，而不是等全部下完才显示。
- **参照旧版**：勇哥明确说「之前版本里有这样一些功能（含『带下载详情』字样、实时进度）」，要求 PM 去查当时需求，不确定再问。

## 1. 背景与问题（PM 查证，非猜）

### 1.1 现象
勇哥在「查询本地房源」页查 **2026-09-07（口径：登录日或变更日）**，底部显示「**共 26 条 / 本页 26 条**」；而他手动在 REINS 平台查同条件得到 **100+ 条**。

### 1.2 库内实证（2026-09-16 只读查库，不影响运行进程）
| 種目组 | 登録轴 | 変更轴 | 合计（去重） |
|---|---|---|---|
| 中古戸建 | 14 | 5 | 14 |
| 新築戸建 | 4 | 4 | 8 |
| 新築マンション | 0 | 4 | 4 |
| 中古タウン | 1 | 0 | 1 |
| 中古マンション | 1 | 0 | 1 |
| **合计** | **20** | **13** | **28**（重叠 5） |

→ 库内 9/7 实际仅 **28 条**，分布极不均衡（一户建 g1 组 22 条，公寓 g2/g3 组仅 6 条）。**公寓组几乎没下下来。**

### 1.3 根因（两层）
1. **数据完整性 bug（已修，待重启）**：v1.6.4 在「下载结束汇总框」收尾时抛 `NameError`（`session_results`/`live_results` 未定义）→ 每轮打印汇总即崩溃；数据已落库但收尾 abort → **后续種目组被截断**（9/8 只跑到 g2 登録轴，77 vs 平台 194；9/7 公寓组同理缺失）。已于 **v1.6.5 修复**，待勇哥双击重启 8765 生效。
2. **进度不透明**：概览页虽有 v1.5.15 的「实时进度」面板，但它是**整体四阶段**视角，**不按「种目 × 登录/变更」两轴分别报数**；勇哥看不到「中古一户建登录轴下到哪、变更轴下到哪」，也无法确认「是不是又只下了部分组」。

> ⚠️ **本 PRD 不重复修 P0 bug**（那条已在 v1.6.5 单独修），但把「**列表全页预取保障**」立为需求（R1），从设计上防止「只落部分页/部分组」的假象复发。

## 2. 需求总览（一句话 + 四步法）

**一句话目标**：让「指定日期下载」做到——**列表全页预取、即时可见；下载过程按「种目 × 登录/变更」两轴透明报数；以平台数据为准、库有则不写、无则补齐详情与 PDF；收尾即整体结束。**

勇哥的四步法（产品视角的流水线，非时间轴）：

```
① 列表查询  → 翻完该(种目×轴)的所有页，全部列表行预取写库（查询页即时可查「共N条」）
② 下载详情  → 后台逐条点详情 + 下载 PDF，补齐全字段
③ 实时更新  → 以平台数据为准对比库：有则不写、无则写；更新「已下X/待补Y」；补完剩余详情+PDF
④ 导出收尾  → 整体结束，进度面板归零待命
```

## 3. 概念澄清（避免口径歧义）

| 概念 | 定义 | 说明 |
|---|---|---|
| **列表层（L1）** | 翻 REINS 列表页、解析列表字段（番号/地址/价格/種目/登録日/変更日） | 最快、不开详情页；决定「查询页共 N 条」的分母 |
| **详情层（L2）** | 对每条开详情页读全字段 → `detail_json` 落库 | 补齐列表没有的字段 |
| **文件层（L3）** | 详情读时并行下 PDF/図面 | 后台线程池，最大在途 2 |
| **登录轴 / 变更轴** | REINS 检索的两个日期筛选：登録年月日 / 変更年月日 | 同设一天 = **并集/OR**（实测 9/8：22∪47−1=68，与平台一致）；**绝不能是 AND** |
| **平台数据为准** | 列表层扫到的「結果 N 件」= 本轮分母 | 与库内已有量比对：库有跳过、库无写入 |

## 4. 详细需求（R1–R6）

### R1 · 列表全页预取保障（数据完整性地基）
- The system shall 在「指定日期下载」中，对**每一个（种目组 × 登录/变更轴）**组合，翻完 REINS 返回的**所有列表页**（受平台展示上限 500 条 / 10 页约束），将该组合下的**每一行列表数据**预取并写入本地库，再进入下一阶段。
- 过程中**禁止在中途（组间除外）截断**；若单轮因异常中断，重启后续跑时必须**补完未跑完的组/页**，而非只重跑已完成的组。
- 验收：跑完一轮后，库内 (reg_date_iso=日 OR chg_date_iso=日) 各組数量应与平台「結果 N 件」逐轴对齐（差≤0 为漏采、=0 为一致）。

### R2 · 房源查询页即时累计/本页态
- The system shall 在「房源查询」页，对「正在下载的日期」显示常驻一行：**「正在下载 {日期} · 累计 {Y} 条 · 本页 {Z} 条」**，随落库实时增长（每 20s 自动刷新，沿用 v1.2.2/v1.5.15）。
- 边抓边落库（`flush_every=1`）已具备 → 本项主要是**确保查询页把「当前正在抓的日期 + 累计 + 本页」作为显式信息呈现**（勇哥录音 04:22–05:13 明确要的）。
- `online_total=0`（无平台数据）时显示「—」，不画假 100%。

### R3 · 概览实时进度面板：按「种目 × 登录/变更」矩阵报数（本 PRD 核心新增）
- The system shall 在概览页「实时进度」面板，把进度从「整体四阶段」升级为 **「种目组 × 登录/变更轴」矩阵**，每组显示：
  - **查询已完成**：该组该轴列表预取条数（L1 分子，= 平台「結果 N 件」）；
  - **下载中**：详情已下 `fetched` / 待补 `need_detail`；
  - **变更轴单独计数**：登录轴、变更轴分别一行（勇哥原话「中古一户建登录登记下载与完成 / 中古一户建变更下载与完成，分别写下载多少条、变更多少条」）。
- 矩阵建议按 **6 小类 × 2 轴 = 12 行**（与爬虫真实检索一一对应），UI 默认折叠为「3 大组」，展开见 12 行明细（**具体折叠粒度见 §11 待确认 Q1**）。
- 复用现有 `runs.scanned/fetched/pdf_saved`、`online_stats.online_total`、`crawl_state.phase/need_detail/need_pdf`。

### R4 · 四步状态机（面板阶段标签）
- The system shall 进度面板按勇哥四步法显示阶段标签与步进：
  `① 列表查询中` → `② 详情+PDF下载中` → `③ 实时更新（已下X/待补Y）` → `④ 导出收尾·整体结束`。
- 无轮次在跑时整块隐藏（沿用 v1.5.15 静态覆盖层逻辑）。

### R5 · 以平台数据为准的增量写入
- Where 列表层扫到某番号，the system shall 与库内比对：**库已有同番号 → 不重复写列表/详情；库无 → 写入并更新**；缺详情页/PDF 的接着补下（沿用 v1.3.0「以已完成物为游标」范式，不存进度文件）。
- 部分完成解耦：详情已落库但 PDF 未下完 → 保留详情、继续补 PDF，不回滚。

### R6 · 确定性 / 续传
- If 中断发生，the system shall 至多丢失当前正在处理的 1 条（沿用 `flush_every=1` + PDF 原子落盘 `.part→os.replace`）。
- Where 重跑同条件，the system shall 跳过 `detail_json` 非空与磁盘已有 PDF 的条目，只补剩余，且进度面板精确显示剩余递减到 0。
