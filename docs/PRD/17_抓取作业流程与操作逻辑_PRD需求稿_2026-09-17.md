## 4. 标准作业流程 SOP（页面级 · 逐动作 · 含停留时长）

> 本节是勇哥点名要的（录音@26:13 "详细说明你的操作逻辑，在哪一个页面里面干什么事情停留多久，然后你后台里面做了些什么事情"）。

### 4.1 一图流（一次完整作业）

```
┌─ 阶段 0：进场 ────────────────────────────────────┐
│  浏览器 → 登录页 → 填账号 → 勾規約 → 登录 → 物件検索 │
│  停留：每步 ≤1 秒                                   │
└────────────────────────────────────────────────┘
                    ↓
┌─ 阶段 1：当日 12 次检索（勇哥定义的"一轮"）──────────┐
│  对 6 个種目 × 2 个日期轴，逐个：                    │
│    复位 → 種別 → 種目 → 所有権 → 大阪府/大阪市 → 日期 │
│    → 点検索 → 读条数 → 翻完所有页 → 存列表 → 返回    │
│  停留：每项 ≤1 秒；点検索后 ≤3 秒读条数（不再干等）   │
└────────────────────────────────────────────────┘
                    ↓
┌─ 阶段 2：详情 ＋ PDF（第二阶段）────────────────────┐
│  回到第 1 页 → 逐条点「詳細」→ 读全字段 → 存 PDF      │
│  → 返回列表 → 下一条                                 │
│  停留：详情 3~4 秒 ／ 间隔 3~5 秒 ／ 偶发停 10+ 秒     │
└────────────────────────────────────────────────┘
                    ↓
┌─ 阶段 3：收尾 ──────────────────────────────────┐
│  导出 Excel → 按天页 → 落快照 → 下架检测 → 对账       │
│  → 推送线上 → 完成通知 → 日志写清"跑完了"            │
│  ⚠ 现状：这一步必崩（P0）                            │
└────────────────────────────────────────────────┘
```

| 種目组 | 種別 | 種目 |
|---|---|---|
| 1 | 売一戸建 | 新築戸建 |
| 2 | 売一戸建 | 中古戸建 |

| 4 | 売マンション | 中古マンション |

### 5.2 序号规范（修"1/12 出现两次 + 1/6 倒退"）

**现状（证据：日志 07:50:49–08:15:30）**

```
序号 1/12（07:50:49）  序号 1/12（07:51:52）   ← 同一号两次
序号 2/12（07:52:53）  序号 2/12（07:53:07）
… 3/12 ×2   4/12 ×2   5/12 ×2   6/12 ×2
序号 1/6 （07:59:18）  ← 视觉倒退
序号 2/6 3/6 4/6 5/6 6/6
```

**根因**：12 次检索的序号 = **组号**（1~6）÷ 12，**未把日期轴计入**；主轮另用 `1/6` 编号，两套编号混在同一条日志流里。

**目标格式**（一次检索一行，序号唯一连续，阶段可见）：

```

[阶段A·当日12次] 4/12  売マンション×新築マンション / 登録年月日=2026-09-17 → 4件
…
[阶段A·当日12次] 12/12 売マンション×中古タウン / 変更年月日=2026-09-17 → 0件（无结果，立即返回）
[阶段B·详情+PDF] 待补 27 条 → 已补 27 条 / 跳过 0
[阶段C·全期間安全网] 1/6 …（如开启）
```

## 8. 数据完整性：对账口径（本次立为**一等公民**）

### 8.1 五个数 + 一个归因（缺一不可）

| 数 | 定义 | 来源 |
|---|---|---|
| ① 平台报告件数 | REINS「結果 N 件」的**总数**（非当前页范围） | `_read_total` + `_parse_total` |
| ② 我方扫描条数 | 实际翻页读到的列表行总数 | `sink.stats.scanned` |
| ③ 新增入库 | 首次入库 / 有变化的行数 | `fetched` |
| ④ 已存在未变 | 库里已有且无变化（**现状完全不可见**） | ③ 与 ② 之差 |
| ⑤ 跳过及原因 | 分三类：平台无図 / 已有 PDF / 已存在不重下 | 新增统计 |
| **归因** | ①−② 的差：区分「**平台 500 截断**」vs「**我方漏采**」 | 平台截断 = 该组报告数 ≥500 |

### 8.2 铁律

- **① 与 ② 的差 > 0 必须给出归因**，禁止只显示差额。
- **"未知"不得作为最终结果**：读不到条数时用列表行数兜底，并标注 `[兜底值]`。
- **对账数据先落库（`runs` 表）再打印**，保证崩溃也不丢。

## 10. 已发现缺陷与根因（**= 勇哥要的"问题的文档"**）

> 勇哥原话（录音@27:01）："历史上之前的这个数据里面的问题，也是需要由项目经理、产品经理、研发经理和测试一起告诉我，**怎么会出现这么多的问题**"。

### 10.1 🔴 P0 · 收尾必崩：`name 'groups' is not defined`

| 项 | 内容 |
|---|---|
| 现象 | 每轮结束打印 `[08:15:32] ✗ 本轮失败：name 'groups' is not defined` |
| **位置** | `core/crawler.py:602` — `"種目组：%d 组…" % len(groups)` |
| **根因** | `groups` 是 **`_live_items()`（1071 行起）的局部变量**（1121 行赋值），而 602 行位于 **`run_round()`（470–666 行）** 内 → 该作用域**从未定义** `groups` |
| 触发条件 | **每轮必崩**（602 行不被任何 mode/trial 条件包裹；demo/live/试跑全中招） |
| **连锁（更严重）** | 修掉 groups 后 **607 行 `run_online_total` 同样未定义**（1162 行才赋值）→ 二次崩溃；且 demo 模式下 `sink` 为 None → `sink.stats` 先抛 `AttributeError` |
| **业务影响（已用库证坐实）** | ① `finish_run(...,"ok")` 已写（595 行），但外层 `except`（661 行）**再次 `finish_run` 把 scanned/fetched 全覆成 0** → `runs` 表 run 88 = `status=error, scanned=0`，而实际扫描 1439 条、落库 53 条；<br>② **609 行后自动推送线上整段跳过** → `publish.mode=auto` 形同虚设，**线上数据停止更新**；<br>③ 完成通知不发；<br>④ 汇总框不打印 |
| **库证** | 只读查库：`runs` 最近 6 轮中 run 88（09-17 07:49 manual）与 run 86（09-16 19:31）均为 `error / 0 / 0 / 0 / 0` |
| **修法（RD 建议，非仅补一个变量）** | 让 `_live_items` 把 `groups` 与 `run_online_total` **作为返回值带回**；`run_round` 用已有变量替换：`online_total`（494 行）替代 `run_online_total`，`st`（517–532 行）替代 `sink.stats`（demo 下 sink=None）；**同时禁止异常兜底覆盖已有计数** |

### 10.2 🔴 同类问题**第三次复发**（根因模式）

| 版本 | 缺陷 | 处置 |
|---|---|---|
| v1.6.4 | 收尾汇总引用未定义变量 `session_results` / `live_results` → 每轮崩溃 | v1.6.5 修（`live_results` 置空） |

**PMO 结论**：这不是"手滑"，是**结构性缺陷**——「收尾汇总块引用子函数内部变量」这一模式没有被任何机制拦住。

1. 汇总块**只使用 `run_round` 自己作用域的变量**，跨函数数据一律**显式返回**；

## 16. 下载完整性校验锁（勇哥核心诉求 · 新增硬门禁）

> 勇哥原话（2026-09-17 续作指令）："在多个页面都检查过、且每一个详情页都查看完之后，在退出之前，我需要加一道'锁'：将我现在线下获取的所有数据和线上的数据进行对比，确保之前的数据都已下载完成。我认为这是一个非常必要的步骤，这样就可以确保当次检索的内容完全下载下来了，这是我的核心目的。"

### 16.1 真问题

§8 已把"对账"立为一等公民（五个数 + 归因，先落库再打印）。但**对账只是"显示"** —— 程序在 §4.4 收尾时即便发现 ①−② 差集 > 0（平台 500 截断 / 某页漏翻），仍会标记本轮 `完成` 并推送。

勇哥要的是一道**退出前的强制校验 + 阻断**：只有当"线下已抓番号集合" 与 "线上平台报告总数" 的**差集 = 0**（或差集可归因于平台截断）时，才允许标记该次检索完成；否则**标记"不完整"并告警/阻断推送**，不允许静默当成成功。这是 §8 的"强制化"升级。

### 16.2 两情形（勇哥口述逐字）

| 情形 | 勇哥描述 | 程序行为 |
|---|---|---|
| (a) 从未下载过 | "如果我之前从来没有下载过，我会直接把每一个页面的详情都下载一遍" | 翻完所有页 → 逐条点詳細 → 落库；退出前跑锁 |
| (b) 已有部分 | "在多个页面检查完、每套详情看完后" | 增量 upsert；退出前跑锁，比对本次应得 vs 已得 |

### 16.3 锁的语义（定义）

```
退出某次检索(某组/某模式) 前：
  N_online  = _read_total() 报告件数（已含分页器页数 × 每页，非当前页范围）
  S_offline = 本次该次检索实际 upsert 的 property_no 集合（去重）
  Δ = N_online − |S_offline|
  若 Δ == 0                → 标记「完整」✅
  若 Δ > 0 且 归因=平台500截断 → 标记「完整(平台截断)」⚠，记录截断组
  若 Δ > 0 且 归因=我方漏采   → 标记「不完整」❌，阻断推送 + 告警，建议重跑该次
```

### 16.4 与 §8 对账的关系

| | §8 对账 | §16 校验锁 |
|---|---|---|
| 性质 | 显示 / 可观测（一等公民） | **强制执行 / 阻断**（硬门禁） |
| 时机 | 收尾打印 + 页面展示 | **退出该次检索之前** |
| 失败处理 | 标红展示 | 标「不完整」+ 阻断推送 + 告警 |

### 16.5 数据口径与落库

- `S_offline` 必须来自**本次该次检索**的 upsert 回写（crawler 已有 `fetched` 计数，需补充 property_no 集合采集；建议落 `crawl_state` 或 `runs` 明细，与 §17.4 的 `search_log` 复用）。
- `N_online` 取自 `_read_total`（§8 ①），**不得用兜底值当锁输入** —— 兜底（读不到条数）时锁直接判「不完整」而非假设完整。
- 新增字段：`lock_result` ∈ {complete, complete_truncated, incomplete}、 `lock_diff`、`lock_reason`（落在 `runs` / `search_log` 检索明细行）。

### 16.6 AC（验收）

| # | AC |
|---|---|
| L1 | 一次检索退出前 `lock_result` 必写（不许缺省"完成"） |
| L2 | 某次因平台 500 截断 → `lock_result=complete_truncated` 且 `lock_reason` 写明截断组 |
| L3 | 某次我方漏采（Δ>0 非截断）→ `lock_result=incomplete`，**不推送线上**、日志红色告警、建议重跑 |
| L4 | 真机一轮跑完，`runs`/`search_log` 中 12 次检索各有 lock 记录，可对账 |

### 16.7 涉及位置 / 风险（高风险变更）

- 涉及：`core/crawler.py` 退出逻辑（§4.4 收尾**前**插入锁）、`core/store.py`（lock 列 / `search_log`）、前端对账面板（§7.2 显示 lock 结果）。
- **风险**：触及"检索退出行为基线" → 触发 8 门禁③（真机端到端）+⑥（发布后健康检查）。**当前代理全端口关闭（见 §17.5 / `_diag_net_out.txt`），真机 e2e 不可做** → 锁的实现可写码，但**发布前必须等勇哥开启代理或排期真机验证**，否则卡门禁③。
