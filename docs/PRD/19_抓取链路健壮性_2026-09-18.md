## 1. 背景与目标

### 1.1 背景
2026-09-18 10:43 手动触发当日同步，日志显示：12 组只跑了 4 组，第 4 组（中古戸建/変更）因「所在地１」区块 `wait_for(timeout=8000)` 超时 → `raise RuntimeError` → **整轮中止**；同时每轮收尾的线上推送均报「✗ 上传失败：未知原因」，待上传行数从 677 涨到 758。

复盘发现三类**相互独立**的故障，分属不同代码路径，不能混为一谈：

| 故障 | 代码位置（修复前） | 触发条件 | 后果 |
|---|---|---|---|
| ① 直录超时杀整轮 | `core/crawler.py` `_apply_manual_conditions` 直录分支 | `use_saved_condition:false` 走直录，REINS 慢渲染时本地区块 8s 未现 | 1 个组瞬断 → 全天 12 组同步作废 |
| ② 推送静默失败 | `core/publisher.py` `post_rows` 早返回用单数 `error` 键，`publish()` 读复数 `errors` 键 | `publish.endpoint` 从配置丢失（为空） | 推送根本没发出，却显示"未知原因"，线上长期旧数据 |
| ③ 结果区 45s 漏抓（D4） | `core/crawler.py` `_read_total` 默认 `timeout_s=45.0` | 检索结果区渲染慢（タウン 类响应尤其慢） | 该组记"未知"→ 0 条，慢种类当日漏抓 |

### 1.2 目标
1. 把三类故障根因与修复固化进需求池，杜绝「静默失败 / 一错全崩」。
2. 建立可验证的健壮性标准（超时重试、失败透明、慢组容错）。
3. 承接 PRD-17（数据完整性）、PRD-18（会议需求，原缺抓取健壮性）的盲区。

## 2. 待执行需求（R1–R3）

> 编号沿用「每文档独立编号」惯例；跨文档引用写「doc#R#」。每条含 EARS 表述与验收标准。

### R1 · 抓取链路健壮性：地区直录超时 + 重试 + 不杀整轮
- **优先级**：P0 ｜ **状态**：✅ 已交付 v1.9.2 + 真机验证（2026-09-18 11:40 轮）
- **EARS**：
  - *WHEN* 地区直录区块（所在地１）在 25s 内未渲染可见，
    *THE SYSTEM* 应先 `page.goto` 重进検索条件入力页并重展面板，**重试最多 3 次（含首次）**。
  - *IF* 3 次重试后仍失败，
    *THEN* 系统**仅跳过当前组**并记「⚠ 跳过本组」，继续其余组，而**不得中止整轮**。
- **验收标准**：
  1. `core/version.py` ≥ 1.9.2；`core/crawler.py` 存在 `_apply_geo_manual_retry`（25s + 重进重试）与专用异常 `_GeoFailed`。
  2. 4 处调用方（`sync_today_dates` / `run_round` / `run_round_options`×2）均 `except _GeoFailed: 跳过该组 + continue`。
  3. 真机：当日同步 12/12 组全部跑完、`server.log` 出现 0 次「整轮中止」、0 次「跳过本组」（REINS 够快时）；即便瞬断也只跳该组。
- **实测证据**：2026-09-18 11:40 轮 6 次「已直录 地区基线（第 1 次成功）」、0 次重试失败、0 次整轮中止、搜集 395/更新 314/新建 81。

### R2 · 推送失败诊断透明化（消除"未知原因"）
- **优先级**：P0 ｜ **状态**：✅ 已交付 v1.9.3 + 真机验证（2026-09-18 12:25 推 758 行成功）
- **EARS**：
  - *WHEN* 线上推送返回失败（endpoint 空 / 令牌错 401 / 网络超时 / 404），
    *THE SYSTEM* 应把**具体原因**写入日志与 `publish_state.last_error`，**不得**吞成"未知原因"。
- **根因（精确）**：用户问"令牌过期还是网络"——**都不是**。是 `publish.endpoint` 从配置丢失（运行时为空），推送根本没发出；且 `post_rows` 早返回用单数 `error` 键、调用方 `publish()` 读复数 `errors` 键，键名不匹配把真实原因"没有配置线上地址"吞成"未知原因"。
- **验收标准**：
  1. `core/publisher.py` 早返回与 `publish()` 调用方统一用 `errors` 键（复数）；`publish()` 兜底读 `error` 键防止任何来源再用单数键。
  2. `config.local.yaml` 的 `publish.endpoint` 已恢复为线上地址；`GET /api/publish/status` 运行态 `endpoint` 非空。
  3. 真机：`POST /api/publish` 增量推送 `ok=true`、`sent==upserted`（758/758）、`errors=[]`。
- **实测证据**：2026-09-18 12:25:49 `ok=true sent=758 upserted=758 total=758 errors=[] url=https://osaka-house-v2.app.workbuddy.host/api/ingest`。

### R3 · 检索结果区超时容错（D4）—— ❌ 假设被证伪，降级重诊
- **优先级**：P1 ｜ **状态**：❌ 复验失败（2026-09-18 12:53 轮）；根因误判，降级为 R4
- **原假设（已推翻）**：把 `_read_total` 默认超时从 45s 抬到 60–90s，可解决「慢组漏抓」。
- **实测证伪（12:53 真机轮）**：タウン 类 4 组（组 9–12 = 新築/中古 × 登録/変更）在 **78–90s 超时上界**仍 0 条；并非"还没等到"，而是结果条数选择器 `config.yaml:129` `result_total: div.text-dark.ml-3` **全 6 種目共用、仅适配非タウン 结果页 DOM**；タウン 结果页结构不同 → 选择器永不命中 → 等到上界才记"未知" → 0 条。
  - 结论：超时只是**表象**，真正卡住的是**选择器不匹配**；单纯抬超时治标不治本（仍 0 条，只是多等几十秒）。
- **已交付代码（保留，无害）**：`_read_total` 超时 45s → 60–90s（`core/crawler.py` v1.9.3，已编译通过），仅减少"快组白等"，不解决タウン 漏抓。
- **验收标准（原）**：❌ 未达成——タウン 4 组仍全 0 条。转 **R4**。

### R4 · タウン 结果页 `result_total` 选择器重诊（承接 R3 真因）
- **优先级**：P0 ｜ **状态**：⏳ 待勇哥真机取证（截タウン 结果页 DOM / F12 存 HTML）；**v1.9.4 超时止血已落地（2026-09-18 14:25），待真机复验**
- **根因（精确）**：`config.yaml:129` `result_total: div.text-dark.ml-3` 为 6 種目共用选择器，仅匹配非タウン 结果页的「件数」元素；タウン 结果页该元素 class 不同，导致 `_read_total` 定位失败、整组 0 条。
- **EARS**：
  - *WHEN* 检索结果条数区域在 60s 内未出现（或 `result_total` 选择器定位失败），
    *THEN* 系统应**回退稳健件数提取策略**（如：取结果列表行数，或解析分页「1 / N 件」文案），而**不得**记"未知" → 0 条。
  - *IF* 某種目（如タウン）结果页 DOM 与非タウン 不同，
    *THE SYSTEM* 应允许**按種目覆盖 `result_total` 选择器**，而非共用一条。
- **验收标准**：
  1. `config.yaml` 支持種目级 `result_total` 覆盖（或 `core/crawler.py` 内建兜底：取「结果列表行数 / 分页文案件数」中可信者）。
  2. 真机：当日同步タウン 4 组（组 9–12）均返回 >0 条、且不卡 60–90s 上界；`server.log` 无「第 N 组 结果区超时」类警告。
  3. 引入新 locator / 选择器 → 触发门禁②（真实 DOM locator）④（count==1 失败 raise）③（真机 e2e 回读条数）。
- **取证要求（勇哥）**：8765 真机 + 代理 7890 开 + REINS 登录态下，跑一轮或手动进タウン 结果页，**F12 复制结果区 DOM 或整页存 HTML** 贴给我，定正确选择器 / 兜底逻辑后再改代码、双击重启 8765 验证。

- **v1.9.4 止血（已落地 · 2026-09-18 14:25，待真机复验）**：不改选择器、不猜日文文案，先止血超时浪费 + 加行数兜底（`core/crawler.py` `_read_total`）：
  - 默认上限 60–90s → **18s**（实测戸建/マンション 计数区 <2s 即出；タウン 旧 65–85s 超时是在追 phantom，纯浪费 ~60s×4/轮）。
  - 计数区缺失时**行数兜底**：`result_rows`（div.p-table-body-row）首頁行数 >0 → 以「N件（首頁行数・総数不明）」估分母（不漏抓，翻页循环仍抓全行）；=0 → 记「未知」但不再久等，日志显式标注「疑0件/タウン構造相違，R4待真機」。
  - 效果（mock 单测已证）：A 计数区正常即时返回（戸建/マンション 无感）；B 有表无计数区→行数兜底；C 无表→快速未知；D 超时上限钉死 ≪ 旧 60–90s。
  - **仍待真机复验**（门禁③）：勇哥双击重启 8765 跑一轮，确认タウン 4 组从 ~75s/组 降到 ~18s/组、且不再刷「未知」；若タウン 真有结果而 `div.p-table-body-row` 不中（结构相違），本兜底仍 0 条 → 届时仍需真机 DOM 定正确行选择器（触发门禁②④）。

## 5. 总监反向挑战（门禁⑦）

- **挑战 1**："endpoint 为什么会丢？是配置清理误删还是同步脚本覆盖？"
  → 核实：`sync_to_publish.py` 的 `_sanitize` 剔除 `token` 类键但**保留** `endpoint`（不在 SECRET_KEYS）。`config.yaml` 模板 `endpoint:''`，真值本应在 `config.local.yaml`。复盘为某次配置整理时 `config.local.yaml` 的 `publish.endpoint` 行被漏写，运行态读取为空。**修复 = 补回该行**，非代码缺陷。
- **挑战 2**："D4 拉到 90s 会不会让慢网时一轮同步拖到几十分钟？"
  → 仅**慢组**走 60–90s 随机；快组即时返回。最坏 12 组全慢 ≈ 12×90s ≈ 18 分钟，仍在维护窗口（07:00–23:00）内，可接受。后续如需可改为「按種目差异阈值」。
- **挑战 3**："推送成功但线上页面为什么还是旧？"
  → 区分：**数据**走 `/api/ingest`（已推 758 行，**线上数据已新**）；**代码版本号**走「发布为应用」部署。两者独立。本次发布仅对齐代码版本号，数据早已到位。
