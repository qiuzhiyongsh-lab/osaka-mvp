## 1. 背景与目标

### 1.1 背景
2026-09-18 10:43 手动触发当日同步，日志显示：12 组只跑了 4 组，第 4 组（中古戸建/変更）因「所在地１」区块 `wait_for(timeout=8000)` 超时 → `raise RuntimeError` → **整轮中止**；同时每轮收尾的线上推送均报「✗ 上传失败：未知原因」，待上传行数从 677 涨到 758。

复盘发现三类**相互独立**的故障，分属不同代码路径，不能混为一谈：

| 故障 | 代码位置（修复前） | 触发条件 | 后果 |
|---|---|---|---|
| ① 直录超时杀整轮 | `core/crawler.py` `_apply_manual_conditions` 直录分支 | `use_saved_condition:false` 走直录，REINS 慢渲染时本地区块 8s 未现 | 1 个组瞬断 → 全天 12 组同步作废 |
| ② 推送静默失败 | `core/publisher.py` `post_rows` 早返回用单数 `error` 键，`publish()` 读复数 `errors` 键 | `publish.endpoint` 从配置丢失（为空） | 推送根本没发出，却显示"未知原因"，线上长期旧数据 |
| ③ 结果区 45s 漏抓（D4） | `core/crawler.py` `_read_total` 默认 `timeout_s=45.0` | 检索结果区渲染慢（タウン 类响应尤其慢） | 该组记"未知"→ 0 条，慢种类当日漏抓 |

### 1.2 目标
1. 把三类故障根因与修复固化进需求池，杜绝「静默失败 / 一错全崩」。
2. 建立可验证的健壮性标准（超时重试、失败透明、慢组容错）。
3. 承接 PRD-17（数据完整性）、PRD-18（会议需求，原缺抓取健壮性）的盲区。

### R3 · 检索结果区超时容错（D4）—— ❌ 假设被证伪，降级重诊

## 5. 总监反向挑战（门禁⑦）

- **挑战 1**："endpoint 为什么会丢？是配置清理误删还是同步脚本覆盖？"
  → 核实：`sync_to_publish.py` 的 `_sanitize` 剔除 `token` 类键但**保留** `endpoint`（不在 SECRET_KEYS）。`config.yaml` 模板 `endpoint:''`，真值本应在 `config.local.yaml`。复盘为某次配置整理时 `config.local.yaml` 的 `publish.endpoint` 行被漏写，运行态读取为空。**修复 = 补回该行**，非代码缺陷。
- **挑战 2**："D4 拉到 90s 会不会让慢网时一轮同步拖到几十分钟？"
  → 仅**慢组**走 60–90s 随机；快组即时返回。最坏 12 组全慢 ≈ 12×90s ≈ 18 分钟，仍在维护窗口（07:00–23:00）内，可接受。后续如需可改为「按種目差异阈值」。
- **挑战 3**："推送成功但线上页面为什么还是旧？"
  → 区分：**数据**走 `/api/ingest`（已推 758 行，**线上数据已新**）；**代码版本号**走「发布为应用」部署。两者独立。本次发布仅对齐代码版本号，数据早已到位。
- **挑战 4（v1.9.5 新增）**："你凭什么说 0 条是『确実 0 件』、不是又一次『选择器没中』的漏抓？"
  → 三条**独立**证据链互证（非单点依赖，任缺其一都还能质疑）：
  1. **日志**（14:05–14:14 真机轮）：タウン 4 组均打出 `已选 物件種別１ = 売マンション` + `已选 物件種目１(行1) = 新築タウン / 中古タウン` → `select_option(label=)` **成功**，種目×種別配对与填表都没错，排除"选错种类导致 0 条"。
  2. **本地库**：`properties.property_subtype` 已有 中古タウン 18 套 / 新築タウン 2 套（在架 18/1，最近见到 2026-09-17 08:15）→ 证明 `result_rows`(div.p-table-body-row) 在タウン 页**本来命中**、链路通；且这 20 套 `absent_runs` 全为 0 → 未被误判下架。
  3. **真机 DOM**：勇哥贴的 0 件页结构既无计数区、也无结果表 → 一次性解释「等不到计数区」与「0 条」为何同现。
  → 三者齐备时，"0 件 = REINS 真没结果"已无其它合理解释。退一万步：若真有结果，v1.9.5 的 tab 見出し兜底（验收④）会让日志出「N件（タブ見出し）」，**不会**还落「未知」——所以复验只会出现两种可接受结局，"未知"被根除。
- **挑战 5（v1.9.5 新增）**："用『0件』判 0，会不会把『検索結果が500件を超えています』这种事前確認框误判成 0？"
  → 会，这是 v1.9.5 初版 mock 单测 **F 用例**抓到的真实坑：初版 `if "0件" in text` 会把「検索結果が**500件**を超えています」（**有 500+ 条**的事前確認框）误判成 0 件。修复：改用负向后顾正则 `(?<![\d,，０-９])[0０]\s*件` —— `0`/`０` 前一位若是数字或逗号（500件/30件/10件）则不匹配，只对孤立的「0件/０件/0 件」生效。mock 单测 F/F2/F3/F4 四用例（500件/30件/全角０件/"0 件"带空格）全绿。→ 新 locator 不是"看见 0 就当 0 件"，而是带边界校验，门禁②仍满足。
