## 1. 一句话目标

管理员在**本地**管理员工账号，员工在**线上站**用自己的账号登录看房源；
账户数据由本地**单向同步**到线上（UPSERT，只带哈希不带明文）。

---

## 2. 线上 vs 线下职责（本次重构核心）

| 能力 | 线下（本地 8765 · 勇哥） | 线上（osaka-house-v2 · 员工） |
|---|---|---|
| 创建员工账号（用户名 + 账号名称） | ✅ **唯一入口** | ❌ 不提供 |
| 生成一次性随机码 | ✅ | ❌ |
| 改角色 / 禁用 / 解禁 / 重置随机码 | ✅ | ❌ |
| 账户数据同步上云 | ✅ `sync_to_publish.py` | 被动接收 |
| 登录（用户名 + 密码） | ✅ | ✅ |
| **首次登录设置自己的密码** | — | ✅ **强制** |
| 日常改自己的密码 | ✅ | ✅ |
| 退出登录 | ✅ | ✅ |
| 看房源 / 对比 / 收藏 | ✅ | ✅ |
| 管理员看员工列表 / 审计日志 | ✅ | ❌ |
| 抓取 / 调度 / 发布 / 番号検索设置 | ✅ | ❌（PUBLIC 站本就受限） |

> **铁律**：线上站**不提供**任何「创建账号 / 改他人密码」的能力，它只认本地同步过来的账户。
> 这样即使线上被攻破，攻击者也拿不到"批量造号"的能力。

## 3. 账户生命周期（主流程 · 勇哥明确）

```
① 线下创建    管理员在本地「员工管理」填：用户名 + 账号名称（显示名）+ 角色
② 生成随机码  系统生成 12 位一次性随机码（大小写 + 数字，剔除 0/O/1/l/I 等易混字符）
③ 线下分发    管理员把「用户名 + 随机码」经微信 / 口头给员工
               ⚠ 随机码不进任何日志、不进 git、不进记忆文件
④ 员工登录    员工在线上站 /login 用「用户名 + 随机码」登录
⑤ 强制改密    cleared=0 → **强制弹出设置密码页**，员工自己设新密码（8–20 位，字母+数字）
⑥ 正常使用    改密后 cleared=1，进入系统看房源
⑦ 后续管理    忘密码 → 管理员线下「重置随机码」重走 ③④⑤；离职 → 线下「禁用」
```

关键状态字段 `cleared`：**0 = 待改密（初始随机码）／ 1 = 已激活**

## 5. 登录与会话（已拍板 Q1–Q5，沿用）

- 凭证：**仅用户名 + 密码**（不采集手机号）
- 密码强度：8–20 位，且同时含字母与数字
- 登录失败 5 次 → 锁 15 分钟
- 会话闲置超时：30 分钟
- 审计日志保留：90 天
- 密码存储：werkzeug `pbkdf2:sha256`（≈26 万次迭代，强度等同 bcrypt，零原生编译依赖）

---

## 6. 同步机制（线下 → 线上，单向）

- 载体：`data/accounts.seed.json`，**只含 pbkdf2 哈希，绝不含明文**
- 时机：`tools/sync_to_publish.py` 的 **③b** 步骤
- 策略 **UPSERT**（勇哥拍板）：
  | 情况 | 处理 |
  |---|---|
  | 线上没有该账户 | 插入（带初始随机码哈希） |
  | 线上已有 | 同步 **角色 / 账号名称 / 禁用态** |
  | 该账户**已改过密码**（`cleared=1`） | **绝不覆盖哈希** |
  | 仍是初始随机码（`cleared=0`） | 跟随种子重置（未激活账户） |
  | 管理员显式「重置随机码」 | 带 `force_reset` 下推覆盖 |
- **防锁死兜底**：线上启动后若账户表无可用账户 → 自动降级为开放态并打日志（绝不自锁）

> ⚠ 已知联动缺陷：见 §8 缺口 ① —— 若"强制改密"不落地，`cleared` 永远为 0，
> 上表第 3 行「不覆盖已改密码」就**永不生效**，每次同步都会把密码打回随机码。

## 11. 回归事故与修复：强制登录把「上传到线上」拦死（v1.9.19 · 2026-09-19 10:2x）

> 本节按**门禁⑧**要求补齐两字段：① 历史教训引用 ② 实现风险。

### 11.1 现象（勇哥导出启动日志实证）

- 06:35 起**每一轮**推送线上均失败，稳定报
  `HTTP 401: {"message":"未登录","status":"error"}`（间或 502 网关瞬时错误）。
- 线上站「本机库 3876 条 / 今天 0 条 / 最近有数据 2026-09-18」，
  而本地库已 **3942 行、当日新增 158 套**（reg 22 + chg 136）→ **下载正常、上传断了**。
- 兜底包 `site_data.json` 正常生成（775 行 / 1.36 MB）→ 失败点在「推」不在「备」。

### 11.2 根因（代码级）

`web/app.py` 的 `_access_guard`（v1.9.13 引入、v1.9.14 起 `auth_enabled=true` 生效）
把 **机器对机器**端点 `/api/ingest` 一并拦下：本机上传器只带 `X-Publish-Token`、
**没有任何浏览器账户会话**，于是被守卫以 `{"message":"未登录"}` 永久 401。

**定位抓手**：`api_ingest` 自己的失败文案是「令牌不对（401）」，而线上收到的是
「未登录」——两句不一样，说明**守卫先于业务校验**拦的，问题在鉴权层而非令牌层。
（另：本地 `publish.token` 与线上校验的 `publish.ingest_token` 实测同值
`sha8=2d7fd02b`，故**本次无需改任何凭据**。）

### 11.3 修复（v1.9.19）

1. `web/app.py` `_access_guard` 放行 `/api/ingest`：
   ```python
   if path == "/api/ingest":
       return None
   ```
   安全性：无令牌/错令牌仍被 `api_ingest` 401 拦下（等于多一层锁），
   且**页面不受影响**，仍照旧跳 `/login`。
2. `core/publisher.py` `post_rows` 令牌**键名兜底**：
   `pub.get("token") or pub.get("ingest_token")` —— 同一密钥历史上两个键名，
   发送读前者、线上只认后者，只改一个就会造成**静默 401**（最难查的一类）。

### 11.4 验证证据（门禁③ / ⑥）

以「线上工程本体 `app_local`」为被测对象（隔离库冒烟，防污染真实主库）：

| 用例 | 修复前 | 修复后 |
|---|---|---|
| ① `GET /` 未登录 | — | **302 → `/login?next=/`**（强制登录未被放开） |
| ② 无令牌 POST `/api/ingest` | — | **401「令牌不对（401）」**（守卫已放行，业务校验在拦） |
| ③ 错令牌 POST | — | 401「令牌不对（401）」 |
| ④ **正确令牌** POST | 🔴 **401「未登录」** | ✅ **200 `{ok:true, upserted:1}`** |
| ⑤ 正确令牌 + 伪造 pdf_path/pdf_url | — | 200，入库后 `pdf_path/pdf_url` 均为 `NULL`（PDF 不上云被守住） |

**发布后线上实测（门禁⑥）**：`POST /api/ingest` 无令牌 → `{"error":"令牌不对（401）"}`（
不再是「未登录」，证明豁免已 live）；带真令牌 → `HTTP 200 {"ok":true,"total":3965}`，
与本地库 **3965 == 3965** 完全对齐。

### 11.5 ① 历史教训引用

- **VULN-02（v1.9.0）**：「对外站唯一门锁」类令牌若随同步上云 = 把锁和钥匙一起挂出去
  → 故 `access_code` 永不随同步上云；`ingest_token` 是**设计例外**（线上靠它校验本机推送）。
- **v1.7.6 同步教训**：`site_data.json` 的生成**必须**走 `core.config.load()` 三层合并
  （`config.yaml` 模板 + `config.local.yaml` 真值），只读模板会拿到空值 → 线上 401 **静默失效**。
  本次同型：**失败信息不同（「未登录」vs「令牌不对」）是分层的唯一线索，别把两类 401 混为一谈。**
- **v1.5.19 设计原意**：`/api/ingest` 存在的意义就是「推数据**不用重新发布**」——
  凡是给这条通道新增鉴权，都必须先回答「上传器有没有会话」。

### 11.6 ② 实现风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 豁免被误扩面 | 若将来把 `/api/ingest/*` 之类前缀也放进豁免，可能连带放开别的写接口 | 当前用**精确相等** `== "/api/ingest"`，不是 `startswith` |
| 令牌双键名残留 | `publish.token` / `publish.ingest_token` 两个名字仍在；若将来只改一个就会静默 401 | 已在 `post_rows` 做兜底；**后续应统一为一个键名**（待排期） |
| 上传器仍无会话 | 该端点永远不参与账户体系，故**不能被「全员必须登录」覆盖** | 已固化本记录；凡动 `_access_guard` 白名单须回归本节用例 |
| 本地进程需重启? | 守卫在**线上**，本机是发送方且令牌未变 → **无需重启 8765** | 证据：v1.9.14 部署前推送本可成功，说明进程内令牌正确 |

### 11.7 顺带发现的工程隐患（非本次修复范围，登记待办）

- **`app_local/core/__init__.py` 缺失**：`sync_to_publish.py` 的 `copy_tree` 会跳过
  `_*.py`，把 `__init__.py` 一起吃掉 → 线上 `core/` 退化为 **namespace package**。
  线上单独部署时可用；但**本机同时存在 osaka-mvp 时会优先加载 osaka-mvp/core**，
  造成「以为在测线上那份、其实测的是本地那份」的假验证（本次冒烟就踩到，已加模块来源自证）。
- **`AGENTS`/冒烟脚本的隔离铁律**：`core/config.py` 的 `ROOT` 是**模块常量**
  （`Path(__file__).parent.parent`），`output_root("./data")` 永远解析到工程自己的 `data/`
  —— **`os.chdir()` 完全无效**。要隔离只能用 `OSAKA_DB` 环境变量指向临时库。
  （事故：一次冒烟把 2 条 `SMOKE_*` 假数据写进了真实主库，已按 `property_no LIKE 'SMOKE%'` 清除并复核为 0。）
- **设置页保存会重写 `config.yaml` 并抹掉全部注释**（`yaml.safe_dump` 的副作用）：
  本次 `checkpoint` 提交里 v1.9.9/v1.9.10 的选择器注释、PRD-19 §17 注释均被抹平。
  建议后续把「注释版模板」拆成只读资料，或保存时只改键值行。
