## 1. 一句话目标

管理员在**本地**管理员工账号，员工在**线上站**用自己的账号登录看房源；
账户数据由本地**单向同步**到线上（UPSERT，只带哈希不带明文）。

---

## 2. 线上 vs 线下职责（本次重构核心）

| 能力 | 线下（本地 8765 · 勇哥） | 线上（osaka-house-v2 · 员工） |
|---|---|---|
| 创建员工账号（用户名 + 账号名称） | ✅ **唯一入口** | ❌ 不提供 |
| 生成一次性随机码 | ✅ | ❌ |
| 改角色 / 禁用 / 解禁 / 重置随机码 | ✅ | ❌ |
| 账户数据同步上云 | ✅ `sync_to_publish.py` | 被动接收 |
| 登录（用户名 + 密码） | ✅ | ✅ |
| **首次登录设置自己的密码** | — | ✅ **强制** |
| 日常改自己的密码 | ✅ | ✅ |
| 退出登录 | ✅ | ✅ |
| 看房源 / 对比 / 收藏 | ✅ | ✅ |
| 管理员看员工列表 / 审计日志 | ✅ | ❌ |
| 抓取 / 调度 / 发布 / 番号検索设置 | ✅ | ❌（PUBLIC 站本就受限） |

> **铁律**：线上站**不提供**任何「创建账号 / 改他人密码」的能力，它只认本地同步过来的账户。
> 这样即使线上被攻破，攻击者也拿不到"批量造号"的能力。

## 3. 账户生命周期（主流程 · 勇哥明确）

```
① 线下创建    管理员在本地「员工管理」填：用户名 + 账号名称（显示名）+ 角色
② 生成随机码  系统生成 12 位一次性随机码（大小写 + 数字，剔除 0/O/1/l/I 等易混字符）
③ 线下分发    管理员把「用户名 + 随机码」经微信 / 口头给员工
               ⚠ 随机码不进任何日志、不进 git、不进记忆文件
④ 员工登录    员工在线上站 /login 用「用户名 + 随机码」登录
⑤ 强制改密    cleared=0 → **强制弹出设置密码页**，员工自己设新密码（8–20 位，字母+数字）
⑥ 正常使用    改密后 cleared=1，进入系统看房源
⑦ 后续管理    忘密码 → 管理员线下「重置随机码」重走 ③④⑤；离职 → 线下「禁用」
```

关键状态字段 `cleared`：**0 = 待改密（初始随机码）／ 1 = 已激活**

## 5. 登录与会话（已拍板 Q1–Q5，沿用）

- 凭证：**仅用户名 + 密码**（不采集手机号）
- 密码强度：8–20 位，且同时含字母与数字
- 登录失败 5 次 → 锁 15 分钟
- 会话闲置超时：30 分钟
- 审计日志保留：90 天
- 密码存储：werkzeug `pbkdf2:sha256`（≈26 万次迭代，强度等同 bcrypt，零原生编译依赖）

## 6. 同步机制（线下 → 线上，单向）

- 载体：`data/accounts.seed.json`，**只含 pbkdf2 哈希，绝不含明文**
- 时机：`tools/sync_to_publish.py` 的 **③b** 步骤
- 策略 **UPSERT**（勇哥拍板）：
  | 情况 | 处理 |
  |---|---|
  | 线上没有该账户 | 插入（带初始随机码哈希） |
  | 线上已有 | 同步 **角色 / 账号名称 / 禁用态** |
  | 该账户**已改过密码**（`cleared=1`） | **绝不覆盖哈希** |
  | 仍是初始随机码（`cleared=0`） | 跟随种子重置（未激活账户） |
  | 管理员显式「重置随机码」 | 带 `force_reset` 下推覆盖 |
- **防锁死兜底**：线上启动后若账户表无可用账户 → 自动降级为开放态并打日志（绝不自锁）

> ⚠ 已知联动缺陷：见 §8 缺口 ① —— 若"强制改密"不落地，`cleared` 永远为 0，
> 上表第 3 行「不覆盖已改密码」就**永不生效**，每次同步都会把密码打回随机码。
