## 0. 结论先行（三句话）

1. **你这次点的「② 正式下载」走的是一条完全独立的链路**（`/api/download/specified` → `run_round_options` → `_collect_from_results`），它**当轮就把「列表 + 逐行点詳細 + 详情全字段 + PDF」一次做完**，不依赖任何后备机制——所以它稳。
2. **它干的活，正是你 PRD 文稿里描述的那套逻辑**（逐页翻 → 逐行比对历史 → 无则当场抓、有则只刷列表字段）。代码与 PRD **基本一致**，只在两处口径上有偏差（见 §4）。
3. **概览页的「开始一轮抓取」在 v1.8.4 之后被降级了**：主轮默认关（`main_round_enabled=false`），它**不再走 `_collect_from_results`**，只做「当日日期同步（纯列表壳）」，详情/PDF 全部推给事后的「阶段B」三手兜底。**详情从「一等公民」变成了「二等公民」**——这才是它「总有这样那样的问题」的结构性根因。

## 4. 与 PRD 文稿的逐条对账（你要的第 ① 件事）

你记忆里 PRD 的核心逻辑（原话拆成 4 条）与代码实际行为对账：

| # | 你的 PRD 描述 | 代码实际（`_collect_from_results`） | 判定 |
|---|---|---|---|
| 1 | 「一页 200 件 → 以 50 件为单位查 5 次，把列表全部下载下来」 | REINS 平台**固定 50 件/页**（`page_size:50`），我方**逐页翻**（`max_pages:10`）。不是「分 50 件查 5 次」，而是「翻页取全」——**机制等价，都是把列表取全** | ✅ 一致（口径差异见下） |
| 2 | 「从第一页开始，逐页检查当前页数据是否与历史匹配」 | `for pg in range(1, max_pages+1)` → 每页 `_bulk_list_rows` → 逐行 `store.get_property(no)` 比对 | ✅ **完全一致** |
| 3 | 「① 没有历史数据 → 就下载」 | `_needs_detail(existing)`：库里没有 / `detail_json` 空 / 缺平台日期未核验 → **抓详情 + PDF** | ✅ 一致（且比 PRD 更细，多第 ③ 条） |
| 4 | 「② 已有历史数据 → 暂停下载」 | 日志「**已存在 xxx（仅刷新列表字段）**」= 跳过该条的详情，只更新列表字段 | ✅ 一致（措辞差异见下） |

**两处口径偏差（须更正 PRD 记忆）**：

- **偏差 A（200 vs 500）**：上限不是「200 件」，而是 **`max_pages:10 × 50 = 500 条`**（平台显示上限，也是截断点）。你记忆里的「200」更可能是 `max_items_per_run` 的旧值；现网值已是 `5000`（受 500 封顶实际约束）。
- **偏差 B（暂停 vs 跳过）**：不是「暂停下载」（整轮停住），而是「**跳过这一条的详情抓取**」——列表字段照刷、下一行照走。所以你看到的「已存在 xxx」是**逐条粒度**的，不是整轮暂停。

> **一句话**：你 PRD 描述的那套逻辑 = **设置页这条链路**。PRD 没有错，代码也基本照做了——**错的是「概览页那个按钮没走这条路」**。

## 5. 差异根因：为什么设置页那条稳，概览页那条总有毛病

### 5.1 一句话根因
> **两条链路对「详情抓取」的定位不同：设置页把详情当「主链的一等公民」（当轮做完）；概览页把详情当「事后的二等公民」（推给阶段B 兜底）。**

### 5.2 为什么概览页会变成这样（历史脉络）
1. v1.5.x：概览页主轮（`_live_items`）**本来也走 `_collect_from_results`**，即一级公民。
2. v1.8.4：因「只搜当日 + 保存条件残留」导致**误标 604 条下架**的历史事故，勇哥拍板**默认关掉全期間主轮**（`main_round_enabled:false`）——这是为「防误下架」付出的代价。
3. 关掉主轮 → 概览页一轮只剩「当日日期同步（列表壳）」。
4. v1.9.1：为补回「详情/PDF」，**解耦出阶段B**（`_backfill_details_pdfs`）——但它是**事后兜底**，不是主链。
5. 于是详情抓取**从一条路变成了三条后备路**，每条都有历史缺陷：

| 阶段B 的第 N 手 | 机制 | 现况 |
|---|---|---|
| 第 1 手（旧） | `goto detail_href` | ❌ 死：REINS「詳細」是 `<button>` 无 href → `detail_href` 全库恒空 → 候选 SQL 永 0 |
| 第 2 手（v1.9.6） | `_fetch_detail_by_no` 番号検索 | 🟡 待激活：需 `selectors.bukken_search_inputs/button`，**config.yaml 现为空** |
| 第 3 手（v1.9.6 补强） | `_backfill_via_inline`（按日期分组调 `run_round_options`，即**复用设置页那条已证可用的路**） | 🔴 曾崩：`sqlite3.Row` 无 `.get`（今日 16:28 实证）→ **v1.9.7 已修，待双击重启 8765 生效** |

### 5.3 为什么设置页那条天然稳
- **零前置依赖**：不碰 `detail_href`、不碰番号検索选择器——它用的就是**当前结果页的 DOM**（`_fetch_detail_inline` 行内点「詳細」，用的是早已配好的 `selectors.detail_button`）。
- **失败半径小**：某条详情点不开 → `log("✗(行内) … 下轮重试")` + `continue`，**其余 349 条照跑**。而阶段B 是「整体 try」，一崩就是 0 条。
- **单一职责链**：列表 → 详情 → PDF → 落库，一条直线，没有「事后补偿」这一层。
- **已被反复验证**：今日白天靠它补了 400 条；本轮 350 条 0 失败。

### 5.4 顺带解释「为什么设置页慢，但你觉得没问题」
慢是**设计如此**（拟人节奏防风控），不是故障：

| 节奏参数 | 值 | 位置 |
|---|---|---|
| 检索间隔 | 2–4 s（8% 概率 10–20 s） | `delay_range_seconds` / `delay_long_*` |
| **详情条间停顿** | **2–4 s** | `detail_gap_seconds: [2,4]` |
| **翻页停顿** | **8–20 s** | `list_page_pause_seconds: [8,20]`（旧版注释：50 行 ≈ 2~3 分钟/页，**预期成本**） |
| 组间停顿 | 10–20 s | `subquery_interval_seconds: [10,20]` |
| PDF | 后台并行，均 **2.9 s/件**（n=102） | 日志 `:2442` |

实测 6.5 s/条 → 350 条约 38 分钟。**换算**：若一天 500 条，全量约 55 分钟。这是「像人」的代价，与「有没有问题」无关。

## 6. 建议（按优先级，含代价）

### P0 · 立刻可用（零代码，今天就能定）
**把「每日全量详情补齐」固定走设置页「② 正式下载」**——它已证可用、零失败、逐条落库。
- 做法：日期勾「当天登录 + 当天更新」+ 指定日期 = 今天 + 勾 6 个種目 → 点 ②。
- 代价：约 6.5 s/条（今天 350 条约 38 分钟）。

### P1 · ✅ 已落地 v1.9.8（2026-09-18 17:50）
**让概览页的「当日日期同步」升级为「当日完整下载」**——在 `sync_today_dates` 的翻页循环里，每行用 `store.get_property` + `_needs_detail` 比对本地详情，缺则调 `_fetch_detail_inline`（与设置页同款行内点詳細）内联补详情+PDF；详情走 `pipeline.ingest`、PDF 走后台 `_PdfWorker`。详情回主链一等公民，阶段B 退化为安全网。
- 收益：详情重新成为一等公民，**阶段B 从「唯一依靠」降级为「漏网补丁」**；概览页与设置页行为统一（PRD-20 §5 根因闭环）。
- 用户原始口径逐条落实：①每一页都翻一次；②检查每页的每行；③每页与本地详情页比对一次（有则不再点、无则下载）；④单页全量 vs 本地日期内对比；⑤首页面下载与检查同步做（同循环完成）；⑥记好哪些需进详情页/下 PDF（即 `_needs_detail` 命中者）。
- 代价：概览页一轮从约 4 分钟 → 数小时（与设置页同速，约 4–6 s/条含拟人停顿）。**仍建议配套**：自动轮保持轻量（每 1–2 h 壳同步）、夜间或手动跑一次全量详情补齐（走设置页那条路），避免长耗时阻塞。
- 门禁③：勇哥双击重启 8765 吃 v1.9.8 → 跑一轮看 `server.log`「概览页日期同步内联补详情 N 条」+ 前端「详情待补」清零 → 通过即 commit + 发布（appId `wbapp_C65E82hYRMCjxjcwW2Ph1E`）。

### P2 · 兜底修正（已落地 v1.9.7，待重启验证）
阶段B 三手后备已修到「第 3 手可用」：**双击重启 8765 吃 v1.9.7** 后，概览页自动轮也能自愈（按 `backfill_cap:300` 条/轮、`backfill_max_minutes:20` 分钟渐进清积压）。
- 局限：每轮 300 条上限 → 积压多时要跑几轮；且仍是「事后补偿」，不如 P1 干净。

### P3 · 可选优化
- 番号検索选择器（`selectors.bukken_search_inputs/button`）：填了阶段B 走更轻量的「逐号」路径；不填也能跑（走第 3 手）。
