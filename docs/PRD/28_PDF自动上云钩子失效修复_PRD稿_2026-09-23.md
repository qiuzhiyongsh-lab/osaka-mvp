## 二、5WHY 根因链（每一层带证据）

1. **为什么线上没有 PDF？** → 该行 `pdf_url` 为空，线上详情页靠 `pdf_url` 渲染 PDF 区。
   *证据*：本地库 `SELECT pdf_url FROM properties WHERE property_no='100140844127'` → 空。
2. **为什么 `pdf_url` 为空？** → 这份 PDF 从未上传 COS（上传才会写回 `pdf_url`）。
   *证据*：COS 无该 key；`uploaded` 计数 61 未含它。
3. **为什么 v1.9.66 的「自动上云」没传？** → 钩子从未被调用。
   *证据*：`grep -c "PDF云·自动" data/logs/server.log` → **0**。
4. **为什么钩子没被调用？** → v1.9.66 把 `on_pdf_downloaded` 钩子**只挂在 `Store.set_pdf`** 上，而这条路径根本没调用 `set_pdf`。
   *证据*：全日志 `grep -c "PDF 已落盘"`（`set_pdf` 调用点的日志）→ **0**。
5. **那 `pdf_path` 是谁写的？** → **`core/pipeline.py:ingest()`**：它自己 `_save_pdf(rec, no, att_dir)` 落盘，再把 `pdf_path` 塞进 `rec` **整行 upsert**，**完全绕过 `set_pdf`**。
   *证据*：`core/pipeline.py:69-93`；日志 `✓ 300140844172 内联补详情`（19:16:24）走的正是 `pipeline.ingest`。

> **一句话根因**：钩子挂在了「次要写入路径」上，而真实主路径（`pipeline.ingest` 整行 upsert）绕过了它 —— **典型「改对了机制、挂错了位置」**。

---

## 三、修法（双保险）

### ① 快速通道：`pipeline.ingest` 补挂同一个钩子
`core/pipeline.py`：落 `pdf_path` 成功后调 `getattr(store, "on_pdf_downloaded")`（线上未注入 → 零开销）。
→ 数据一落库，30 秒内自动进上传队列。

### ② 兜底自愈：新增「欠账巡检」常驻线程（核心保障）
`core/pdf_cloud.py` 新增：
- `pending_nos()`：按「**库 + 盘**」查「`pdf_path` 非空 且 `pdf_url` 非 `http`」的番号；
- `sweep_pending()`：有欠账 → 复用 `start_upload`（日志/进度/回推全复用）；上传任务在跑时**自动让路**（不抢跑）；
- `_start_auto_sweep_loop()`：每 **10 分钟**扫一次；**启动 20 秒后先跑首检**（重启即补齐历史欠账）；
- 幂等守卫 `_SWEEP_STARTED`；日志前缀 `[PDF云·巡检]`。
`serve.py` + `web/app.py __main__`：本地（`not PUBLIC`）拉起。

### 为什么「巡检」比「钩子」更对
PDF 落库有**多条写入路径**：`pipeline.ingest`（主）/ `set_pdf`（后台 worker 回收）/ 手工补抓 / 未来新增路径。
钩子是「事件驱动」，**新增路径就会漏**；巡检是「状态驱动（库+盘为准）」，**天然覆盖所有路径**，还能自愈历史欠账与上传失败。

## 五、影响面 / 风险

- **仅本地生效**：线上 `OSAKA_PUBLIC=1` 不注入钩子、不启动巡检 → 线上行为零变化，**不需要发版**。
- **不烧钱**：只上传 PDF 文件到 COS + 回推 `pdf_url`，不触发任何 AI 调用（不进云端兜底）。
- **资源**：巡检 SQL 为单表全扫（约 4.8k 行，毫秒级）；无欠账时完全静默。
- **并发安全**：与手动上传任务互斥（有 running 任务则跳过本轮）。
- ⚠ **需勇哥重启本地 8765** 才生效（当前 running=1.9.66）。
