## 二、隔离契约（四条铁律，代码与注释双重固化）

| # | 铁律 | 落地位置 | 违反后果 |
|---|---|---|---|
| 1 | 路由前缀统一 `/api/emp/`，与 `/api/ingest`（财产数据）**彻底分离** | `web/employee_api.py::PREFIX` | 财产数据与员工业务数据互相污染（R-1） |
| 2 | 🚨 **绝不**把 `/api/emp/**` 加进 `PUBLIC_HIDDEN_APIS` | `web/app.py` 该列表内已写警示注释 | 线上全线 403，客户管理模块直接报废 |
| 3 | 两类端点两套鉴权，不许混用 | 见下表 | 击穿 W6 隔离 / 数据裸奔公网 |
| 4 | 所有查询**强制** `owner_username` 过滤；写操作校验 `owner == 当前登录用户` | 各接口 | 员工互看互改数据 |

### 鉴权分野
- **员工端** `/api/emp/{fav,tags,customers}/*` → 走 `_access_guard` 登录守卫，归属人 = `_current_user()['username']`。
- **机器端** 仅 `/api/emp/export` → 在 `_access_guard` 中**显式豁免**（本地 worker 没有也不该有浏览器会话），接口内部用 `_relay_token_ok()` 校验 `X-Publish-Token`（与 `/api/ingest`、`/api/ai/relay` 同款）。

> ⚠ 豁免**只给 export 这一个只读端点**。fav/tags/customers 的写接口一律不豁免——否则任何人都能改别人数据。

## 三、接口清单

### 员工端（需登录）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/emp/fav` | 我的收藏列表 |
| POST | `/api/emp/fav/toggle` | 加/取消收藏（`{property_no}`，幂等切换） |
| GET | `/api/emp/tags` | 我的标签列表 |
| POST | `/api/emp/tags` | 建标签（`{name,color?}`，同名幂等返 `dup`） |
| DELETE | `/api/emp/tags/<id>` | 删标签（同步解绑引用，避免孤儿数据） |
| POST | `/api/emp/tags/bind` | 房源⇄标签 绑定/解绑 |
| GET | `/api/emp/tags/of?property_no=` | 该房源上我打的标签 |
| GET | `/api/emp/customers` | 我的客户；管理员 `?scope=all` 看全部（**只读**） |
| POST | `/api/emp/customers` | 建档（`{name,phone?,note?}`，只写 `created_at`） |
| PATCH | `/api/emp/customers/<id>` | 改客户（**W6：仅归属本人，管理员 403**） |
| DELETE | `/api/emp/customers/<id>` | **软删**（R-5，仅归属本人） |
| POST | `/api/emp/customers/<id>/transfer` | 转移归属（**仅 admin**，T6 留痕） |
| POST | `/api/emp/customers/<id>/bind` | 客户⇄意向房源 |
| GET | `/api/emp/status` | 自检：登录态/库健康（QA 用，不暴露他人数据） |

### 机器端（X-Publish-Token）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/emp/export?since=&limit=` | 增量导出 T1–T6（留空 = 全量首拉），返回 `next_since` 作下轮水位线 |

## 四、数据模型变更（幂等迁移，绝不 DROP）

在 v1.9.68 的 T1–T6 六表基础上补两类列：

| 列 | 表 | 原因 |
|---|---|---|
| `updated_at` | favorites / tags / property_tags / customer_properties | 增量同步需统一水位线；改标签名/改备注这类更新若无此列，增量捕获不到 |
| `deleted` / `deleted_at` | customers | **R-5 缓解**：客户删除必须软删，保留对账轨迹 |

> ⚠ 迁移列**不加 `NOT NULL`/`DEFAULT`**：SQLite 的 `ALTER ADD COLUMN` 带 NOT NULL 必须有 DEFAULT，历史行会拿到默认值导致水位线错乱。旧行保持 `NULL`，查询用 `COALESCE(updated_at, created_at)` 兜底。

落点仍为独立库 `data/employee.db`（**不塞主库**——主库线上会被 `site_data.json` 按 stamp 重灌，员工数据混进去会被冲掉）。

## 六、历史教训引用（门禁⑧ ②）

本次设计直接继承了以下血案教训，均在代码注释中固化：

1. **🚨 v1.9.64「线程/钩子只放 `__main__` 永不启动」**
   → 本步路由注册与建表自检都挂在 **web/app.py 模块导入**处（非 `__main__`）：线上 `serve_public.py` 只 `create_app()`、本地 `serve.py` 只 `import web.app`，都不跑 `__main__`。

2. **🚨 v1.9.66「钩子挂在非主路径等于没挂」**（PDF 自动上云从未触发）
   → 鉴权不靠"某一处守卫"，而是**每个接口内部自己校验 owner**（W6）+ 机器端点自己校验令牌，纵深防御，避免"只挂一处被绕过"。

3. **🔴 v1.9.19「机器通道被登录守卫误拦 → 线上数据静默停更」**
   → `/api/emp/export` 必须在 `_access_guard` 显式豁免，否则本地 worker 拿不到数据；但豁免范围**严格限定**为该端点。

4. **R-4 线上 data 盘持久化、发版不重置**
   → 建表/加列全幂等（`IF NOT EXISTS` + `PRAGMA table_info` 判断后才 ALTER），禁 DROP/重建。

5. **「四反模式」（账号同步）**
   → 同步内核另起 `employee_data_sync`，不复用 `account_sync` 通道。
