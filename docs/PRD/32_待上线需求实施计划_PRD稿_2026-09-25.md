## 三、批次 1 需求详述（EARS 写法）

### 3.1 U5 / U6 一次性数据清洗

- **U5**：系统应在执行 `tools/clean_misaligned_repair_fund.py --apply` 前**先备份** `data/jproperty.db` 到 `.backups/`；
- 当执行清洗时，系统应只修正**列错位**（`repair_fund` 与 `unit_price_tsubo` 等值误置）的 1060 条，**不得删除任何房源行**；
- 若清洗影响行数 ≠ 预期，系统应**中止并回滚**（从备份恢复）。
- **U6**：系统应仅为 `reg_date_iso` 与 `chg_date_iso` **双空**的行补齐日期（实证当前 **389 条**，非旧记的 1192）；补齐来源 = 详情页重抓或平台日期回填；同样先备份、可回滚、只此一次。

> 📌 **实证纠正**：`detail_json` 空 = **336 条**（其中在架 `is_active=1` 仅 **33 条**），旧记"321"已过时。

### 3.2 G-1 PDF 下载失败重试

- 当 PDF 下载失败时，系统应**至少重试 2 次**（间隔取自 `crawl.delay_range_seconds`）；
- 若仍失败，系统应把该番号写入**失败台账**（新表或 `pdf_recrawl_queue`），并置标记，**不再静默放弃**；
- 台账应可由"欠账补抓"任务消费（见 3.3）。

### 3.3 欠账补抓

- 系统应支持按条件（如 `has_floorplan=1 且 pdf_path 为空`）扫描欠账并补抓；
- 实证当前该量级 = **1146 条**（`has_floorplan=1` 但无 PDF），远大于单条 `300140678627`；
- 补抓应在**平台工作时段（日本时间 07:00–23:00）**内进行，并限速。

### 3.4 G-3 下架房源终局跳过

- 当某番号连续 **2 轮**检索结果为 0 件时，系统应将其标记为**终局跳过**（`_SKIP`），后续轮次**不再发起检索**；
- 系统应在日志中区分「终局跳过」与「真失败」，不得把 0 件当失败计数。

### 3.5 §16 下载完整性校验锁

- 当一轮下载即将结束（退出前）时，系统应**强制校验**本轮应下项与实际落库项；
- 若存在缺口，系统应**阻断退出**并提示（或按勇哥选择：告警 + 写台账），不得静默结束。

### 3.6 §17⑧ 日志按次检索

- 系统应新建 `search_log` 表（实证：**当前不存在**），按「每次检索」记录：时间 / 条件 / 结果数 / 耗时 / 是否触限；
- 查询页或运维页应能按次检索该日志。

### 3.7 G-5 relay 回推失败提示

- 当 AI 接力回推线上失败时，前端**不得**显示「完成」；
- 系统应区分「本地生成成功」与「线上回推成功」两态，并把回推失败**明示**给操作者 + 写入 `publish_state.last_error`。

### 3.8 P-5 沿线/车站面板

- 系统应提供「全部线路」面板：支持**全选 / 取消全选 / 按关键字筛选**；
- 应包含 **なんば (S16)** 等实测站名（v1.9.53 遗留）；
- 该面板应在**种子灌库后重新学习**线路字典（`serve_public.py` 已 force=True，本地需同款）。

### 3.9 P-4 搜索页 selector 校准

- 系统应把「検索条件入力页 / 物件詳細页」的选择器**配置化**（走 `config.yaml`），不再硬编码；
- 未配置时应返回**明确提示**，而非静默失败（v1.9.x 已有此约束，需补齐两页的 outerHTML 取证）。

## 五、勇哥要求「说明」的机制（本节为说明，不含实现）

### 5.1 D1 结构性根因（现状）

`core/crawler.py:520` 用 `main_round_enabled` **一个开关**同时控制 ① 全期間主轮（数据主力+下架基线）② 阶段B 补详情。该开关当前为 `false`（v1.8.4 勇哥拍板关），于是**阶段B 补详情也被一起关掉** → 这就是"详情长期补不上"的真根因。
**解耦方案（待确认）**：新增独立开关 `crawl.stage_b_enabled`（默认 true），使阶段B 不受主轮开关影响；主轮维持 false 不动（符合 U3 决策）。

### 5.2 RB-1 500 条上限（方案与优劣）

- **现状**：REINS 单次检索上限 500 条；老房源被挤出窗口即取不到。已有规避＝拆细房型（12 子查询）。
- **方案 A（时间倒序 + 水位线增量）**：按更新时间倒序取，只取上次水位线之后的增量。**优**：不漏新/变更，请求少。**劣**：依赖平台排序稳定；历史老盘补不到。
- **方案 B（超限告警 + 自动细分）**：触及 500 即告警并按区/駅/价格段自动细分再查。**优**：覆盖全。**劣**：请求数倍增，风控风险上升。
- **建议**：先上 A（低风险），B 的"告警"先做（只告警不细分），细分留作开关 `crawl.auto_split_on_limit`（默认关）。

### 5.3 G-1 PDF 下载重试（机制）

当前 `core/crawler.py` 的 retry 仅覆盖**会话重登**（`_retry` 守卫，只重试一次）与**地域手动重试**（`_apply_geo_manual_retry`，max_attempts=3）；**PDF 下载本身失败即放弃、无重试、无台账** → 所以出现「図面有、8 天无 PDF」。
**拟做**：下载失败 → 重试 2 次 → 仍失败写台账 + 标记，交"欠账补抓"消费。

### 5.4 欠账补抓（机制）

条件扫描（`has_floorplan=1` 且 `pdf_path` 空）→ 生成补抓队列 → 在平台工作时段内限速重抓。实证量级 **1146 条**，需分批并限速（避免风控）。

### 5.5 detail_json 为空（机制）

实证：**336 条**（在架仅 33 条）。成因（旧记）＝列表页「詳細」为 `<button>` 而非直链，走不到详情。
**处理机制（待勇哥定）**：① 优先补这 33 条在架的（价值最高）② 已下架 303 条可不做 ③ 或全部走"欠账补抓"队列。

### 5.6 G-2 轮末报告口径

轮末「PDF 0 份」未把**内联补详情**路径（列表页行内点詳細补的 PDF）计入 → 报告与实际不符。**拟做**：统一口径，报告分列「主路径 / 内联补详情 / 补抓」三个来源。

### 5.7 G-5 relay 回推（机制）

v1.9.63 AI 接力：线上点「重新生成」→ `POST /api/ai/relay/request` → 本地 2s `claim` → `run_one(force=True, allow_cloud=False)` → `post_ai` 回推 → 前端轮询。
**问题**：回推失败时前端仍显示「完成」（前端只看本地生成结果）。**拟做**：前端区分两态；回推失败写 `publish_state.last_error` 并提示。

### 5.8 B⑰ 代理红线 / 真机 e2e（给勇哥的说明）

- **是什么**：Playwright 的 Edge 只认本机代理 `127.0.0.1:7890`；而 AI 侧的 Bash 沙箱**禁止访问公网**，所以凡需登录 REINS 的真机端到端验证（番号検索、上传定时器、周期重算）**我在沙箱里跑不了**。
- **为什么是"发布阻塞"**：门禁③（真机 e2e）无法由我完成，只能由勇哥在本机操作。
- **换方案的选项**：① 勇哥本机跑、我出检查清单（当前做法）② 增加"离线可验"的替代断言（不碰 REINS）③ 开放沙箱公网（平台限制）。
- **本次勇哥已定**：真机由**勇哥来做**，我出测试方式（见 §6.2）。

### 5.9 RB-2 会话自愈重登（评估）

勇哥条件：**若登录周期对平台与时间影响不大，就不做**。
- 影响面：重登会额外打 REINS 登录接口（风控敏感）+ 耗时。当前已有**会话失效时问人**（`crawler.py:707-724`，只重试一次）。
- **建议**：先评估"一轮内会话失效频率"；若低频（<1 次/轮）→ **不做**（影响不大），维持现有"问人"机制。
