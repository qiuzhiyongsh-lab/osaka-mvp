## 0. 一句话目标

把"搜索并下载信息"从**粗放的全量/按日重拉**升级为**以「平台是否在我上次成功拉取后更新」为锚点的增量判定**，并据此决定「详情是否重拉」「PDF 是否重下」「重拉结果如何升主」（📌 详情留历史、**PDF 只留最新一份**，见 D13），在「不漏新变更」与「不浪费 REINS 请求/带宽」之间取平衡。

---

## 1. 背景与问题起源

勇哥在 2026-10-01 提出一组关于"下载筛选"的直觉规律（见 §2 原文梳理），核心命题是：

> **价格/内容变了才值得重新拉；没变就不该浪费一次抓取。**

这个命题方向是对的，但落地前必须先厘清三个前提，否则会漏数据或踩坑：
1. **"我下载过" ≠ "它没再变过"**（REINS 平台侧会持续更新，我方不重拉就陈旧）。
2. **系统当前没有"我方拉取的是哪个平台版本"的锚点字段**，也没有 PDF 的版本/指纹记录——这俩是增量判定的地基，必须先补。
3. **PDF 与价格不是 100% 绑定关系**，"改价→PDF 必变"是强信号但非铁律，应以 PDF 自身指纹为准。

---

## 2. 勇哥原始规律（需求输入 · 原文梳理）

> 以下为勇哥原话的结构化转述，作为本 PRD 的需求输入；逐条质疑见 §4。

### 规律 1 · 历史已下载信息
- 若搜索到的信息已在历史记录中，**且我已经下载了它的 PDF 和详细内容** → 我的内容已经是最新的。
- 因此历史中已有的信息**可以不下载**；或者即使下载了，详情也只是存在某处**作为历史记录，不会去实际使用**。

### 规律 2 · 新增 / 更新信息
- 若下载的信息是在**我上次下载之后更新的** → 必须对信息做进一步更新。
- 因为它的信息可能比我现有的更新；里面内容**可能改变、也可能没改变**。
- 不管有没有改变，都**要把信息重新拉取下来一次**。

### 规律 3 · PDF 文件补充
- **历史上没有 PDF、现在有了** → 肯定必须下载。
- 历史上有 PDF、现在有过调整，分两种：
  - **(a) 调整后没有改价格** → 默认它的 PDF 是不变的。
  - **(b) 调整后改了价格** → 它的 PDF 文件一定会有改变，这个时候 PDF **一定是需要下载的**。

## 4. 对勇哥规律的逐条质疑与修正（核心）

> 标注 C1–C8 为"修正点"，最终拍板进 §9 决策记录 D 表。

### C1 · 规律 1「已下载 = 内容已最新」是错的（最关键的谬误）
- **证据**：`crawler.py:3868-3887` 专门加了 `backfill_refresh_stale_days` 来对抗"REINS 已降价本地没跟"——这本身就是"我方以为有数据、其实平台已变"的活证据。
- **谬误**：已下载只代表"过去某个时间点拉过一次"，不代表"之后平台没再变"。规律 1 漏掉了"下载后平台又更新"这个窗口。
- **修正**：把规律 1 与规律 2 合并为一条**增量判定**——"自上次成功拉取以来，平台侧 `chg_date_iso`/`reg_date_iso` **没变过**的，才可跳过；**变过的，必拉**。" 用平台日期做锚点，而非"历史有无"二分。

### C2 · 规律 1「只存历史、不升主」缺少"何时升主"规则
- **分析**：把重拉结果存为历史版本（类似 git 历史）的思路**本身合理**。但勇哥没定义：重拉后发现内容**确实变了**，主区还用老的，数据就是错的。
- **修正**：必须配套"升主规则"——重拉后做 diff，有**实质变化**（价格/地址/关键字段）就**升主 + 写历史版本**；无变化就仅更新时间戳、不消耗 PDF（除非 PDF 探测到新）。详见 §5 规则 C。
  > 📌 此处的"写历史版本"**仅指详情（detail）**，`property_history` / PRD-35 F5 时间轴要用。**PDF 不写历史**（D13 拍板，只留最新一份）。

### C3 · 规律 3(b)「改价 → PDF 一定变」过于绝对
- **证据**：PDF 文件名确带价格（`crawler.py:221`），改价通常重生成 PDF —— 勇哥直觉**有支撑**。
- **但**：REINS 的 PDF 是"物件図面/資料"，可能是固定模板或"重要事项说明书"，价格只是其中一页/文件名；部分系统改价不重新生成整份 PDF（价格字段与 PDF 分开维护）。更稳的判据是 **PDF 自身指纹（hash/内容）**。
- **且**：系统当前**根本探测不到"PDF 变了"**——覆盖式存储、无 hash、URL 又拿不到（全是 button）。所以即便想"靠改价推断 PDF 变"，也先要解决"怎么知道 PDF 变没变"这个前置问题（见 C5/C8）。

### C4 · 规律 3(a)「没改价 → PDF 不变」非绝对
- **分析**：`chg_date` 变了（平台有更新）但价格没变，可能改的是平面图/照片/備考/地図——这些恰好是 PDF 主要内容。所以"没改价→PDF 不变"也是概率性的。
- **修正**：同样以 PDF 自身指纹为准，价格只是强信号之一。

### C5 · 规律 3「PDF 有无」的探测前提缺失（内在矛盾）
- **矛盾**：勇哥说"历史无 PDF、现在有必须下"——但检测"现在有"本身就要**每次去探一下该房源详情页有没有 PDF 按钮**。而按 C1 的增量判定，若该房源"未变化"我们本想跳过它，跳过的同时就**探不到 PDF 新增**。
- **原修正（2026-10-01 17:40）**：增量判定里保留一个**轻量"PDF 可用性探测"**，不能因"详情未变"就完全不探 PDF。
- ✅ **2026-10-01 23:30 实证修正 —— 本矛盾已被"列表三图标"零成本化解，无需额外探测**：
  1. 勇哥 23:27 指出：REINS **检索结果列表页**每行右侧有 3 个标志（画 / 図 / 所），**亮=有、灰=无**——"有没有 PDF（図面）"在**列表页就能直接看出来**。
  2. 证据链：① PRD-10 §15.3 已坐实三图标类名（`p-icon-type-ga` 画 / `-zu` 図 / `-sho` 所）；② `crawler.py:1099-1107` + `_LIST_ICON_JS`（1120-1133）**已在解析**，落成 `has_photo/has_floorplan/has_map`；③ `store.py:38-39` 注释原话「这三个标记在**列表页就能读到**……永远准确」。
  3. **决定性实证**（对存档 `data/probe/result_page.html` 按行切块统计，58 行）：有「図」= **56**、有「画」= **19**、有「所」= **21**、三个都没有 = **2**；且**全页无任何 disabled/gray/off 类灰态类名** → 证明 **"灰"= DOM 里根本不渲染该 div**，当前 `has_*=1/0` 解析**完全准确**，能真实区分有无。
  4. **关键推论**：列表扫描是**每轮必做**的（阶段1 全列表对齐），而图标是**顺手取的**（`crawler.py:1099` 注释「一次 evaluate 顺手取回，零额外往返」）→ **刷新"平台现在有没有図面"的成本 = 0，不需要进详情页探**。
  5. **结论**：C5 矛盾消解。增量判定下即使跳过详情，只要该房源出现在当天列表里，`has_floorplan` 就会随列表刷新 → **"历史无 PDF、现在有"能被零成本发现**。规则 B 据此升级为**两层判据**（见 §5 规则 B 修订版 + §6.2）。
- ⚠ **残留边界（如实记录）**：v1.8.4 起 `main_round_enabled=false`，**只扫当天登録/変更的房源列表** → 图标只覆盖"当天有变动"的房源。这与本 PRD 增量判定的目标集合**恰好一致**（没变的不拉），故主路径无损；但**老房源若平台新増図面**（既不变动、又不在当天列表）探测不到 → 需低频全量补扫兜底（见 Q8）。

### C6 · 判定"是否更新"的锚点字段未定义（会踩老坑）
- **谬误**：勇哥用"上次下载之后更新的"，但没说用什么字段判断。
- **修正**：必须比较 **平台日期 `chg_date_iso`/`reg_date_iso`** 与"我方该房源**最后一次成功拉取时对应的平台日期版本**"。
- ⚠ **坑警示**：绝不能用我方 `last_seen_at` 当"更新"判据——这正是 memory NEW-1/D8 推送缺口的根因（"内容变了但没被再看到就永不重推"）。下载侧若复用该口径会重蹈覆辙。需在 properties 表新增 `last_pulled_chg_date`（我方拉取时记录的平台 chg_date），下次 `chg_date_iso > last_pulled_chg_date` 即触发必拉。

### C7 · 规律 2「不管变没变都重拉」成本过高
- **分析**：安全但重。REINS 有"续期"类更新（`meta_only`，PRD-35 已定义）：平台 `chg_date` 变了但内容实质没变（如延长广告期）。若"不管变没变都拉详情+PDF"，会反复重拉、反复重下 PDF，浪费且可能触发 REINS 风控。
- **修正**：以"`chg_date/reg_date` 落在我上次拉取窗口之后"作为"必拉"触发；拉回后做 diff，无实质变化就仅更新时间戳、不重复耗 PDF（除非 PDF 探测到新）——与 C2 升主规则联动。

### C8 · 盲区：PDF 历史版本存储缺失
- **事实**：当前 PDF 是 per-property 一份覆盖存（`crawler.py:148`），无版本/历史。勇哥规律 3 的"重新拉取作为历史记录"**无地基**。
- **修正（2026-10-01 23:23 实证修正）**：**指纹能力系统已有、可直接调用**，不是从零建——`ai_pipeline.pdf_hash()`（`ai_pipeline.py:51-57`）已实现"PDF 没变就不重跑"，`ai_structure.pdf_hash` 字段已有（`store.py:671`）。真正缺的是：①指纹**没有落到主库 properties**（当前只在 AI 库，且仅覆盖被 AI 处理过的约 40%）；②无版本归档（仍是覆盖式一份）。
- ✅ **2026-10-01 23:35 勇哥拍板（D13）：PDF 历史版本「暂不留存」，只保留最新一份，将来再考虑存储**。故：
  - ②「无版本归档」**不再是缺陷，而是被确认的目标状态**——PDF 保持**覆盖式单份**（沿用 `crawler.py:148`），新 PDF 直接替换旧文件。
  - M1 地基简化为：**补主库 `pdf_sha256` 字段 + 一次性建全量基线**；**不再引入 `pdf_ver` / 版本归档 / 历史目录**。
  - ⚠️ **范围澄清（别误伤）**：本拍板**只针对 PDF 文件**。**详情（detail）的历史版本照旧保留** —— C2 升主规则与 `property_history` 时间轴（PRD-35 F5）不受影响，仍需 diff 后写历史、升主。二者不可混为一谈。
  - 📌 **已知代价（如实记录，便于将来回看）**：PDF 被覆盖后**无法回溯旧版図面**（如"降价前的户型图/价格页"拿不回来）。若将来要看历史 PDF，需届时重做归档；当前按勇哥决定不预防性建设。

## 5. 修正后的下载筛选规则（建议落地版 · 可直接转代码）

### 规则 A · 详情增量判定三态
| 状态 | 触发条件 | 动作 |
|---|---|---|
| **跳过** | `max(chg_date_iso, reg_date_iso) <= last_pulled_chg_date`（平台自我方拉取后未变）**且** `detail_json` 已存在 | 不重拉详情 |
| **必拉** | `max(chg_date_iso, reg_date_iso) > last_pulled_chg_date`（平台自我方拉取后变了） | 重新拉详情 → 进规则 C 升主/diff |
| **可疑补拉** | `detail_json` 为空/伪详情（缺 address），或 `last_seen_at` 过旧（`backfill_refresh_stale_days`） | 强制拉详情（沿用现有 backfill 逻辑） |

> 纯函数草案（RD 转交粒度）：
> ```python
> def need_detail_pull(row, last_pulled_chg_date):
>     plat_max = max(filter(None, [row["chg_date_iso"], row["reg_date_iso"]]), default="")
>     if not row["detail_json"] or _is_pseudo(row):       # 壳/伪详情
>         return "FORCE"
>     if plat_max and plat_max > (last_pulled_chg_date or ""):
>         return "PULL"                                    # 平台自我方拉取后变了
>     return "SKIP"
> ```

### 规则 B · PDF 增量判定（2026-10-01 23:50 修订版 · **Q8 拍板 B：以详情页为准**）

> ✅ **勇哥 23:44 拍板 Q8 = B：维持 v1.8.3「以详情页为准」**，**不复活** v1.5.13 的图标门禁。理由原话：「还是 B 吧……因为工作量没有增加太多」。
> ⇒ **每套都照常进详情页，由「図面参照」按钮是否存在决定下不下 PDF**（现状行为，代码不用改）。
> ⇒ 列表 `has_floorplan` 图标**仍只作统计与"定性"**，**不拦截任何下载**（与 `crawler.py:1731-1735` 现状一致）。
> ⇒ 判据仍分两层，但**第 1 层改由详情页按钮说了算**，图标降级为辅助定性：
> - **第 1 层「有没有」** = 详情页「図面参照」按钮是否存在（B 方案唯一判据）+ 图标作**零成本定性**；
> - **第 2 层「变没变」** = `pdf_sha256` 指纹 → 只在第 1 层判"有"之后才用。

**第 1 层 · 有无判定（详情页为准）**

| 详情页「図面参照」按钮 | 平台図图标 | 我方 PDF | 判定 | 动作 |
|---|---|---|---|---|
| **有**（能点到） | 亮 | 无 | **无→有** | **必下**（勇哥规律 3 首句） |
| **有** | 亮 | 有 | 进入第 2 层 | 比指纹，指纹不同才重下 |
| **无**（点不到） | 灰 | 无 | **不适用** | 🟢 **零成本"定性"**：标记「平台本就没有図面」→ **不计入 PDF 缺口、不记失败、不再反复追问**（沿用 `crawler.py:517-542` 现有"缺口分母只算 has_floorplan=1"口径） |
| **无** | 灰 | 有 | **有→无**（平台撤図，罕见） | 保留旧 PDF + 告警，**不自动删** |
| **有** | 灰（图标滞后，罕见） | — | **以详情页为准** | 照下（B 方案的好处：**不存在"图标滞后导致漏下"**） |

> 📌 **B 方案下 C5 矛盾自动消失**：每套都进详情页 ⇒ "历史无 PDF、现在有"天然会被发现，**不需要额外探测机制**（原本为解 C5 设计的探测逻辑作废）。代价=白跑趟数略多，勇哥已接受。
> 📌 **保留"定性"价值（不违背 B）**：图标虽不拦截，但当"图标=0 且详情页也点不到按钮"时可零成本定性为"平台本就没有"，把这类房**从 PDF 缺口/失败里剔除**——**不增加任何请求**，纯记账改进。

**第 2 层 · 变没变（以 `pdf_sha256` 指纹为准）**

| 状态 | 触发条件 | 动作 |
|---|---|---|
| **有→有·同** | 新下载文件 `sha256 == pdf_sha256` | 不覆盖、不归档、仅记时间戳 |
| **有→有·变** | `sha256 != pdf_sha256` | 重下 → **直接覆盖旧文件**（D13：不留存历史版）→ 更新 `pdf_sha256` |
| **改价强信号** | `price != previous_price` 且我方已有 PDF | 仍走指纹比对；改价仅作**优先探测/人工核查**信号，**不豁免指纹校验**（C3/C4 修正） |

> ⚠ 修正勇哥 3(a)/3(b)：PDF 是否变**一律以 `pdf_sha256` 指纹为准**，价格不是判定依据（勇哥 23:44 确认："PDF 文件也有指纹，指纹变化再重下"）。
> ⚠ **图标只管"有没有"、绝不当"变没变"的判据**：図图标亮着 ≠ 図面内容没换过（C4 已证：改備考/改照片不改价时图标仍亮）。

**第 2 层的执行方式（勇哥授权"你来把握哪种方式"→ 二巴定：size 预筛 + sha256 终判）**

勇哥 23:44：「PDF 文件也有指纹，指纹变化再重下。包括可以去对比文件的情况。你来把握哪种方式。」

| 步骤 | 做什么 | 成本 | 判定力 |
|---|---|---|---|
| ① **size 预筛** | 新下载文件与旧文件比大小（只 `stat`，不读内容） | 极快 | 大小不同 ⇒ **直接判"变了"**，立即重下（跳过算 hash） |
| ② **sha256 终判** | 大小相同 ⇒ 才算 sha256 比对 | 读一次文件 | **唯一确定性判据** |
| ③ **mtime** | ❌ **禁用** | — | `os.replace()` 落盘 ⇒ mtime=我方下载时刻，非平台生成时刻（§6.1 已证，会假阳性） |

> 采用理由：绝大多数"真变了"的 PDF 大小也会变 ⇒ ① 能省掉大部分读盘；② 兜住"内容变而大小恰好不变"的碰撞。二者结合 = **又快又准**，符合勇哥"指纹变化再重下 + 也可以对比文件情况"的意图。

### 6.1 PDF 指纹可行性实证 + 替代判据可靠性评估（勇哥 23:23 追问）

**问题1：能否直接获取每一个 PDF 的指纹？**

✅ **能，且系统已在算、已在用——不是从零建**：

| 已有能力 | 代码位置 | 说明 |
|---|---|---|
| `pdf_hash()` | `ai_pipeline.py:51-57` | sha256 前 16 位，1MB 分块读；注释原话「PDF 没变就不重跑——省时省力」 |
| `ai_structure.pdf_hash` 字段 | `store.py:671` | 注释：「来源 PDF 指纹（sha256 前 16 位），用于「PDF 变了才重跑」」 |
| `_sha256_of()` | `pdf_cloud.py:195-197` | 完整 sha256，用于上传审计（`pdf_upload_audit` 表存 sha256，`store.py:936`） |
| 按番号记录当前 PDF sha256 | `ai_structure_store.py:367` | `{property_no: 当前 PDF 的 sha256 前 16 位}` |

- **成本实测**：本地 `data/attachments` 现有 **6094 份** PDF（实测），约 3.1GB。算指纹是**只读本地文件**，单份几 MB → 毫秒级；全量建基线 = 读一遍 3.1GB（几分钟，可后台跑）。
- **无需全量重算**：已被 AI 处理过的（约 2412 份）直接复用现有 `pdf_hash`；只需"新下载时算"+"补算剩余未覆盖的"。
- ⚠ **当前真实缺口**：指纹只落在 **AI 库 `ai_structure`**（且仅覆盖被 AI 跑过的约 40%），**主库 properties 没有** → PRD-37 的 PDF 判定读不到主库。**M1 地基（D13 简化后）= 补主库 `pdf_sha256` 字段 + 一次性建全量基线**；~~引入版本归档~~ ❌ 已取消（勇哥 23:35 拍板 PDF 不留存历史版）。

**问题2：不获取指纹，用 大小 / 修改时间 判断行不行？**

| 判据 | 可靠性 | 结论 |
|---|---|---|
| **文件大小 (size)** | 🟡 中 · 可粗判 | 改价→PDF 重生成，**大小几乎必变**（价格数字变、可能带生成戳）→「大小不同」可判"变了"。但存在"内容变而大小恰好不变"的碰撞 → **不能作确定性判据**。优点：只 `stat` 不读内容，极快。 |
| **修改时间 (mtime)** | 🔴 **最差 · 不可用** | PDF 是我方下载后 `os.replace()` 原子落盘（`crawler.py:40,148-149`），**mtime = 我方下载时刻**，不是 REINS 侧生成时刻 → 只反映"我何时下的"，**完全不反映平台侧 PDF 变没变**。且现有 `_pdf_exists`（"文件在=已下载→跳过"，`crawler.py:152-158`）根本不重下，mtime 一直停留在最初下载时刻，更失真。**反例：同一份 PDF 重下一次 → mtime 变但内容没变 → 误判为"变了"（假阳性）。** |
| **ETag / Last-Modified (HTTP 头)** | 🔴 **拿不到** | 最优雅（不下载完整文件就能问"变没变"），但 REINS 的 PDF 是 `<button>図面参照</button>` 点击下载、**整页无 `<a href>` 直链**（`crawler.py:218-224`）→ 无 URL 可发 HEAD 请求，故拿不到 HTTP 层判据。 |
| **PDF 内容指纹 (sha256)** | 🟢 **唯一可靠** | 逐字节确定性；系统已有 `pdf_hash()` / `_sha256_of()` 可直接调；本地全量可读，零外部依赖。 |

**结论与落地建议**：
1. **指纹是唯一可靠判据**，且已有能力可直接复用——问题不是"能不能"，而是"把已有能力铺到主库"。
2. **size 可作"预筛"**：先 `stat` 比大小（极快）→ 大小不同直接判变、必重下；大小相同再算 sha256 确认 → 能省掉多数读盘。
3. **mtime 明确不可用**（只反映我方下载时刻），**禁止**作为判据。
4. 落地：M1 = 补主库 `pdf_sha256` 字段 → 一次性对 6094 份建基线（后台跑）→ 后续每次新下载先比 size、再算 hash。

### 10.2 步骤1 · 列出所有下载方式中的下载条件

**体系A 条件（来源 `cfg.crawl` + `cfg.schedule` + `cfg.download`）**
- 日期轴：当天「登録/変更」双轴 × 6 種目组 = 12 次检索（`collect.html:204` roundplan 预览）
- 種目：主轮组（默认 6 组，与体系B 默认值语义一致：一户建2+公寓4）
- 所有权/可选过滤：由 `cfg.crawl` 决定，**设置页无 UI 暴露**（用户无法在界面调自动更新的这些过滤）
- PDF：`cfg.download.pdf` 全局，默认 True（`crawler.py:1557/3098/3296`）—— **体系A/B 共用同一开关**
- 时间：`window` 07:00–23:00（`app.py:3099-3101`）+ 随机间隔（`interval_hours` / `random_min/max`，`app.py:3080-3098`，下限夹 5 分钟防轰炸）
- 附加开关：`main_round_enabled`（全期间主轮，默认关）/ `sync_dates_backfill_prev_day`（前日补齐，默认开）/ `stage_b_enabled`（阶段B 补详情+PDF，默认开）/ `auto_split_on_limit`（500件拆细，默认关）

**体系B 条件（来源 `collect.html` 表单）**

- PDF：读全局 `cfg.download.pdf`（同体系A）
- 控制：暂停/继续/停止 + 按日进度（PRD-36）

### 10.3 步骤2 · 比较并确定最优

- **用途正交，不互斥**：体系A = 持续自动维护全库新鲜度（**主力**）；体系B = 按需精确补抓历史日期段（**补漏**）。**不存在谁替代谁**。
- 若问"日常主用" → 体系A（自动更新）是主力；体系B 是补漏/补历史。
- 若问"轻量验证" → 体系A 试跑(trial) 与 体系B「确定(预览)」都是轻量校验档，用途相同。
- 🔴 **对 PRD-37 落点的结论**：增量判定（§5 规则 A/B/C）应**优先叠加到体系A**（让自动更新从"全量当天双轴"升级为"增量判定 + 当天双轴"）；体系B 已是按日期段天然增量、无需改判定逻辑，仅需在 UI 复用同一套"增量/PDF 指纹"提示。

### 10.4 步骤3 · 是否需要进一步调节
