> 与之并列的另一条线是**研发线**（`core/`、`web/`、`config.yaml`）。两条线的关系见 §一。

---

## 一、两条线是什么

| | **产品线**（本目录 `docs/`） | **研发线**（`core/` `web/` …） |
|---|---|---|
| 回答什么问题 | 做成什么样、为什么这么做 | 怎么做出来的 |
| 读者 | 业务方 / 产品 / 同事 | 看代码的人、下一个接手的人 |
| 载体 | PRD 稿、方案、沟通记录（Markdown） | Python / Jinja 模板 / JS / CSS |
| 改动时机 | 想法先落到文档 | 文档定了再改代码 |
| 版本号 | 各 PRD 稿自己的版本；主 PRD 另有 `vX.Y.Z` | `core/version.py` 的 `VERSION`（页脚显示它） |
| 备份 | 与研发线 **同一次存档** | 同左 |

**为什么两条线用一个仓库而不是两个仓库**：这个项目里"改需求顺带改代码"是常态（例：`v1.2.5` 同时改 PRD 与 4 个 `.py`）。
若拆成两个仓库，回滚会变成半截——代码退回去了、PRD 没退，下一个接手的人就会照着错的文档去理解代码，比不回滚更危险。
所以约定是：**两条线分开阅读、分开演进，但在同一个检查点里一起备份**。
（确实要拆两个仓库也能做：把 `checkpoint.py` 扩展成"双仓库分别提交"，见 `../../README.md` 第六节。）

## 三、备份约定（两条线同时备份）

一次 `checkpoint.bat` / `python checkpoint.py "说明"` 同时覆盖三块内容：

| # | 内容 | 落到哪 |
|---|---|---|
| 1 | **数据** | 房源库 `data/jproperty.db` → `.backups/db/`（保留最近 20 份，内容没变不重复存） |
| 2 | **产品线** | `docs/**` 的全部改动 → git 检查点 |
| 3 | **研发线** | `core/**`、`web/**`、`config.yaml`、根目录脚本 → 同一个 git 检查点 |

存档输出会**分别报告两条线各改了几个文件**；`python checkpoint.py --lines` 可单独查看两条线各自的状态。
详见 `../../README.md` 第六节。

## 四、维护约定

1. **先文档、后代码**：需求想清楚先写进本目录，再动 `core/` `web/`。
2. **一个需求落两处**：功能类改动写进 `../UI_PRD/界面的UI及功能.md`（界面口径）+ 本目录对应主题 PRD（业务口径）。
3. **每轮沟通必须留痕**：与业务方的每一次澄清/拍板，追加到 `00_沟通记录与需求演进.md`，只增不删。
4. **不同步的东西要标出来**：写「待确认 / 尚未实现」时用 ⏳ 标记，闭环后改成 ✅ 并注明版本。
