## 1. 文档目的与读者

- **本文是什么**：把「用 AI 把房源 PDF（REINS 物件チラシ，含**文本型 PDF 与图片型 PDF**）里的信息读出来、变成结构化表格、并展示到网站房源详情页」这件事，从**需求 → 架构 → 功能 → 接口 → 决策**一次说清。
- **读者**：产品经理（PM）、开发经理（RD）、项目经理（跟踪进度）、QA（验收门禁）。
- **与现有文档关系**：本功能是详情页的一个**新增卡片「AI 解读」**，不改动主抓取链路；它依赖现有的 `properties` 主库做交叉校验，但**独立存储、独立库文件**（勇哥硬要求：AI 数据与其他数据不直接相关）。

## 2. 背景与目标

### 2.1 背景
- REINS 每套房源有一张 PDF（物件チラシ），含价格、面积、构造、管理费、中介联系方式等约 59 个字段；PDF 多为**图片/扫描件**，也有部分文本型；靠人工录入成本高、易错。
- 已能把这些 PDF 用 AI 识别成一张 Excel 总表（《大阪房源PDF数据总表》，59 列、193 行），但**识别结果还没系统、稳定地进入网站详情页**。
- 勇哥要求：AI 识别结果**单独一个文件存储**，与主业务数据分离；字段可人工编辑、可审计；详情页卡片统一叫「**AI 解读**」。

### 2.2 目标
1. **自动/半自动**把 PDF（文本型或图片型）读成结构化字段（尽量本地、尽量不花钱）。
2. 识别结果进**独立库文件**，按房源番号关联到详情页。
3. 详情页用一张「**AI 解读**」卡片展示：① 分组字段（有则显、无则不显；无校验规则列灰显「待补规则」，见 P2-13）② 异常数值红色标注 ③ 六维雷达图 + 约 200 字中文结论 ④ 字段可人工编辑并留痕 ⑤ 员工改过的字段**蓝色显示** ⑥ **AI 识别 vs 主库差异摘要行**（见 FR-12）。
4. 质量可控：取不准的值**宁缺勿滥**（脏值不显），进「待核对」交人裁决（闭环见 FR-11）。
5. 提供**设置项**：后台可手动选择「哪些数据通过 AI 读取」。
6. 线上站：用户/员工点「AI 生成数据」按钮 → **任务派发到本地电脑执行** → 跑完即时同步上传（不冲突、有状态提示、有离线/超时兜底，见 FR-9）。

### 2.3 非目标（Out of Scope，本版）
- 不改写 `properties` 主库任何抓取字段（AI 只是**派生/解读层**）。
- 不做贷款、税费测算。
- 不做 PDF 原文件公有站外发（合规：公开站只展示 detail 结构化内容）。
- **上云自动提取**（破「线上只读」约束）本期不做（D6 已用派发架构规避）。

**两条入口的现状（11.3⑥已拍板）**：

## 4. 功能需求（FR）

### FR-1 PDF 本地优先提取（三级降级，D1 写死）
- **数据来源**：仅**文本型 PDF** 与**图片型 PDF**（REINS 物件チラシ）；不处理其他来源。
- **L1 文字层**：`pdf_local_extract.text_of()` 直接读文字层。
- **L2 本地 OCR**：按**字段重要性分级降级**（P2-12）——关键字段（价格、面积、间取）缺失即强制走 L2；次要字段缺失仅标 warn 不强制 OCR。L2 用本地 OCR 补抽。**图片型 PDF 的 OCR 引擎由我选型**（目标：日文图片 PDF 效果更好；候选 tesseract-jpn 高参数 / PaddleOCR-jp，最终以实测效果定），并配套**数据层校验**（复用 `ai_quality`，OCR 残片/噪声按 FR-2 拦截）。
- **L3 云端兜底**：**暂不做**（D3，见第 8 节）。当前代码里 L3 分支保留但默认不启用，避免误花钱。
- **硬规则 D1（写死不许改）**：「先用本地读取或做 OCR，读不出来才发第三方模型。」→ L1/L2 出结果就**绝不走 L3**；若将来启用 L3，每次调用记入 `ai_run_log.cloud_used`，本地命中记 `local_hit`。

### FR-2 质量闸门（宁缺勿滥）
- 模块 `ai_quality.check(col, value, ctx)`：`(ok, reason, normalized)`；不过闸门的列不写入结构字段，进「待核对」。
- 关键规则（已实测、已修坑）：専有面積 ㎡↔坪 ±3%；月度费用 `0 < x ≤ 300000` 且合计≥分项；構造/現況/管理体制 枚举白名单；**FAX≠TEL**；E-MAIL/地址格式；**标签残片拦截**（OCR 把邻标签值切给本字段）；通用噪声/超长值驳回。
- **无规则列显示策略（P2-13，采纳）**：约 29/59 列无显式规则 → **不静默丢弃**，在卡片中**灰显 + 角标「待补规则」**；与「脏值不显（宁缺勿滥）」区分：待补规则 ≠ 脏值，灰显可接受，待后续扩列。
- **现状（11.3⑤已拍板）**：约 30/59 列有显式规则，勇哥**暂时接受**此口径，不强制扩列（扩列为可选优化，见 11.1）。

### FR-3 独立库存储
- 文件：`data/ai_pdf_store.db`（与主库 `jproperty.db` 同目录、不同文件）。
- 表（**v1.2.0 调整**）：
  - `ai_field_meta`(59 列四语言字典)
  - `ai_structure`(每房源一行，**新增列** `edit_policy` `revision` `extractor_version`，见下)
  - `ai_edit_log`(编辑审计，含 `editor`、`revision_after`)
  - `ai_run_log`(运行账)
  - ~~`ai_tasks`~~ **移出本地库**（见 P0-2）：任务队列**建在线上发布库**，本地 HTTP 轮询。
- **人工值保护 R1（升级为 edit_policy，见 P0-4）**：`ai_structure.edit_policy` 三选一 `never`(默认，AI 永不覆盖 edited 字段) / `prompt`(平台变更时弹提示让员工决定) / `auto`(允许 AI 覆盖)。本期默认 `never`；`upsert(..., preserve_edited=True)` 对 `never` 列生效。

### FR-4 Excel 总表批量导入（**临时/弃用**，11.3⑥）
- `tools/import_ai_pdf_excel.py` 仍可用（193 行在库），但**不在产品口径内**；将来全部走 B 路数据库跑。保留作为历史数据回填手段，不新增功能。

### FR-5 六维雷达图 + 200 字结论
- `ai_score.build_radar()` 六维（通用权重，和=100）：性价比 25% / 地段交通 20% / 收益性 15% / 房龄 15% / 舒适度 15% / 流动性 10%。
- **权重按房产类型（P1-8，采纳为设计扩展）**：`ai_score.build_radar()` 留 `weights_by_kind` 字典，按 `kind`(マンション/戸建/土地) 取不同权重；本期实现三档 + 默认回退通用权重（依赖 `kind` 字段可靠可取得——Excel 总表含種目列、B 路 PDF 可抽，故可行）。
- `ai_score.build_conclusion()`：约 200 字中文卖点，脏单价闸门（>250万/㎡ 或 <8万/㎡ 视为 OCR 脏数据，改用 价÷面积 重算）。
- **结论数字一致性硬约束（P1-7，采纳）**：200 字结论中的所有数字**必须与雷达图/字段对得上，不得凭空写**（由字段推导，加断言校验）。
- **免责声明（P1-7，采纳，强）**：「AI 解读」卡片底部固定一行：「AI 自动生成，仅供参考，请以实际合同为准」。带客户看房场景，AI 数字错会出大事，故强制。
- **「结论错误」反馈（P1-7，采纳）**：卡片加反馈按钮，员工一键标记 → 记 `ai_run_log` 供模型优化。

### FR-6 详情页「AI 解读」卡片展示
- 路由：`GET /api/ai-interpret/<property_no>`（对外命名统一「AI 解读」；后端路径由 `ai-structure` 重命名为 `ai-interpret`，前端/i18n/文案同步改，见 11.1①）。
- 卡片内容：① 雷达图（SVG `aiRadar()`）② 约 200 字结论（含底部免责声明，FR-5）③ 分组字段（有则显、无则不显；无规则列灰显「待补规则」，FR-2）④ 异常色标（`warn`=红字；`danger`=红字黄底）⑤ 可编辑（`aiBindEdit()`）⑥ **员工改过的字段蓝色显示**（`.ai-edited-employee{color:#1565ff}`，见 FR-7）⑦ **AI 识别 vs 主库差异摘要行**（FR-12）⑧ **编辑回溯 hover**（FR-10 回溯）。
- **四语言**：zh / zh_tw / en / ja 字段名与分组名来自 `ai_field_meta`。

### FR-7 字段编辑、审计与员工权限
- `POST /api/ai-interpret/<property_no>/edit`：改单字段 → 写 `structure_json` + 记 `ai_edit_log`(含 `editor`) + 标 `edited=1`。
  - **乐观锁（P0-3，采纳）**：请求须带 `expected_revision`；与当前 `revision` 不符返回 **409**，前端提示「另一员工刚改过，已为你刷新最新值」；`ai_edit_log` 保留所有版本可回溯。
  - **editor 捕获（已知实现缺陷，见 13.4）**：当前代码用 `request.user`（Flask 无此属性）致 `editor` 恒空，须改为 `session["user_id"]`/`_current_user()`；上线前必修。
- `GET /api/ai-interpret/<property_no>/edits`：编辑历史（供 hover 回溯，FR-10）。
- **员工编辑（11.2⑥已拍板，P0-5 绑定发布）**：线上员工**有权限编辑**（无疑问）。要求：① 编辑必须带 `editor`（员工账号，可追溯谁改的）；② 员工改过的字段**前端用蓝色显示**。
  - **前置依赖（P0-5，修复矛盾）**：员工编辑的**本地部分**可直接动手；**线上编辑功能 = 员工账号体系（PRD-19 v2）上线到线上 + 蓝色 UI，二者绑定一起发**，线上无 `/staff` 前 `/edit` 保持 403（见 12）。

### FR-8 每晚定时抽取
- `ai_scheduler.AIScheduler`：本机 23:00–06:00 窗口；队列「遗留+当日新增（按 PDF mtime 增量）」，单轮 `max_per_run` 只防过载不裁任务；`pdf_hash` 未变跳过；**`extractor_version` 变化时 `--force` 重跑（P2-11）**。

### FR-9 线上触发 · 本地执行（即时同步 + 故障域兜底，11.2⑤已拍板）
- **触发**：线上详情页「AI 生成数据」按钮 → `POST /api/ai-tasks`（写**线上库** `ai_tasks`：status=pending, property_no, requested_by=员工, created_at）。
- **状态提示**：前端点按钮后轮询/或 SSE 显示「当前正在读取」→「正在 AI 解读，请稍后」→ 完成/失败。
- **本地执行**：本地 8765 进程新增**轻量拉取循环**（集成进 `ai_scheduler` 或独立线程），每 ~15s 向线上 `GET /api/ai-tasks?status=pending`（带令牌，复用 `/api/ingest` 令牌机制）拉任务 → 对每个 pending 番号执行 `ai_pipeline.run_one`（读本地已落盘 PDF）→ 调线上 `POST /api/ingest`（v1.9.19 已豁免登录守卫）上传 → 更新 status=done。
- **故障域兜底（P0-1，采纳）**：
  - 本地每 15s `POST /api/ai-heartbeat`（带令牌）；线上超过 **60s** 无心跳即判「本地离线」。
  - 前端按钮置灰 + 提示「本地服务离线，请联系管理员开机」；页面显示在线/离线**状态灯**。
  - pending 任务超过 **4 小时**自动标记 `failed_timeout`（不永久 pending）。
- **冲突规避（勇哥要求「确保不冲突」，已分析）**：
  - 资源：本地 AI 读的是**本地已落盘 PDF**，不占用 REINS 爬取的 Playwright/Edge 浏览器会话；主轮（浏览器）与 AI（OCR/模型读本地文件）互不抢端口/会话。
  - 任务锁：本地拉取先标 `running`（乐观锁），同一番号正在跑则跳过；与每晚 D3 调度队列执行入口同为 `run_one`，**天然去重**，不重复跑。
  - 网络：线上只读、不反向连本地，**无 NAT 穿透问题**（本地主动拉+推）。
  - 结论：**与现有 8765 进程无冲突**。

### FR-10 设置项：手动选择哪些数据走 AI 读取（11.2→已拍板的最小上线方案）

- 此页是「宁缺勿滥」的另一半——只进不出等于黑盒，必须闭环。

### FR-12 AI 识别 vs 主库差异摘要（P1-9，采纳）
- 「AI 解读」卡片顶部固定一行差异摘要，例如「AI 识别价格 2800 万（与主库 3000 万差 -200 万，待核对）」。
- 本地 8765 可直接读 `jproperty.db` 主库字段对比；线上需 `/api/ai-interpret` 一并返回主库对应字段（或独立 `/api/ai-diff`）。
- 价值：AI 的真正用处是**发现 REINS 抓取错漏**，而非仅展示。

### FR-13 备份与回滚（P2-15，采纳，强）
- 每晚 `sync_to_publish` 前自动备份 `ai_pdf_store.db.YYYYMMDD`，保留最近 **14 天**；OCR/重跑跑坏可回滚。

## 5. 非功能需求（NFR）
- **成本**：L1/L2 本地 0 元；L3 暂不做。
- **性能（P2-14，采纳）**：单份 PDF 提取秒~数秒级；批量夜里跑。MVP 阶段先跑 **200–500 套试点**，测单份真实耗时后再决定全量排期（3872 套 × 数秒 ≈ 数小时，夜里 7 小时窗口勉强够；图片型全 OCR 可能翻倍）。
- **合规/安全**：AI 数据独立库；不覆盖人工主数据（R1/edit_policy）；公开站不暴露 PDF 原文件、不暴露凭据（`config.local.yaml` 真值 gitignore）；员工编辑留痕。
- **可观测**：`ai_run_log`（本地命中/云端花费/结论错误反馈）、`ai_edit_log`（谁改的、版本）、`ai_tasks`（派发状态）、心跳在线状态均可查。
- **可靠性**：提取/打分全程 try/except 兜底；线上只读站 PRD-25 代码在也不崩（no-op）；`ai_pdf_store.db` 每日备份（FR-13）。

## 6. 数据模型（独立文件 `ai_pdf_store.db` + 线上库）
> 详见 `core/ai_structure_store.py` SCHEMA；字段名以《总表》59 列为准。

| 表 | 关键列 | 说明 |
|---|---|---|
| ai_field_meta | col_name, seq, group_key, zh, zh_tw, en, ja, source | 59 列四语言字典 |

| P2-13 | 29 列无规则字段静默丢弃 | **部分采纳** | 不静默丢弃：灰显 + 角标「待补规则」。但需与「宁缺勿滥(脏值不显)」区分——待补规则 ≠ 脏值，灰显可接受。修正了我「无则不显」的硬规则。 | FR-2 显示策略 |

### 13.2 我的保留/补充意见（非照单全收）
- **P0-3 严重度**：我内部判 P1，因 14 人内部工具同字段并发极低；但为达评审「有条件通过」条件且成本低，仍按 P0 落地。若排期紧，可先上 `expected_revision` 校验、409 提示，全版本回溯后续补。
- **P1-8 依赖**：权重按 kind 的前提是 `kind` 字段可靠。若 B 路 PDF 抽不出稳定種目，则回退通用权重——这是**设计扩展点**，不阻塞 MVP。
- **P2-13 与「宁缺勿滥」的边界**：我明确「灰显待补规则 ≠ 脏值显示」。脏值（OCR 残片/超范围）仍不显；仅「无校验规则故未裁决」的列灰显，待扩列后转正常。

### 13.3 已知实现缺陷（我自查发现，供评审注意）
- **editor 捕获 bug**：`web/app.py` 的 `api_ai_interpret_edit` 用 `getattr(request, "user", None)` 取操作人，但 **Flask 的 `request` 无 `.user` 属性**（正确应为 `session["user_id"]` 或 `_current_user()`）。实证：`ai_edit_log.editor` 恒为空串。此 bug 直接卡死 P0-3/P0-5/P1-10 的「谁改的」留痕，**上线前必修**（小改动、本地 8765 重启即生效）。
- **ai_tasks 当前在本地库**：代码 `core/ai_structure_store.py` 的 `ai_tasks` 表定义在本地 `ai_pdf_store.db`，与本文 v1.2.0「归属线上库」决策不一致——实现时需将 `ai_tasks` 迁到线上发布库 schema，本地侧改为 HTTP 轮询。属 P0-2 落地动作。
