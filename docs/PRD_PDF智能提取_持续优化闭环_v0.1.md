# PRD：PDF 智能提取能力（OCR 识别 + 选模型 LLM 提取 + 持续优化闭环）

> **版本**：v0.1（草稿，待勇哥评审后共同细化，尚未落地）
> **日期**：2026-09-26
> **作者**：小巴（基于勇哥在另一台 WorkBuddy 沉淀的《本地 PDF 房源信息提取系统》经验 + osaka-mvp 现有提取链路对比后整理）
> **目标读者**：勇哥（产品拍板人）+ 接手实现的工程师

## 0. 一句话总纲（先读这段）

勇哥想要的能力：**PDF（单个或一批）进来 → 用文本识别 + 图形识别软件把它变成文字 → 再丢给"当前选中的某一个大语言模型"做进一步结构化识别 → 模型在这个过程中不断自我优化、识别率越来越高。**

目前这个能力在两处都有"半成品"：
- **A 号机（你的经验文档）**：已经把"认字（OCR）+ 选模型填表（LLM）+ 6 层质量护甲"跑通，但**没有自我优化闭环**（反例是手写的历史错题）。
- **B 线（osaka-mvp）**：已经把"认字（OCR）+ 规则正则填表"跑通且极省成本，LLM 只当兜底解说员，**既不擅长结构化填表、也没有护甲和闭环**。

本稿的核心主张：**把 A 号机的"LLM 填表 + 护甲"和 B 线的"规则填表"打通，并补上两边都缺的"持续自我优化闭环"**——这才是勇哥真正想要的那一步。

## 1. 现状对比：A 号机经验 vs osaka-mvp 现有提取链路

| 维度 | A 号机（本地 PDF 提取系统 PRD） | osaka-mvp B 线（ai_pipeline 三级降级） | 差异 / 互补点 |
|---|---|---|---|
| **认字层 L1** | PyMuPDF 直接抠文字层（≈100% 准、零成本） | `core/pdf_local_extract.py` 同款（含部首归一、模糊认定、取值闸门） | **完全一致，都已验证** |
| **认字层 L2** | Tesseract OCR（CPU、免费、数字稳） | `core/ocr_local.py` 同款（含空格塌缩/复选框噪声/千分位修复/标签切分） | **完全一致，都已验证** |
| **二次识别层（填表）** | **LLM 当主力填表员**：纯文本 → 本地 `qwen2.5vl:3b` → 59 列 Excel，启用 schema 约束锁格式 | **规则正则当主力**；LLM（`core/ai_extract.py`，豆包 `doubao-seed-1.6`）**仅当 `min_fields` 未达到才兜底**，且只产出"标题/卖点/字段/备注"解说卡，**不做 59 列映射** | 两套填表策略：**A=LLM 为主，B=规则为主**。B 已在 REINS 上把规则做到极致（免费+高准）；A 的 LLM 填表更适合**没有规则的新 PDF 域**或**规则抽不到的漏网字段** |
| **质量护甲** | 字典/别名归一 + 反例注入 + GBNF schema 约束 + Pydantic 后校验 + 三字段视觉复核 + 双路交叉验证（6 层） | L1/L2 有取值闸门 + 模糊认定 + `ai_quality` 打分；但 **LLM 层（L3）没有任何 schema/反例/交叉验证护甲** | A 的护甲是 B 线 LLM 层**完全缺失**的部分，可直接补强 |
| **持续优化闭环** | **无**（反例是人工手写的历史错题，不自动增长） | **无**（L3 每次独立调用，不积累经验） | **两边都没做**——这正是勇哥本次想要的新能力 |
| **成本原则** | 主链路本地 0 成本；线上 AI 只抽样抽查 | 本地规则免费；LLM 兜底按 `min_fields` 阈值才触发（同样节流） | 节流思路一致 |
| **模型选择** | Ollama 本地 `qwen2.5vl:3b`（可换 deepseek-r1:7b 当复审） | 云端豆包（OpenAI 兼容，可换 Ollama/DeepSeek），由 `config.local.yaml` 的 `ai` 块（base_url/model/api_key）切换 | 都已支持"选模型"，接口可统一 |

**关键洞察（给勇哥的结论先讲）**：
1. "认字"这件事两边已经**完全解耦且验证过**，不用重做，复用即可。
2. "填表"两边其实是**两条互补路线**——B 线规则为主（REINS 已证明省钱高准），A 号机 LLM 为主（适合新域/漏网字段）。**最优解是让它们共存、按域择优选**。
3. 勇哥最看重的"模型不断自我优化、识别率不断提高"，**目前两边都是空白**。本 PRD 把这块作为设计重点（见第 3 节）。

## 2. 核心结论：要不要做成 Skill？

**建议：做成 Skill（可复用能力），但边界要划清。**

### 2.1 为什么值得做成 Skill（而非只写进 osaka-mvp 代码）
- 勇哥的诉求是**通用能力**："PDF 过来 → 识别 → 选模型 LLM → 持续优化"，不只在 REINS 用，将来任何"从 PDF 抽结构化字段"的场景都能复用。
- 它是一条**固定多步流水线**（装识别软件 → 识别文字/图形 → 选模型提取 → 校验 → 沉淀错题 → 再优化），符合"可复用工作流"的 Skill 标准。
- 涉及的环境/工具决策（Tesseract 路径、Ollama 模型、提示词护甲、错题本）每次都会重造，**抽成 Skill 能一次沉淀、处处调用**。

### 2.2 边界划清（重要，避免重复造轮子）
| 归属 | 内容 | 理由 |
|---|---|---|
| **保留在 osaka-mvp 代码**（不进 Skill） | `pdf_local_extract.py` / `ocr_local.py` 的 L1/L2 规则与 OCR 修复、REINS 59+ 字段表、取值闸门 | 已在 REINS 上验证、与业务强绑定，是项目资产不是通用能力 |
| **做成 Skill（通用能力）** | ① 可调用的"PDF→结构化提取+持续优化"编排 ② 提示词护甲（反例库/字典归一/schema/交叉验证）③ 模型路由（本地 Ollama ⇄ 云端豆包/DeepSeek/Gemini，统一 OpenAI 兼容）④ 错题本 + 评测集 + 自动打分 + 自进化逻辑 | 与具体业务解耦、可移植 |
| **Skill 的"REINS 域配置"** | 复用 osaka-mvp 现有 L1/L2 规则 + 现有字段表，作为该 Skill 的一个域预设 | 既保留 B 线已验证成果，又享受 Skill 的护甲与闭环 |

> 一句话：**Skill 是"发动机+变速箱"，osaka-mvp 的 REINS 规则是"已调好的这台车专属零件"**。发动机通用，零件专用。

### 2.3 与现有 `pdf` Skill 的关系
WorkBuddy 已有一个通用 `pdf` Skill（读/合并/转换 PDF）。本能力是**在其之上的"识别→结构化提取→自进化"工作流**，二者不冲突：底层仍可用 `pdf` Skill 做文件处理，本 Skill 负责"抽字段 + 提准闭环"。建议**独立新 Skill**（如 `pdf-structured-extract`），而非塞进通用 `pdf`。

## 3. 重点设计：持续自我优化闭环（勇哥最想要的能力）

> A 号机只有"静态护甲"（反例手写），B 线连护甲都没有。**"识别率不断提高"必须靠一个数据闭环来实现**，分三阶段成熟度。

### 3.1 闭环总图
```
PDF ──► 认字(L1/L2) ──► 选模型LLM提取 ──► 校验/落库
                                       │
            ┌──────────────────────────┘
            ▼
   错题本（Feedback Store）
   · 人工红字标注（勇哥在页面点"错"）
   · 双路交叉不一致
   · Pydantic 拒收 / 取值闸门驳回
   · 线上抽查 vs 真值
            │
            ▼
   周期性自进化
   · 自动把错题归类 → 增长 反例库 / 字典归一 / 视觉复核触发规则
   · 评测集(Golden Set) 自动打分（字段级精确/召回）
   · 改动前后对比，防过拟合
            │
            ▼
   回到"选模型LLM提取"（下一轮更准）
```

### 3.2 三阶段成熟度（对应落地 ROI）
| 阶段 | 内容 | 价值 | 工程量 |
|---|---|---|---|
| **P0 · 静态护甲** | 把 A 号机已验证的 6 层护甲（字典归一 + 反例 + GBNF schema + Pydantic + 三字段视觉复核 + 双路交叉）封装成可调用脚本/Skill | 立刻提准，复用 A 号机实证 | 小（搬运+适配） |
| **P1 · 反馈驱动提示词自进化** | 错题本沉淀；把"模型错在哪"自动归类进反例库/字典归一/视觉复核规则；每次改动用评测集回归 | "识别率不断提高"的**最小可闭环** | 中 |
| **P2 · 模型自进化** | 难例评测自动选最优模型/参数；可选本地微调（LoRA） | 上限再抬一截 | 大 |

### 3.3 度量"识别率不断提高"的关键（没有度量就没有优化）
- **评测集（Golden Set）**：从真实 PDF 中挑一批"已由勇哥/真值核过"的样本（建议起步 30–50 份，覆盖文字稿/扫描件/难例）。
- **自动打分**：字段级精确率/召回率（对照真值），按"关键数字字段（価格/面積/管理費/積立金/総戸数）"加权。
- **回归护栏**：任何提示词/规则改动，必须在 Golden Set 上跑前后对比；若某字段召回掉点 > 阈值，**禁止发布**该改动（防过拟合到个别错题）。
- **错题锚点**：每条错题保留"PDF 原文片段 + 模型输出 + 正确值"，新规则必须能在大样本回测中不拖累其他字段。

### 3.4 反馈来源（谁告诉模型"你错了"）
1. 勇哥在页面点的"红字/标错"（人工最高置信）。
2. 双路交叉验证不一致（自动中等置信）。
3. Pydantic 拒收 / 取值闸门驳回（自动高置信的结构错误）。
4. 线上抽查对比（抽样，低成本）。

## 4. 落地架构（Skill + osaka-mvp REINS 域）

### 4.1 Skill 目录（草案）
```
skills/pdf-structured-extract/
├── SKILL.md                  # 触发词/用法/工作流
├── extract_pipeline.py       # PDF→OCR→选模型LLM→结构化 编排
├── prompts/
│   ├── base_extract.md       # 系统提示词
│   ├── counterexamples.md    # 反例库（自动增长）
│   └── schema.json           # 输出字段 schema
├── model_router.py           # 本地Ollama ⇄ 云端(豆包/DeepSeek/Gemini) 统一接口
├── feedback_store.py         # 错题本（sqlite/jsonl）
├── eval_golden.py            # 评测集自动打分 + 回归护栏
└── domains/
    └── reins_osaka.py        # REINS 域预设：复用 osaka-mvp L1/L2 + 字段表
```

### 4.2 与 osaka-mvp 的接线点（不推翻现有代码）
- **L3 升级**：把 `core/ai_extract.py` 当前的"解说卡"升级为"带 schema+反例+交叉验证的严填表"，调用 Skill 的 `extract_pipeline`。
- **新增 L4 自进化**：在 `ai_pipeline.run_one` 后挂"错题采集 + 周期回归"，写 `feedback_store`。
- **模型选择器统一**：Skill 的 `model_router` 对接 `config.local.yaml` 的 `ai` 块（base_url/model/api_key），运行时切换本地/云端。
- **页面反馈入口**：详情页"红字标错"按钮 → 写错题本（勇哥已在 B 线有标红机制，扩展即可）。

### 4.3 模型选择策略（给勇哥的默认建议）
| 场景 | 默认模型 | 理由 |
|---|---|---|
| REINS 常规字段（规则已覆盖） | 不调 LLM，走 L1/L2 规则 | 免费、≈100%/95–98% 准 |
| 规则漏网字段 / 新 PDF 域 | 本地 `qwen2.5vl:3b`（Ollama） | 免费、3B 填表准 81.6%（A 号机实测） |
| 难例 / 三高风险字段复核 | 云端豆包/DeepSeek/Gemini（抽样） | 更准，但按"抽查"节流 |
| 自进化评测 | 同提取模型 + 真值比对 | 闭环内用 |

## 5. 实施分阶段（建议节奏）

| 阶段 | 任务 | 产出 | 依赖勇哥决策 |
|---|---|---|---|
| **P0** | 把 A 号机"OCR+LLM 填表+6 护甲"封装成独立可跑脚本/Skill，先能跑你那 336 份 | 通用提取能力可复用 | 是否先做通用 Skill 还是先接 osaka-mvp |
| **P1** | osaka-mvp L3 升级（严填表+护甲）+ 错题本 + 评测集打分 | B 线 LLM 层提准 + 闭环最小可用 | 反馈谁来做（人工 vs 自动） |
| **P2** | 闭环自动化（提示词自进化 + 回归护栏） | "识别率不断提高"兑现 | 闭环做到哪一级 |
| **P3** | 模型自进化（自动选模/本地微调） | 上限再抬 | 是否值得工程量 |

## 6. 开放问题（待勇哥拍板，讨论用）

1. **主提取链路以谁为主？**
   - 方案 A（像 A 号机）：LLM 为主填表，规则/OCR 只认字。
   - 方案 B（像 osaka-mvp）：规则为主填表，LLM 仅兜底。
   - **小巴建议：REINS 域用 B（已验证省钱高准）；全新的 PDF 域用 A（无规则时 LLM 顶上）。两者共存。**

2. **"持续优化"要做到第几阶段？** P0/P1 已有明确价值且工程量可控；P2/P3 工程量大，是否现在就规划？

3. **错题反馈谁来做？** 纯人工（勇哥红字）最准但慢；纯自动（交叉+拒收）快但可能误标。建议**自动采集 + 勇哥抽检确认**。

4. **模型边界？** 本地 qwen 免费但 3B 准 81.6%；云端更准但要钱。默认"本地为主、云端抽查"，是否同意？

5. **先做通用 Skill 还是先增强 osaka-mvp？** 小巴倾向**先做通用 Skill（P0）独立验证 336 份**，再回灌 osaka-mvp（P1），这样能力可复用、风险隔离。

## 7. 给勇哥的人话版总结

- **我们做了什么对比**：你那份经验（A 号机）和现在 osaka-mvp 的提取（B 线），"认字"部分完全一样且都验证过；"填表"部分一个是 LLM 为主、一个是规则为主，其实是互补的两套；你最想要的"模型自己越用越聪明"，两边现在都还没有。
- **我们建议什么**：把这套能力做成一个 **Skill（可复用发动机）**，REINS 的规则继续留在 osaka-mvp（专属零件），两者通过"REINS 域配置"接起来；并补上**错题本 + 评测集 + 自动打分**这个"自进化闭环"，让你的识别率真的能不断提高。
