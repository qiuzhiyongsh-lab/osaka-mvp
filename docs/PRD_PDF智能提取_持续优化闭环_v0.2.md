# PRD：PDF 智能提取能力（OCR 识别 + 选模型 LLM 提取 + 持续优化闭环）

> **版本**：v0.2（已吸收勇哥 5 项拍板决策，细化架构与 P1 交互）
> **日期**：2026-09-26
> **作者**：小巴（基于勇哥《本地 PDF 房源信息提取系统》经验 + osaka-mvp 现有提取链路对比 + 本轮决策整理）
> **目标读者**：勇哥（产品拍板人）+ 接手实现的工程师

---

## 0. 一句话总纲

勇哥想要的能力：**PDF 进来 → 文本/图形软件变成文字 → 丢给"当前选中的某个 LLM"做结构化识别 → 模型在"认错→被纠正→再识别"的闭环里不断自我优化、识别率越来越高。**

本稿结论：**把 A 号机"LLM 填表 + 6 层护甲"和 B 线"osaka-mvp 规则填表"打通共存，并补上两边都缺的"持续优化闭环"**；做成**可复用 Skill（发动机）**，REINS 规则留在 osaka-mvp（专属零件），本地软件与 WorkBuddy 识别服务通过**交接区**解耦回灌。

## 1. 现状对比：A 号机经验 vs osaka-mvp 现有提取链路

| 维度 | A 号机（本地 PDF 提取系统） | osaka-mvp B 线（ai_pipeline 三级降级） | 差异 / 互补点 |
|---|---|---|---|
| **认字层 L1** | PyMuPDF 抠文字层（≈100% 准、零成本） | `core/pdf_local_extract.py` 同款（部首归一/模糊认定/取值闸门） | **完全一致，都已验证，复用** |
| **认字层 L2** | Tesseract OCR（CPU、免费、数字稳） | `core/ocr_local.py` 同款（空格塌缩/复选框噪声/千分位修复/标签切分） | **完全一致，都已验证，复用** |
| **二次识别（填表）** | **LLM 为主填表员**：纯文本 → 本地 `qwen2.5vl:3b` → 59 列 Excel，schema 锁格式 | **规则正则为主**；LLM（`ai_extract.py` 豆包）仅 `min_fields` 未达才兜底，且只产"解说卡"不映射 59 列 | A=LLM 为主，B=规则为主，互补 |
| **质量护甲** | 字典归一 + 反例 + GBNF schema + Pydantic + 三字段视觉复核 + 双路交叉（6 层） | L1/L2 有取值闸门 + `ai_quality` 打分；**LLM 层无任何 schema/反例/交叉护甲** | A 的护甲是 B 线 LLM 层**完全缺失**的部分 |
| **持续优化闭环** | **无**（反例手写历史错题，不自动增长） | **无**（L3 每次独立调用，不积累经验） | **两边都没做——本次重点补** |
| **成本原则** | 主链路本地 0 成本；线上 AI 只抽查 | 本地规则免费；LLM 兜底按阈值触发 | 节流思路一致 |
| **模型选择** | Ollama 本地 `qwen2.5vl:3b`（可换 deepseek-r1:7b 复审） | 云端豆包（OpenAI 兼容，可换 Ollama/DeepSeek），由 `config.local.yaml` 的 `ai` 块切换 | 都已支持"选模型"，接口可统一 |

**关键洞察**：
1. "认字"两边已完全解耦且验证，复用即可，不重做。
2. "填表"是两条互补路线——B 线规则为主（REINS 已证明省钱高准），A 号机 LLM 为主（适合新域/漏网字段）。**最优解=共存、按域择优选**（已拍板）。
3. 勇哥最看重的"模型越用越聪明"，目前两边空白。本稿第 4–6 节专补。

## 2. 核心结论：做成 Skill（边界划清）

**做成 Skill（可复用能力），但 REINS 规则继续留在 osaka-mvp。**

| 归属 | 内容 | 理由 |
|---|---|---|
| **保留在 osaka-mvp**（不进 Skill） | `pdf_local_extract.py` / `ocr_local.py` 的 L1/L2 规则与 OCR 修复、REINS 59+ 字段表、取值闸门 | 已在 REINS 验证、与业务强绑定，是项目资产 |
| **做成 Skill（通用能力）** | ① "PDF→结构化提取+持续优化"编排 ② 提示词护甲（反例库/字典归一/schema/交叉验证）③ 模型路由（本地 Ollama ⇄ 云端，统一 OpenAI 兼容）④ 错题本 + 评测集 + 自动打分 + 自进化 | 与业务解耦、可移植 |
| **Skill 的"REINS 域配置"** | 复用 osaka-mvp L1/L2 + 字段表，作为该 Skill 一个域预设 | 既保留 B 线成果，又享 Skill 护甲与闭环 |

> Skill = 发动机+变速箱；osaka-mvp 的 REINS 规则 = 这台车专属零件。发动机通用，零件专用。

与现有通用 `pdf` Skill 不冲突：底层仍可用 `pdf` Skill 做文件处理，本 Skill（`pdf-structured-extract`）负责"抽字段 + 提准闭环"。

## 3. 已确认决策（本轮拍板，作为执行依据）

### 3.1 主提取链路以谁为主 → **按域择优选，两者共存**
- **REINS 域**：沿用 **B 线规则为主**（已验证省钱高准，≈100%/95–98%），LLM 仅兜底漏网字段。
- **全新 PDF 域**（无现成规则）：采用 **A 号机 LLM 为主**（认字后直接丢 LLM 填表）。
- 同一 Skill 内通过"域预设"切换主链路，不二选一。

### 3.2 持续优化做到第几阶段 → **做 P0 / P1 / P2，P3 规划先不做**
- **P0**（静态护甲）：搬 A 号机 6 层护甲，立刻提准。✅ 做
- **P1**（反馈驱动 + 可转人工）：错题本沉淀 + 评测集打分 + **人工抽检复核看板**（交互见第 5 节）。✅ 做
- **P2**（模型/规则自进化）：借用已识别信息做迭代——难例自动选最优提示词/规则，评测集回归护栏。✅ 做
- **P3**（模型自进化/本地微调）：工程量最大，**本轮只规划不实施**。

### 3.3 错题反馈谁来做 → **自动采集 + 勇哥抽检确认 + 明确试运行节奏**
- 反馈来源（自动采集，无需勇哥主动）：① 双路交叉不一致 ② Pydantic 拒收 / 取值闸门驳回 ③ 低置信度字段 ④（可选）线上抽查。
- 勇哥角色：**抽检确认**，而非逐条标错。前几日全量确认建反例库，稳定后切抽检。
- **试运行节奏**（见第 6 节）：先跑 1 天看量 → 每日迭代 → 3–7 天后转抽检 → 据识别率再定。

### 3.4 模型边界 → **本地为主、云端抽查；并明确"本地软件放哪 + WorkBuddy 回灌"**
- 默认**本地 Ollama `qwen2.5vl:3b` 为主**（免费，3B 填表准 81.6%，A 号机实测）；**云端豆包/DeepSeek/Gemini 仅抽查难例**。
- **架构意图（勇哥明确）**：本地软件负责"认字 + 规则 + 权威数据源"，**WorkBuddy 用自动方式做一次 LLM 识别，再把结果回灌本地软件**。
- 落地拓扑见第 4 节（本地软件与 WorkBuddy 识别服务通过"交接区"解耦）。

### 3.5 先做通用 Skill 还是先增强 osaka-mvp → **先 P0 通用 Skill 独立验证，再回灌**
- **P0**：先把通用 Skill 跑通，独立验证你那 **336 份** PDF（风险隔离、能力可复用）。
- **P1/P2**：再把 Skill 回灌 osaka-mvp（L3 升级 + 错题本 + 交接回灌）。

## 4. 落地架构：本地软件 ↔ WorkBuddy 识别服务（交接设计）

### 4.1 拓扑（解决"本地软件放哪 + WorkBuddy 怎么回灌"）

```
┌──────────────────────────────────────────────────────────┐
│  本地软件（勇哥机器：权威数据源）                            │
│  · 拥有 PDF 文件、SQLite DB、Ollama(qwen)                  │
│  · L1/L2 认字（PyMuPDF+Tesseract，复用 osaka-mvp）         │
│  · REINS 域：规则填表（B 线，已验证）                      │
│  · 新域/漏网：产出"待识别任务" → 写入【交接区·Inbox】       │
│  · 轮询【交接区·Outbox】→ 拉回结构化结果 → 合并入库         │
└───────────────┬───────────────────────┬────────────────────┘
                │ 写任务                  │ 读结果
                ▼                         ▲
┌──────────────────────────────────────────────────────────┐
│  【交接区】共享文件夹 / tdrive（与机器无关，解耦关键点）     │
│   · inbox/  ：{task_id}.json（PDF路径/文本/OCR/目标schema/  │
│              域预设/优先模型/优先级）                       │
│   · outbox/ ：{task_id}.result.json + done 标记             │
└───────────────┬───────────────────────┬────────────────────┘
                │ 监听                     │ 写回
                ▼                         ▲
┌──────────────────────────────────────────────────────────┐
│  WorkBuddy 识别服务（通用 Skill pdf-structured-extract）    │
│  · 自动化监听 Inbox → 调 extract_pipeline                  │
│  · LLM 识别（本地 Ollama ⇄ 云端抽查）+ 6 层护甲            │
│  · 评测集打分 / 错题本写入                                 │
│  · 结果写 Outbox（done）                                   │
└──────────────────────────────────────────────────────────┘
```

**"本地软件放哪"的推荐**：本地软件**留在勇哥本机**（必须本地访问 PDF + Ollama + DB，无法纯云端）。WorkBuddy 与本地软件**默认同机**时，交接区可用本机共享文件夹，直接文件握手；若将来分离到不同机器，交接区平移到 **tdrive / 云端共享盘**即可，协议不变（文件契约解耦，零改 Skill 逻辑）。

### 4.2 交接协议（文件契约，最小可用）
- **任务入队** `inbox/{task_id}.json`：
  ```json
  { "task_id":"...", "pdf":"路径或base64", "text":"L1文字层",
    "ocr":"L2 OCR 文本", "domain":"reins|generic",
    "schema":"目标字段表名", "prefer_model":"local|cloud",
    "priority":1, "created_at":"..." }
  ```
- **结果回灌** `outbox/{task_id}.result.json`：
  ```json
  { "task_id":"...", "fields":{...}, "confidence":0.9,
    "route":"local|cloud", "counterexamples":[...],
    "needs_review":false, "done":true }
  ```
- 本地软件轮询 Outbox，读到 `done` 即合并入库并清理任务；`needs_review=true` 的条目进第 5 节复核看板。

### 4.3 Skill 目录（草案）
```
skills/pdf-structured-extract/
├── SKILL.md
├── extract_pipeline.py       # PDF→OCR→选模型LLM→结构化 编排
├── prompts/{base_extract,counterexamples}.md + schema.json
├── model_router.py           # 本地Ollama ⇄ 云端 统一接口
├── feedback_store.py         # 错题本（sqlite/jsonl）
├── eval_golden.py            # 评测集自动打分 + 回归护栏
├── handoff.py                # 交接区 Inbox/Outbox 读写（4.2 协议）
└── domains/reins_osaka.py    # REINS 域预设：复用 osaka-mvp L1/L2 + 字段表
```

### 4.4 与 osaka-mvp 的接线点（不推翻现有代码）
- **L3 升级**：`core/ai_extract.py` 解说卡 → 带 schema+反例+交叉验证的严填表，调用 Skill `extract_pipeline`。
- **L4 自进化**：`ai_pipeline.run_one` 后挂"错题采集 + 周期回归"，写 `feedback_store`。
- **交接回灌**：本地软件侧新增 `handoff_watch.py`（轮询 Outbox 合并入库）；WorkBuddy 侧自动化监听 Inbox。
- **模型选择器**：Skill `model_router` 对接 `config.local.yaml` 的 `ai` 块（base_url/model/api_key），运行时切换。
- **页面反馈入口**：详情页"标错"按钮 → 写错题本（B 线已有标红机制，扩展即可）。

### 4.5 模型路由策略
| 场景 | 默认模型 | 理由 |
|---|---|---|
| REINS 常规字段（规则覆盖） | 不调 LLM，走 L1/L2 规则 | 免费、≈100%/95–98% 准 |
| 规则漏网 / 新 PDF 域 | 本地 `qwen2.5vl:3b`（Ollama） | 免费、3B 准 81.6% |
| 难例 / 三高风险复核 | 云端豆包/DeepSeek/Gemini（抽样） | 更准，按抽查节流 |
| 自进化评测 | 同提取模型 + 真值比对 | 闭环内用 |

## 5. P1「转人工」交互设计（勇哥重点要求）

> 目标：**系统自动干活、勇哥只抽检**，不被海量标错淹没。两类触发，一个看板。

### 5.1 何时转人工（两类触发）
1. **勇哥主动标错**：详情页 / 复核页每个字段旁有"标错"按钮 → 弹小修正卡，勇哥填正确值或确认 → 写错题本（**最高置信**）。
2. **系统自动路由复核**：当 ① 双路交叉不一致 ② Pydantic 拒收 ③ 置信度 < 阈值 ④ 域为新域首识别，条目自动进**待复核队列**，无需勇哥主动。

### 5.2 复核看板交互（核心）
- **列表模式**：每条待复核显示「来源 PDF + 页码 + 关键字段（価格/面積/管理費…）+ 冲突标记 + 模型置信度 + 风险等级（高/中/低）」。
- **单条复核**：左「PDF 页面缩略图」右「结构化结果表单」，冲突字段**高亮**；操作按钮：**确认正确 / 改为___ / 这条不要**。
- **批量模式**：「全部确认」「批量通过低危」「只看高危」；高危优先排前。
- **闭环回收**：确认/修正的条目自动归类 → 增长 反例库 / 字典归一 / 视觉复核触发规则 → 下一轮更准。

### 5.3 自动采集（勇哥零主动）
系统把"交叉不一致 + Pydantic 拒收 + 低置信"自动进队列并标注来源与冲突点；勇哥打开看板只需**抽检确认**，不要求逐条。每日看板顶部给出「今日待复核 N 条 / 已自动解决 M 条 / 识别率曲线」。

## 6. 试运行节奏（决策 3 落地）

| 阶段 | 动作 | 目的 |
|---|---|---|
| **Day 0 探测** | 跑 1 天真实数据（或 336 份子集）。统计：① 需 LLM 识别的 PDF/字段量 vs 规则已覆盖 ② 自动采集待复核量 ③ Golden Set 初始识别率 | 定基线 + 预估人工量 |
| **Day 1–7 每日迭代** | 每天自动识别 + 自动采集错题 + 勇哥每日抽检确认（前几日全量确认建反例库）；看识别率曲线 | 建反例库、快速提准 |
| **Day 3–7 切抽检** | 待复核量稳定后，从"全量确认"切"抽检"（每天抽 10–20% 或只抽高危），其余按现有规则/上轮结果落库 | 降人工成本 |
| **之后** | 据识别率决定是否进 P2（提示词/规则自进化） | 数据驱动决策 |

> 没有度量就没有优化：任何提示词/规则改动，必须在 Golden Set（起步 30–50 份真值样本）跑前后对比，单字段召回掉点 > 阈值则禁止发布（防过拟合）。
