## 0. 结论先行

1. 软件今天暴露**两类真问题**：单轮爬虫跑到 REINS 维护时段仍不收兵（round_overflow）；昨夜事故后本地与线上房源数据漂移（data_drift）。两类都属实、都该修。
2. **二巴的理解大方向正确，但有一处事实性硬伤**——它称维护页识别 `_check_maintenance`「已失联、grep 无匹配」，实测该函数在 `core/crawler.py:2355` **有定义且被 6+ 处调用**。因此它的 G3「恢复失联兜底」开错了方向，本 PRD 已修正为「强化既有维护识别 + 时钟兜底」。
3. **升级分两层**：本地程序（爬虫/调度/推送/同步）必须升；线上站点（对账端点/ingest 幂等/selfcheck 自检）也需要升，但**线上部署受 2104 死命令制约**——2104 不能 redeploy（发布记录已删），干净通道只有 v100（见《v100 立为生产》方案）。

- 可靠兜底必须是**时钟驱动**（任何发请求前用 `_now_tz()` 判窗口），不依赖页面内容；
- 既有 `_check_maintenance` 应**强化**（扩大关键字/检测空表单/维护遮罩），作为第二道防线，而非「从零恢复」。

## 2. 问题域 A：单轮越界（round_overflow）—— 纯本地升级

**根因（修正后）**：
- `scheduler.py:341` 的窗口门禁只在「发车前」判一次，轮次一旦启动，**组内每个动作不再回头看时钟**；
- 组内失败是「组级隔离」（`_GeoFailed` 只跳组），无轮级熔断 → 8 组把同样的失败演了 8 遍；
- 单轮无总时长上限 → 第 7 组 1h57m、今日第 4 轮 5h50m；
- `_check_maintenance` 存在但因页面内容判定太窄而未触发，且它本就不是时钟兜底。

**需求（EARS，交 RD，全部本地）**：
- **A1【核心】轮级软截止 + 每动作前时钟门禁**：`round_deadline = min(round_start + max_round_minutes, window_end_jst)`；在**每组开始、每组内循环、阶段 B 补详情、番号検索**等任何发请求动作前，用 `_now_tz()` 判窗口 → 超时就优雅收尾（当前组处理完再停，禁止半条强杀），标记 `truncated/window_expired`，`resume` 续跑接管剩余。
- **A2 维护页识别强化**：保留并扩展 `crawler.py:2355 _check_maintenance`——增加「空検索表单 / 维护遮罩 / 非预期空白页」判定，与 `SessionExpired` 并列；作为 A1 时钟兜底的补充，而非唯一防线。
- **A3 轮级同质失败熔断**：同轮内 `_GeoFailed/MaintenanceDetected/同类 TimeoutError` 连续 ≥ N（默认 3）次 → 中止本轮剩余组，合并输出一条汇总日志（禁 8 份重复堆栈）。
- **A4 单轮/单组时长上限**：`crawl.max_round_minutes`（默认 60）、`crawl.max_group_minutes`（默认 20）；超限停详情/PDF，留待下一轮（列表级结果照常入库）。
- **A5 故障归因纠偏**：输出「疑似页面改版」前先排除维护/网络/会话失效；附「本节已成功 N 次、最后成功 HH:MM:SS」，维护时段禁止建议改 `use_saved_condition`。
- **A6 单轮可观测性**：每轮开始/结束输出 `本轮时限 <HH:MM:SS JST>`、已用时/剩余组数、收兵原因。

> 注：以上全是**本地 8765 跑的爬虫/调度代码**，不涉及线上站点，本地升级即可生效。

## 3. 问题域 B：本地↔线上数据漂移（data_drift）—— 本地 + 线上

**根因**：单向增量推送 + 无对账 + 无内容级自检 + 无失败补偿。昨夜事故后线上回滚到 v1.9.100 半成品、失联 6.5h，增量推送补不回回滚窟窿（H1/H2/H3 待 F1 对账验证）。

**需求（EARS，交 RD）**：
- **B1【P0】线上对账端点 + 本地对账脚本**：`GET /api/reconcile`（X-Publish-Token，token 端点，机器安全）返回番号摘要；本地 `tools/reconcile_push.py`（dry-run 默认，`--push` 才重推）。二巴已写 session 版原型 `diag_local_vs_remote_20260928.py`，本项把它升级为 token 版并加自动重推。→ **需线上部署**。
- **B2【P0】推送失败补偿队列**：增量推送 5xx/超时 → 本批番号写入 `data/push_pending.json`，下轮优先重推；pending 非空时日志头部显「待补 N 条」。→ **纯本地**。
- **B3【P1】ingest 幂等加固**：确认 `web/app.py:485 STORE.upsert_many` 已是 upsert；B3 重点改为**验证 `properties.property_no` 唯一索引 + 去重迁移**，杜绝重复行（线上总数反而多 292 的疑点）。→ **需线上部署（唯一性保证）**。
- **B4【P1】selfcheck 内容级自检**：`/api/selfcheck` 增 fav.js 字节数 + 关键标记计数 + DB 行数 + **版本回退检测**（running < disk → drift=true 并双通道告警），消灭「drift:false 假绿灯」。→ **需线上部署**。
- **B5【P1】线上恢复标准动作写进发版 SOP**：宕机/平台恢复/重发布后，OPS 立即 selfcheck + 对账 + 缺口>0 则 `force_full_push.py` 全量重推。
- **B6【P2】员工回流失败熔断**：连续失败 ≥ 5 次 → 间隔 60s 拉长至 10min，同因合并输出。→ **纯本地**。
- **B7【P2】轮次超长治理**：承接 A4（`max_round_minutes=60`）。
