# 36 · 历史时点查询 vs 最新信息：全网调研与产品设计方案（调研备忘）

> **文档性质**：调研 + 产品设计建议（**非 PRD**，未动代码、未拍板落地）。
> **发起**：勇哥 2026-10-01 —— 关于"按日期查询时，如何既尊重用户查询意愿、又保证给客户的是相对最新的信息"的经典产品难题。
> **核心例题**：一套房 9/1 录入、9/15 变更、9/30 再变更。用户查"9/15"时应展示什么？
> - 方案A（展示最新）→ 与查询时间点不符
> - 方案B（只展示 9/15 当时内容）→ 用户拿不到最新信息
> 行业如何平衡这两点？

---

## 一、全网调研结论（4 类来源，带出处）

### 1. REINS 后台本身（日本官方流通系统，仲介専用）
- **REINS 是单一"当前记录"模型**：每套房源在系统里是一份**始终最新**的主记录；价格/状态变更时原地更新，并打 `変更年月日`（变更日）。
- **日期筛选 = 发现（Discovery），不是"时光倒流"**：仲介按 `登録日 / 更新日` 过滤，是为了"找出**在某日新登録或发生变更**的房源"——命中的是"变动节点"，显示的仍是该房**当前最新**内容。
- 变更履歴作为**独立可查的层**存在（系统对业者提供变更历史），但不替代主记录的"最新"。
- 公开侧（REINS Market Information / RMI）只披露**成交价**（非挂牌价），且 10 万円 粒度、屋齢 ±2 年——说明官方也把"时点数据"限定在"成交参考"用途，**不用于代表在售房源当前状态**。
- **出处**：reins.co.jp；dovetail.co.jp（REINS 实时更新/统一库）；media.ina-gr.com（RMI 只公开成交价）；realestate-kyoto.com / japandirealestate.com（REINS vs MLS 结构差异）。

### 2. 日本门户（SUUMO / LIFULL HOME'S / At Home）
- **主视图永远是当前挂牌**：这些站只展示在售房源的**当前**价格与信息，不做"时点回放"。
- **被诟病"信息过时/残留"**：note 一文指出门户信息"只在仲介上传那一刻是新的"，出现"已成交却仍在售""照片是几年前"等问题——反面印证"主信息必须标最新 + 给变更信号"的重要性。
- **价格变更履歴作为叠加层**：LIFULL 有"真価格页"把历史改定价格数据**叠加**在当前房源之上（subger.com 描述）。即"主信息最新 + 历史可展开看"。
- **出处**：note.com/juutaku_honne429（门户信息滞后批评）；lifull.com 市场报告；subger.com（LIFULL 价格履歴叠加层）；ga-tech.com.tw（门户清单）。

### 3. 欧美（MLS / Zillow / Renx 等）
- **"Listing history / Days on market / price drops"是主记录之上的独立层**：MLS 字段含 listing history、DOM、照片、状态变更；平台提供"价格历史""降价提醒"作为**叠加在当期挂牌上的时间线**。
- **日期筛选用于"可比成交"（Comps），与在售房源本身分离**：评估师用"近 12–24 个月成交"做锚点，明确"历史成交是锚、当前挂牌是决策输入"。
- **出处**：renxhomes.ca（历史挂牌/降价提醒/真 DOM）；vestaba.com.au（数据滞后→当前市场才是决策依据）；henti.lv / visionaryecho.com（历史成交 vs 当前挂牌，时点数据用于 comparable analysis）；bentoncountyar.gov（评估值时点快照 vs 当前市场）。

### 4. 金融/官方登记（时点数据的"正确打开方式"）
- **历史 = 锚点（context），当前 = 决策输入**：爱尔兰房价登记、美国估税都强调"登记价是某时点的成交证据，不代表今天值多少；当前价值要由专业估价+市场调整得出"。
- 这给了设计哲学层面的支撑：**时点数据不该"替代"当前信息，而应作为"对比/背景"呈现**。

## 二、行业共识（提炼）

> **没有一家主流产品用"把旧版本当主信息"来解决这个矛盾。**
> 行业的统一解法是 **"三层分离"**：

| 层 | 做什么 | 行业对应 |
|---|---|---|
| **匹配层（尊重查询意愿）** | 日期筛选决定"房源是否出现在结果里"（按 登録日/更新日 命中变动节点） | REINS 按登録/更新日发现；MLS 按成交日做 Comps |
| **信息层（永远最新）** | 卡片/详情**主区永远展示当前最新字段** | 所有门户 + REINS 主记录均如此 |
| **提示/历史层（可见偏差）** | 当"命中日期 ≠ 最新变更日"时，明确提示"你按 X 命中，但它已变到 Y"；并给可展开的时间轴看全过程 | LIFULL 价格履歴叠加层；MLS/Zillow price history |

**所以勇哥的例题答案不是"二选一"，而是"分离"**：
- 用户查"变动截至 9/15" → 房源因 9/15 的变更**命中**（匹配层满足查询意愿）；
- 卡片/详情**主区显示 9/30 的最新价与信息**（信息层保证最新）；
- 卡片上亮一个 chip：「⚠ 按 2026-09-15 筛选命中；该房 09-30 已再次变更，以下为最新」；
- 点进详情 → F5 时间轴把 **9/15 那个节点高亮标"命中节点"**，用户一眼看全"9/08 首登 → 9/15 变更 → 9/30 再变更"。

## 三、映射到我们系统（现状摸底，非新造）

| 需求层 | 我们已有 | 差距 |
|---|---|---|
| 匹配层（双日期命中） | `reg_date_iso` / `chg_date_iso` 双日期 OR 过滤（store.py 查询口径） | ✅ 已具备 |
| 信息层（永远最新） | `detail_json` 只保留**最新一份** | ✅ 天然就是最新 |
| 提示层（命中≠最新） | 无 | 🔴 **需新增**：命中日期 vs 最新变更日 的偏差 chip/横幅 |
| 历史层（时间轴） | `changes` 10221 行（字段级 old→new）、`snapshots` 42168 行、`property_history` 778403 行 | ✅ PRD-35 **F5** 正在做（时间轴）；本调研建议**给命中节点加高亮** |
| 回放层（看 9/15 当时内容） | `property_history` 按日存 price/change_date/status；`snapshots` 存 content_hash | 🟡 **仅当该日有抓取记录才能真回放**；老房源完整字段自 F5.1 基线机制上线起才完整（D10 限制，不得伪造） |

→ **本调研的落地成本极低**：匹配层/信息层已有；只需在 PRD-35 的 F5 基础上补两件事——
1. **F5+**：时间轴对"查询命中日期"节点做高亮（"此节点即你筛选命中的变动"）；
2. **F6（新，轻量）**：查询/列表卡片上加「命中日期 ≠ 最新日」偏差提示 chip + 详情页顶部横幅。

## 四、给勇哥的 PM 建议（结论先行）

1. **采用"三层分离"作为我们查询页/详情页的默认设计哲学**——不提供"把旧版本当主信息"的模式（行业无 precedents，且会造成"已成交/已变价却显示旧值"的误导，正是 SUUMO 被骂的点）。
2. **日期筛选只管"命中"，不管"回放"**：用户查 9/15，得到的是"在 9/15 及之前发生过变动的房源集合"，但每条都给最新信息 + 偏差提示。
3. **偏差提示是必须做的**（F6）：否则用户会困惑"我查 9/15 为什么给我 9/30 的价"。这是平衡两诉求的"粘合剂"。
4. **"看 9/15 当时内容"作为可选回放**（F5+ 的 as-of 视图），仅在有该日快照时开放；无数据的诚实标注"该日完整字段未留存"。
5. **这完美复用 PRD-35 的 F5 时间轴**：F5 把"首次→每次变更→当前"串成线，本调研只是给它加"命中节点高亮"+"偏差提示"两个小增量，不必另起炉灶。
