## 三、关键技术决策：为什么没按原方案的「按 id 直接 REPLACE」

原方案 §5.2 写的是「按 id 幂等 upsert（`INSERT OR REPLACE`）」。**执行前实测把它证伪了**：

```
customer_properties  id=28：2104=(客户3, 300133659888)  ≠  v100=(客户3, 300140894949)
customer_properties  id=29：2104=(客户3, 300140894934)  ≠  v100=(客户2, 300140894949)
```

两个库的 `id` 各自 autoincrement 生长 ⇒ **撞号 ≠ 同一个实体**。REPLACE 的语义是「有冲突先删后插」，会把 v100 独有的这 2 条客户↔房源关联**静默吃掉**。

改为 **业务键合并**（`web/employee_api.py::_merge_rows`）：

- 同 id 且同业务键 → 就地 UPDATE
- 业务键命中唯一行 → 合并进那一行（**保留目标 id**，源 id 记入重映射表）
- 目标无此业务键 → INSERT（源 id 被别的实体占用时让自增分配新 id）
- 外键 `tag_id` / `customer_id` 在 id 重排时自动重映射

结果 = **源 ∪ 目标，两端一行都不丢**，且支持 `dry` 预演与整体事务回滚。
