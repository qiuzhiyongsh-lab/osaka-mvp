## 一、调研结论：顶级上线部署工程师怎么学、怎么迭代

### 1.1 能力模型 · Google SRE「发布工程（Release Engineering）」四大哲学
来源：Google SRE Book《Release Engineering》/《Building Secure & Reliable Systems》。

| 哲学 | 内核 | 对本项目的映射 |
|---|---|---|
| **Self-Service（自助）** | 工程师能自助发布，不依赖"发布管理员"手工放行 | 我们已经做到：一条 `sync_to_publish.py` + 同目录 `deploy` 即可自助发版，无需平台人工介入 |
| **High Velocity（高频）** | 小步快跑，高频发布降低单次爆炸半径 | 我们目前仍以"大版本"为主（v1.9.x 跳跃）；下一步应推进"改完即发、小步提交" |
| **Hermetic Builds（密闭构建）** | 构建环境与产物可复现、可溯源 | 我们靠 git tag + checkpoint 快照保证可溯源；构建物 = 发布包 `app_local/`，已是确定性拷贝 |
| **Enforcement（强制）** | 策略靠工具强制，不靠人记 | 我们靠 `8 门禁` + `online-release-engineer` 红线 + `incident-log` 预防 checklist 强制 |

> 关键洞察：**能力迭代的第一性原则 = 把"人容易忘/容易手抖"的事，变成"工具强制 + 文档沉淀"。** 这正是我们 skill 化路线的正确性证明。

### 1.2 版本发布怎么做 · 分支与 cherry-pick 策略
来源：Google「Trunk-Based Development」+《Release Engineering》。

- **main 收所有提交**，发布从 main 拉 `release/X.Y.Z` 分支，**发布分支永不回并 main**（避免把"已发布但需稳定"的状态反向污染开发线）。
- 发布后发现线上 bug → **只在该 release 分支 `cherry-pick` 修复**，绝不把未发布的开发提交混进来。
- 每次发布打 **annotated tag `vX.Y.Z`**，tag 是"可回溯的发布锚点"，不是装饰。

> 本项目现状：只有 `main` 单线 + checkpoint 提交，尚无 tag / release 分支 → **这正是 #558 要补的机制**（见 `Git发布与备份机制_2026-09-27.md`）。

### 1.3 渐进式交付（Progressive Delivery）
来源：Martin Fowler / LaunchDarkly 实践。

| 模式 | 作用 | 我们能否用 |
|---|---|---|
| **Blue-Green（蓝绿）** | 两套环境，秒级回滚 | 平台单沙箱，不适用；但我们的 `selfrestart` + 同目录 deploy 已实现"零删除切换" |
| **Canary（金丝雀）** | 先放 5% 流量，观察再全量 | 单实例站点不适用流量切片；可改为"先发到备用 app（`osaka-mvp-v100`）验真机，再切主系统" |
| **Feature Flags（功能开关）** | 部署与发布解耦，关开关即回滚 | **立即可用**：我们已有 `config` 开关体系（如抓取计划开关），可做"新功能默认关、验证后开" |
| **Shadow / Dark launch** | 新代码影子运行不影响用户 | 抓取层可"影子跑一轮"对比新旧解析结果再上线 |

> 落地建议：**短期用「备用 app 金丝雀 + 功能开关」替代蓝绿**；中长期把"抓取/解析"这类高风险改动改为影子验证。

### 1.4 无罪责复盘（Blameless Postmortem）+ 5 Whys
来源：Google SRE《Postmortem Culture》。

- 事故复盘**不追责任**，追"系统在哪个环节没挡住"。
- 用 **5 Whys** 逐层追问到根因（不是"谁犯的错"）。
- **Action Items 必须有 owner + 截止日期**，否则复盘 = 写给自己看。
- 多因素事故用 **Fault Tree（故障树）** 补充 5 Whys 的线性盲区。
- **SEV 分级**避免"每次小事故都写长篇 postmortem"的疲劳。

> 本项目已内建：BUG 诊断强制 5WHY（`dev-release-governance`）、`incident-log.md` 案例库、沟通红线。**缺口 = 缺 SEV 分级与 action item 追踪表**。

### 1.5 能力如何"不断迭代" —— 学习飞轮
综合上述，顶级工程师的能力迭代是一个闭环飞轮：

```
踩坑 → 写进案例库(incident-log) → 提炼成预防 checklist → 工具/红线强制 → 下次 deploy 自动核对
   ↑                                                                         ↓
   ←←←←←←← 定期蒸馏(把重复建议变默认动作、删过时结论) ←←←←←←←←←←←←←←←←
```

三个学习来源：**① 自己的事故库（最高频）② 业界标准（SRE Book / 大厂工程博客）③ 同行评审（四角色 / 多 Agent 红队）**。
