## 一、卡顿根因（5WHY · 硬证据）

日志源：`osaka-mvp/data/logs/server.log`

| 层 | 现象 / 证据 |
|---|---|
| 现象 | 12:07–12:08 抓取遇 REINS 详情页 `TimeoutError` 一波（共 **7 次**，行 18920–18933）；勇哥在后台页卡顿，点返回回搜索页恢复。 |
| 1 | 本地 8765（`serve.py`）以 `threaded=True` 起 Flask，REINS 抓取 `SCHED` 后台线程**与 Web 服务同进程**（serve.py:100/105/145）。 |
| 2 | 12:07 抓取撞上 REINS 站点响应慢 → Playwright 等超时重试，期间持续 `内联补详情` 写库。 |
| 3 | `core/store.py` 连库 **`journal_mode=delete`（非 WAL）** + `busy_timeout=5000`（实测 PRAGMA）。SQLite 默认回滚日志模式下，**写事务会阻塞所有读**。 |
| 4 | 抓取密集写占住 SQLite 写锁 → Edge 在后台页发出的查询请求被挂起（等锁最长 5s）→ 页面"卡顿"。 |
| 5 | 用户点返回键 = 浏览器取消/关闭挂起的 XHR → 请求不再等待 → 回到搜索页（轻量查询）立即成功 ⇒ 看似"恢复"。 |

**根因一句话**：单进程内「抓取写」与「Web 读」抢同一 SQLite 锁，且库未开 WAL ⇒ 抓取风暴时 Web 查询被拖死。

## 二、出现此类问题后如何处理（当前可立即做）

- **用户侧（你）**：卡顿时直接点返回或刷新到搜索页即可（挂起请求被取消，不影响数据）；不要在卡顿页反复点。
- **运维侧（AI/我）**：
  1. 看 `data/logs/server.log` 是否在同一时刻有 `TimeoutError` / 密集 `内联补详情`；
  2. 确认是否处于抓取轮次（REINS 24 次检索的某一步）；
  3. 抓取是后台线程、会自动续跑/退避，一般无需手动干预；若持续卡，可重启 8765（双击 `start_mvp.bat`）。
- **注意**：**绝不**由 AI 去 `taskkill` 8765（那是你双击启动的进程，铁律）。

## 三、PM 视角：系统性预防（结合"网页下载/日期口径"既有内容）

已检索项目内相关既有设计：`date_caliber`（any/registration/change/download，search.html:197 / store.py:1796,1915）、双口径（顶部"今天 N 条"=下载口径 vs 查询页默认=平台口径，MEMORY.md"数据链路/口径"）、`busy_timeout`、`journal_mode`。

| 优先级 | 措施 | 说明 | 风险/前提 |
|---|---|---|---|
| 🔴 P0 | **开 WAL** | `PRAGMA journal_mode=WAL`：读不阻塞写，根治锁竞争卡顿。 | DB 级改动，会产 `-wal/-shm`；备份需先 checkpoint。**待勇哥确认**。 |
| 🟠 P1 | 抓取连续超时自动退避 + 限并发 | 12:07 那波 7 次超时说明 REINS 慢时应指数退避、降并发，别硬砸。 | 低，纯爬虫逻辑。 |
| 🟠 P1 | Web 查询加超时 + "加载中/重试"提示 | 前端 `AbortController` 取消旧请求；后端查询设超时，避免无提示假死。 | 低。 |
| 🟡 P2 | 后台页加"系统状态"指示 | 显示"抓取进行中/空闲"，让卡顿有解释而非神秘。 | 低。 |
| 🟡 P2 | 长期：抓取与 Web 进程分离 | 抓取独立 worker，彻底不抢 Web 的 CPU/锁。 | 架构改动，需评估。 |

> 结论：最划算的是 **P0 开 WAL**（一次性，直接消除根因）。
