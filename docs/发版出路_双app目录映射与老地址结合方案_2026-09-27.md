# 发版出路：双 app 目录映射 与「老地址 + 新程序」结合方案

> 日期：2026-09-27 ｜ 责任：大巴（本工作区 2026-09-11-09-50-22）
> 目标：把**最新程序（v1.9.100 完整版）**结合到**最早发布的地址 osaka-house-v2**上。

---

## 一、结论（先行）

1. **官方机制**：发布目标 = 本地目录在**服务端**记录的 app。从**同一目录**重新发布 = **覆盖该 app、保留原链接**；只有目录换成新 app 才会换地址。（依据：内置 sites 技能文档 + 公开资料）
2. **当前死结**：目录 `osaka-house-publish/app_local` 的服务端记录已被切到 **L8M4**，而平台侧把 L8M4 **标记为已删除** → 每次 deploy 都返回 `sites_deploy_app_deleted`，卡死。
3. **老地址仍在**：osaka-house-v2 = app **C65E82**，在「设置→数据管理→应用」列表里仍显示「已发布」，但其沙箱 `8bcd…` 已 **404**（下线/失效），且目录已不再指向它。
4. **本地程序是最新最完整的**（v1.9.100，fav.js 30199B，F2/F6 齐全）。"结合不上"**不是文件问题，而是服务端目录映射问题**。
5. **客户端改不动**：改本地 `.genie`、deploy 时显式传 appId、跨工作区复制记录——均已被实验证明**无效**（工具读的是服务端映射）。

## 二、关键证据

### 1. 部署历史（同一目录 `osaka-house-publish/app_local`）
| 时间 | appId | sandboxId | 链接 |
|---|---|---|---|
| 09-24 09:26 ~ 09-27 10:02（12 次） | `wbapp_C65E82…` | `8bcd…` | **osaka-house-v2** ✅ |
| 09-27 10:25 | `wbapp_L8M4…` | `5963…` | 2104034688228982784… |
| 09-27 12:45 | `wbapp_L8M4…` | `5963…` | 5963…子域 |

→ 目录原本稳定绑定 **C65E82（osaka-house-v2）**，**10:25 那次 deploy 把它切到了 L8M4**。

### 2. 沙箱探活
- `8bcd…`（C65E82 / osaka-house-v2 后端）→ **404**（死）
- `5963…`（L8M4 后端）→ **200**（活，跑半残版）

### 3. deploy 工具返回原文
```
sites_deploy_app_deleted
  appId = wbapp_L8M4tyzslRfAA0IWoy29Iz （已删）
  提示：该目录之前发布到的 app 已删除，重发不可能，只能新建 app
```

### 4. 同名双 app 的事实
两个 appId（C65E82 / L8M4）**指向同一个 localDir**（`…\osaka-house-publish\app_local`）。这正是官方文档警告的"一个项目在重复发布中被创建了多个 appId"的情形。

## 三、出路（按推荐排序）

### 方案 1｜先做「判定 deploy」（安全，绝不变地址）
从 `app_local` 目录再 deploy 一次，观察工具把目标落到谁：
- 若落到 **C65E82** → 最新程序直接覆盖回 **osaka-house-v2**，成功。
- 若仍报 **L8M4 已删** → 坐实服务端映射卡在 L8M4，转方案 2 或 3。

**安全性**：目录已有 app 记录，工具**不会**自动新建 app（deleted ≠ 无记录）。故本次 deploy 只会"覆盖已有 app"或"报错"，**不会新建、不会换地址**。

### 方案 2｜平台侧修正映射（保地址·根治）
请平台把 `app_local` 目录的服务端映射**改回 C65E82**（或恢复 L8M4）。服务端映射只有平台能改，这是唯一"稳保 osaka-house-v2 地址"的根治路径。

### 方案 3｜新建 app（换地址）
在「设置→数据管理→发布的应用」由**你手动新建**一个 app → 目录绑定新 app → deploy。
- 代价：**换新地址**（osaka-house-v2 永久拿不回）
- 违反你此前"绝不换地址"的死命令，仅作兜底。
