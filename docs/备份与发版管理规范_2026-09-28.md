## 2. 备份频率是怎么定出来的（定方案的逻辑）

### 核心公式

> **备份频率 = f(变化速度, 丢失代价, 备份成本)**
> 但**先要过 3-2-1 关**——**位置决定"备份成不成立"，频率只决定"丢多少"。顺序不能反。**

### 四步法

**Step 1 · 按「不可再生性」分级**（不是所有数据都配同样的备份成本）
先回答"这东西丢了，能不能再拿到"。拿不回来的，钱再少也要高频 + 异地；能重抓的，低频就够。

**Step 2 · 用 RPO / RTO 反推频率**
- RPO（能承受丢多少数据）→ 决定**频率**
- RTO（能承受多久恢复）→ 决定**备份放哪、如何组织**（全量/增量、解压即用还是需重建）

**Step 3 · 用「变化速度」校准**
- 变化快 + 不可再生 → 高频（员工数据）
- 变化慢 + 可再生 → 低频（PDF 全量基线）
- 频率上限 = 变化速度；**超过变化速度的备份是纯浪费**

**Step 4 · 用 3-2-1 检验**
3 份副本 / 2 种介质 / 1 份异地。**没过这一关，频率再高也是假备份。**

### 两个关键洞察（本系统最该记住的）

**洞察 1 — 同一块盘上的 23 份快照 ≠ 23 份备份。**
`.backups/` 里 23 份 jproperty 快照看起来很安全，但它们的**存活相关性是 1.0（同生共死）**：硬盘一挂、机器一丢、C 盘写满，全部归零。这是最典型的假安全感。**异地副本数目前 = 0。**

**洞察 2 — 全系统性价比最高的一笔保险，现在几乎没买。**
`employee.db` 只有 **106 KB**，但它承载的是「员工自己建的客户/收藏/标签」——**丢了永久没了，而且线上 2104 才是权威源**。每小时备份一整年也不到 1 GB，成本近乎为零。现在它只是"跟着 checkpoint 顺带快照"，且没有异地。

| 层 | 资产 | 体积 | RPO | 频率 | 保留策略 | 异地 |
|---|---|---|---|---|---|---|
| **热** | `employee.db` | 106 KB | ≤ 1 小时 | **每小时** | 30 天 | ✅ 每日 |
| **温** | `jproperty.db` | 98 MB | ≤ 4 小时 | 每个抓取轮次后 + 每日全量 | 7 天本地 / 30 天异地 | ✅ 每日 |
| **温** | `ai_pdf_store.db` | 8.3 MB | ≤ 1 天 | 每日 | 30 天 | ✅ 每日 |
| **温** | PDF **增量**（只备新增） | 每天几十个 / 几 MB | ≤ 1 天 | 每日增量 | 永久（单份） | ✅ 每日 |
| **冷** | PDF **全量基线** | 3.1 GB | ≤ 30 天 | **每月 1 次** | 3 份滚动 | ✅ 每月 |
| **随** | 代码 | 4.5 MB | 1 次提交 | 每次 commit 推双远端 + 每日兜底 | 永久 | ✅ **已达标** |
| **密封** | `config.local.yaml` + 凭据 | 极小 | 变更即备 | 变更时 + 每周 | 5 份 | ✅ 加密后进异地 |

### 异地传输量估算
每日异地 ≈ employee(106KB) + jproperty(98MB) + ai(8.3MB) + PDF增量(≈几MB) ≈ **110 MB/天**；
SQLite 压缩率通常 3–5 倍 → 实际上传 **约 25–35 MB/天**。对网盘 / 对象存储完全无压力。
**PDF 的 3.1 GB 不走每日**：走「每日增量 + 每月全量基线」，避免把带宽和空间打爆。

## 4. 发版：保证「版本确定性」

### 现状盘点

| 项 | 状态 |
|---|---|
| 版本号单一源 `core/version.py` | ✅ 已有 |
| 漂移自检 + `/api/selfcheck` + 页脚告警横幅（v1.9.58） | ✅ 已有 |
| 发布单一通道 `sync_to_publish` | ✅ 已有 |
| 同目录 redeploy 保地址（地址死命令） | ✅ 已有 |
| **每次发布打 tag** | ❌ 仅 `v1.9.100` 一个 |
| **发布包可回溯到确切 commit** | ❌ 线上是生成物 `app_local/`，非 git 检出，**不知对应哪个 commit** |
| **发布包归档（可确定性回滚）** | ❌ 无 |
| **发布前强制校验工作树干净** | ❌ 无（脏树同步出去 = 无法复现） |

### 版本确定性四条铁律

| # | 规则 | 落地方式 |
|---|---|---|
| **V1** | **每次发布必打 tag** | `git tag v1.9.101` → 推 GitHub + GitLab 双远端 |
| **V2** | **发布包内嵌 `BUILD_INFO`** | `sync_to_publish` 生成 `BUILD_INFO.json`（版本号 + commit sha + 构建时间 + 是否脏树） |
| **V3** | **线上 `/api/ping` 暴露 version + sha + build_time** | 与已有漂移自检打通 → 一查就知道"线上跑的到底是什么" |
| **V4** | **发布包归档 + 发布前强制干净树** | 每次发布 tar 到 `.backups/releases/`，脏工作树直接拒绝同步 |

**回滚确定性** = 归档包 + tag + 同目录 redeploy ⇒ 可确定性回到任一历史版本，且**不会重派子域**（守住 2104 地址死命令）。

## 6. 附：可直接落地的执行要点

- **备份手段**：SQLite 用 `VACUUM INTO`（原子、不停机、产出紧凑副本），不要直接 `cp` 正在写的库。
- **命名规范**：`<资产>_<YYYYMMDD>_<HHMMSS>_<短sha>.db`，与现有 `.backups` 风格一致。
- **保留策略**：本地 7 天滚动（控住 1.7 GB→约 700 MB），异地 30 天。
- **异地目标**：优先选**已有连接**的网盘/对象存储，避免新增维护面。
- **红线**：凭据永不入库、永不进 git；异地包必须加密。
