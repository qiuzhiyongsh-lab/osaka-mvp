## 问题 A · 固定域名 osaka-house-v2 永久 404 丢失

**现象**：`osaka-house-v2.app.workbuddy.host` 变死链，勇哥想"拿回域名"已不可能（2026-09-27 实测 + 平台文档确认）。

**5WHY**
1. 为什么 404？→ 自定义域名仅在"新建 app 时分配"；删掉底层 app 后域名被平台释放。
2. 为什么删底层 app？→ 为"刷新代码"走删应用→重部署路径（误判）。
3. 为什么以为只能删？→ 没去读发布工具官方文档确认"重发布是否保留链接 / 是否刷新代码"。
4. 为什么没读文档？→ 把 session 旧结论（"沙箱复用=不重建"）当铁律，没核实工具 schema。
5. **根因**：地址变更的唯一触发点 = **删应用**；标准 `workbuddy_sites_deploy` 工具**无任何 reclaim/绑定已释放自定义域名的参数**（见 `sites/SKILL.md`："An app is found → publishing overwrites it, keeping its link"——只复用已记录的 shareLink，无法 reclaim 已释放域名）。

**证据**
- `sites/SKILL.md`："Publishing reuses the target app's recorded sandbox... share link stays the same and the content behind it is replaced"；无 reclaim 自定义域名参数。
- 实测：删 `osaka-house-v2` 后，`wbapp_C65E82hYRMCjxjcwW2Ph1E` 底层虽仍活（数字子域 `8bcd2d43`、v1.9.94、独立库），但自定义域名已 404。

**整改项（已落地）**
- ✅ 铁律：绝不主动换/回收子域；子域是用户资产，只有勇哥本人说"换地址"才可动（`online-release-engineer` 红线 2）。
- ✅ 发布只走"同目录重部署"，地址永不因发版改变。
- ⏳ 域名已无法拿回；如未来确需固定品牌域名，路径是"新建 app 时分配"（不可逆、需勇哥拍板），非重部署能解决。

## 问题 B · 僵尸 app 并存 + 数据分叉

**现象**：线上出现多 app 拓扑——主系统 `L8M4`（2104，v1.9.100，接同步/员工权威）、旧 `C65E82`（osaka-house-v2 底层，v1.9.94，独立库）、备用 `vN7DtOaDBJW4muPFZxjbxl`（osaka-mvp-v100，v1.9.100，库分叉）。

**5WHY**
1. 为什么多 app？→ 几次"删了重发/另起炉灶"留下历史 app 未清理。
2. 为什么另起炉灶？→ 误以为旧 app"坏了/代码上不去"需新建。
3. 为什么误以为坏了？→ 没用 selfcheck 带 cache-buster 验证 running_version，被缓存旧值误导。
4. 为什么有数据分叉？→ 各 app 独立库，发版重建按各自发布包灌库。
5. **根因**：缺乏"单一权威 app + 同目录重部署"纪律，把"发版"和"新建 app"混为一谈。

**证据**：`MEMORY.md` App 拓扑章节（2026-09-27 实测厘清三 app 状态）；`director_audit.py` 已改 ping 指向 2104 主系统。

**整改项（已落地）**
- ✅ 决策：保留 2104（L8M4）为**唯一主系统**长期使用；C65E82、vN7DtOaDBJW4muPFZxjbxl 仅作备用/不接同步。
- ✅ 发版严格"同目录重部署"，不新建 app → 不再制造僵尸。

## 问题 C · 被迫多轮 UI「删除应用」操作（破坏性甩给用户）

**现象**：让勇哥亲手进 UI 删应用做发版，前后 3 轮；把本可用接口/脚本绕开的"刷新代码"问题，降级成"要用户做破坏性操作"。

**5WHY**
1. 为什么逼删？→ 1.9.99 代码没上线（deploy 复用旧沙箱，running_version 停在旧版）。
2. 为什么没刷新？→ 当时没意识到"同目录 deploy 已刷新代码"，或 deploy 后未 selfrestart。
3. 为什么降级给用户？→ 没先穷举"不删也能刷新"的通道（selfrestart 接口当时未实现/未用）。
4. 为什么没通道？→ v1.9.100 之前缺"非破坏性刷新代码"机制。
5. **根因**：① 缺 selfrestart 通道；② 违反"不可逆操作不甩给用户"（dev-release-governance 红线）。

**证据**：`online-release-engineer` SKILL.md §二.1 红线 1/3；`incident-log.md` INC-01。

**整改项（已落地）**
- ✅ v1.9.100 实现 `POST /api/admin/selfrestart`（带 X-Publish-Token）→ 进程原地 execv 重启加载新代码，**零删除、零地址变更、零 UI 操作**（见 `Git发布与备份机制` SOP ⑥）。
- ✅ 发版 SOP 首步即"同目录 deploy + 必要时 selfrestart"，永不进 UI 删应用。

## 问题 D · 子域被平台重派（数字子域）

**现象**：同目录 deploy 复用 sandboxId（数据不丢、代码刷新），但平台**可能重派数字子域**；sandboxId 恒不变。换域名后本地 `config.local.yaml::publish.endpoint` 与 `tools/*` 硬编码旧域名会静默打空。

**5WHY**
1. 为什么重派？→ 平台在同目录 deploy 时可能重新分配数字子域（非 sandboxId）。
2. 为什么打空？→ 本地 endpoint / 工具硬编码了旧子域，没跟着更新。
3. 为什么硬编码？→ 早期图省事直接写死域名，未抽成单一配置源。
4. 为什么没发现？→ 推送/回流静默失败，无断言告警。
5. **根因**：缺乏"换域名后 3 处联动 + grep 扫残留"的强制检查。

**证据**：`MEMORY.md`「换域名后必同步的 3 处」；`director_audit.py` 已改指向 2104。

**整改项（已落地）**
- ✅ 换域名后必同步 3 处：`config.local.yaml::publish.endpoint` / `tools/_verify_release.py::BASE` / `director_audit.py` ping 地址。
- ✅ 改完 endpoint 后 `grep -rn` 扫 `tools/` 无残留硬编码旧域名（INC-06 预防项）。

## 问题 E · 反复用"需要吗"追问被批（沟通红线失守）

**现象**：今晨反复把小事当选择题甩回（被批 5 次），违反"禁止收尾追问"红线。

**5WHY**
1. 为什么追问？→ 对"可逆/增值/有流程的小事"不自信，习惯确认。
2. 为什么不敢直接做？→ 没区分"不可逆（需确认）"与"可逆小事实做"。
3. 为什么没区分？→ 沟通纪律未内化成默认动作。
4. 为什么没内化？→ 红线是文字，未形成"收尾只给已做/现状/可选下一步"的肌肉记忆。
5. **根因**：缺"收尾纪律"的强制模板——每次交付结尾固定输出「已做 / 现状 / 可选下一步」，不反问。

**证据**：`dev-release-governance` 沟通红线；`user_memory` 收尾纪律（2026-09-27 确立，跨项目适用）。

**整改项（已落地）**
- ✅ 收尾模板固定为「已做 / 现状 / 可选下一步」，禁用"需要…吗？"收尾。
- ✅ 所有工作完成后单独回一句"所有的工作已完成。"

## 问题 F · 员工数据险丢（删应用会丢线上权威库）

**现象**：线上 2104 是员工业务数据（收藏/客户/标签）权威源；若走"删应用→重建"，`employee.db` 不在发布包 → 数据丢失。

**5WHY**
1. 为什么险丢？→ 删应用 = 删沙箱 = 删线上库；`employee.db` 不在发布包。
2. 为什么不在发布包？→ 发布包只含 `site_data.json / accounts.seed.json / ai_pdf_store.db`，刻意不含员工业务库（避免被种子覆盖）。
3. 为什么没通道补救？→ 当时"保数据重建 SOP"依赖删后重灌，本身脆弱。
4. 为什么脆弱？→ 无"本地→线上"推送通道（employee_data_sync 单向只拉不推）。
5. **根因**：把"发版"和"数据生命周期"错误绑定——发版本不该碰数据。

**证据**：`MEMORY.md`「删应用仍会丢员工数据（但现已可避免）」；`#556` 已全量导出线上员工库 JSON 留底（counts 与本地 EXACT MATCH，证伪备份完整性）。

**整改项（已落地）**
- ✅ 铁律：发版 = 同目录重部署 + selfrestart，**绝不删应用** → 员工数据永不因发版丢失。
- ✅ 数据上线唯一通道 = `force_full_push.py`（`/api/ingest`），与发版解耦。
- ✅ 本轮已留底：`.backups/db/emp_online_2104_full_20260927_2137.json`（favorites=13/customers=8/customer_properties=24/property_tags=34/customer_tags=14/tags=16）。
