## 0. 先回答第 0 问：软件"在后台跑"到底指什么？

这是本轮唯一一个**纯答疑、无需改动**的问题，先讲清楚，避免后面重复纠结。

### 0.1 你看到的那两行日志是什么

```
GET /api/logs?since=2   每 2.5 秒一次
GET /api/ping           每 4 秒一次
```

这两个都**不是后台任务**，而是**你浏览器里开着的那个网页**在轮询：

| 接口 | 谁在调 | 频率 | 作用 | 关掉网页后 |
|---|---|---|---|---|
| `/api/ping` | `base.html`（所有页面） | 每 4 秒 | 心跳：连不上就在页面顶部亮红色横幅「本地服务已停止」，而不是给用户看 `Failed to fetch` | **立即停止** |
| `/api/logs?since=N` | 概览/抓取设置页的状态盒子 | 每 2.5 秒 | 拉最新几行日志贴到页面上（`since` 是"我已有的行号"，只增量取） | **立即停止** |

**结论：把浏览器标签页关掉，这些日志立刻就没了。** 它跟"要不要对外展示数据"没有任何关系。

### 0.2 真正"常驻后台"的只有两样

| 常驻物 | 是什么 | 能不能停 |
|---|---|---|
| **Flask 服务进程**（8765，`start_mvp.bat` 那个黑窗口） | 提供网页和 API | **不能停**——停了网页就打不开。空闲时 CPU≈0，内存几十 MB |
| **调度器线程**（`Scheduler._loop`） | 决定"什么时候自动抓一轮" | 可以停（点「停止自动更新」），但**停了也不省什么**，它 99.9% 的时间在 `sleep` |

### 0.3 和「日本时间 23:00–07:00」的关系 —— **是相关的，而且已经做好了**

23:00–07:00 这八小时，是 REINS 自己**做维护、不对外提供数据**的时间。软件里的对应机制是**运行时段（`schedule.window`）**：

```
config.yaml → schedule.window: { start: '07:00', end: '23:00' }
```

- 调度线程到点会发现"不在窗口内"，打印 `当前不在运行时段…等待 N 分钟后继续`，然后**睡到次日 07:00**，期间**一次都不抓**。
- 这正是你截图里那行 `当前不在运行时段` 的来源。
- 所以：**夜里软件确实"在跑"，但什么都不做**——不发请求、不碰 REINS、不占用带宽。

### 0.4 所以你的两个选项分别对应什么

| 你的判断 | 对应的操作 | 建议 |
|---|---|---|
| ①「如果相关，我认为没必要去跑」 | 点「停止自动更新」→ 调度线程退出，夜里彻底静默 | **不推荐**：这条线程夜里本来就不干活；而且第二天要记得手动开，容易忘 |
| ②「如果不相关，可以看情况」 | **什么都不用做** | ✅ **推荐**。它只在你开着网页时产生那两条轮询日志；关掉网页即停 |

> **一句话**：夜里"跑着"的只是一个睡着的线程 + 一个待命的网页服务；不想看到那些日志，**关掉网页标签页**就行了，不需要动设置。

## 4. 逐项设计（R2 – R10）

### R2 · 更新间隔改为「分钟制」

**问题**：现在最小单位是小时（固定 1/2/4/8 小时；随机 1.0–3.0 小时），粒度太粗。

**设计**（按已拍板 Q1：**只保留随机模式，去掉「定时」**）：

| 现在的输入 | 改成 |
|---|---|
| 自动更新方式：① 定时（1/2/4/8 **小时**）② 随机（1.0–3.0 **小时**） | **去掉模式下拉**；只留 **随机下限 / 随机上限（分钟）** 两个数字框，如 `20` – `60` |

**配置变更**（`config.yaml → schedule`）：

```yaml
schedule:
  enabled: true
  mode: random              # 固定 random（界面不再暴露模式选择）
  random_min_minutes: 20    # 新增：随机下限（分钟）
  random_max_minutes: 60    # 新增：随机上限（分钟）
  random_min_hours: 1.0     # 兼容保留（老配置仍可读；分钟键缺失时按 ×60 换算）
  random_max_hours: 3.0     # 兼容保留
  window: { start: '07:00', end: '23:00' }
```

**边界规则（重要，会写进代码）**：
- 最小间隔 **≥ 5 分钟**（低于 5 分钟等于高频轰炸 REINS，违背"像人"原则 → 直接夹到 5）。
- 随机模式若 `上限 < 下限`，自动对调。
- 抓一轮本身耗时可能超过间隔（用户机器上一轮约 25–40 分钟）→ **间隔从"上一轮跑完"开始算，不会重叠**（现有 `_loop` 已经是这个语义，保持不变）。

**验收**：设 `30` 分钟 → 页面显示"随机间隔 20–60 分钟"；`/api/schedule` 返回分钟字段；下一轮时间 = 跑完时间 + 随机值。

### R5 · 测试 / 正式下载的功能划分

| 按钮 | 位置 | 条件来源 | 抓取量 | 落库 | 变化 |
|---|---|---|---|---|---|

**"正式下载"的合并规则**（这是本方案的关键设计）：

```
用户点【正式下载】
  ├─ 若 ④ 里没动过任何条件（全默认） → 等价于老的「真实下载」：按 config 保存条件跑
  └─ 若 ④ 里有条件（选了種別/種目/日期…） → 等价于老的「指定日期下载」：
        在 exclusive 内跑（暂停当天轮次），跑完自动恢复
```

两条路径共用 `run_round_options()`，只是 `opts` 的来源不同。**界面上只有一个「正式下载」按钮**，避免你面对两个功能相近的按钮不知点哪个。

### R6 · 限制条件三层设计

#### (a) 核心条件（必选，默认已按你的口径预置）

| 组 | 可选项 | 默认 |
|---|---|---|
| **物件種別** | 売一戸建 / 売マンション / 売土地 | 按 `config.search.kinds` 预选 |
| **物件種目 · 一戸建** | **新築戸建、中古戸建**（**只给这 2 项**） | 全选 |
| **物件種目 · 公寓** | **新築マンション、中古マンション、新築タウン、中古タウン**（**前 4 项**） | 全选 |
| **物件種目 · 土地** | 土地 | 全选 |
| **日期** | ☑ 当天登录（`登録年月日` = 今天）<br>☑ 当天更新（`変更年月日` = 今天） | **两个都勾** |
| **土地権利/借地権** | 所有権のみ | **勾选**（R6-c） |

> REINS 的「基本条件」原生就是 **2 行 ×（種別 + 種目1 + 種目2）= 一次检索最多 4 个種目**。
> 所以「公寓前 4 项」正好**一次检索填满**（新築マンション + 中古マンション / 新築タウン + 中古タウン），
> 一户建 2 项同理。**日期若两个都勾 = 两次检索**（登録一次、変更一次），结果合并去重。

**关于"当天更新 + 当天登录"的实现**：
- 现值 `date_type` 单选（登録年月日 / 変更年月日），改为**复选框两个都能勾**；
- 勾一个 → 跑 1 次检索；勾两个 → 跑 2 次检索，按 `物件番号` 去重合并；
- `date` 默认**今天**（日本时间）。

#### (b) 可选条件（**默认全部不勾选**）

| 可选条件 | 控件 | 默认状态 |
|---|---|---|
| 区（大阪市） | 下拉 | ☐ 不勾 → 输入禁用 |
| 价格（万円） | 上/下限 | ☐ 不勾 |
| 面积（㎡） | 上/下限 | ☐ 不勾 |
| 沿線名 | 文本 | ☐ 不勾 |
| 駅名 | 文本 | ☐ 不勾 |

交互：**每个可选条件前面一个复选框，勾上才启用后面的输入框**（未勾 → 置灰、不参与检索）。
另加一个「展开可选条件」折叠开关，默认折叠，保持页面清爽。

#### (c) 补充项

| 项 | 默认 | 逻辑 |
|---|---|---|
| 土地権利/借地権 = 所有権のみ | **勾选** | 勾上 → 检索前点选该 radio；**页面上找不到该项时自动退回「指定なし（全部）」**，只告警不报错（沿用现有 `_tick_ownership_only` 的降级策略） |

### R8 · 查询页状态保留

**现象**：查完一次 → 点「房源对比」→ 再回「房源查询」，条件被清空回默认（当天 + 不限種目）。

**设计**：把筛选条件存进浏览器 `localStorage`（键 `qstate`），进入页面时回填。

| 要保留的 | 说明 |
|---|---|
| 关键词、日期、區、種目多选、價格/面積上下限、每頁條數、頁碼 | 全部回填 |
| 不清楚的 | 「刷新」按钮 = 显式重置为默认并清空 `qstate`（避免用户想重置却重置不了） |

**注意边界**：若用户因为"想回到默认"才切页面的，可能觉得"怎么又是旧条件"。因此**在筛选区显示一枚「当前为上次查询条件 · 点此重置」的提示条**，一键回到默认。

### R10 · 展开区字段名四语言化

**问题定位**（已查实）：`search.html → fillDetail()` 第 471–481 行，详情页额外字段**直接把原始英文键名当标签显示**：

```js
Object.keys(d).forEach(function(k){
  ...
  h += '<div class="df"><span class="dk">'+esc(k)+'</span>...   // ← esc(k) = trade_type / management_fee …
});
```

所以你会看到 `trade_type`、`management_fee`、`repair_fund`、`broker` 这类英文。

**设计**：`compare.html` 里已经有一份现成的字段小词典（`JP2KEY` → 四语言 i18n），本轮把它**提到公共位置**（`web/static/fieldmap.js`），供**查询页展开区 / 对比页 / 详情页**三处共用：

```
原始键（detail_json 的英文或日文键）
   → JP2KEY 命中 → t('xf.xxx')  四语言
   → JP2CN 命中  → 中文
   → 都不命中    → 保留原键（并记入"待补词表"，绝不用网上扒的译名）
```

**你强调的"不要使用从网上扒下来的字段名称"** → 落实为一条硬规则：
> **所有字段名一律来自本项目的 i18n 字典（`i18n.js` 的 `xf.*` 系列），由我们按业务含义自己定义；禁止照抄 REINS 官方译名或第三方网站的译法。**
> 未收录的键**宁可显示原键 + 标注「待补译」**，也不擅自翻译。
