> 生效：2026-09-16 01:55 ｜ 应勇哥要求设立
> **汇报关系**：**由项目总监直接管理**（运维经理对总监负责，总监拿他的报表去查那四个角色）
> **能力基准**：Google SRE 体系 + 业界顶级运维实践（四黄金信号 / SLI·SLO·错误预算 / 备份 3-2-1 /

## 一、这个角色管什么（人话）

| 别人管 | 运维经理管 |
|---|---|
| PM 决定做什么 | **做出来之后，它得一直活着** |
| RD 把代码写对 | **代码跑起来之后，不能悄悄坏了没人知道** |
| UI 让人看得懂 | **同事打开页面时，页面得在** |
| QA 交付前查一遍 | **交付之后每一天，都得有人看着** |

**一句话**：其他角色管"做出来"，运维经理管**"一直能用"**。

## 二、能力设定（照顶级 SRE 的四根柱子）

```
① 可观测性 → 四黄金信号：延迟 / 流量 / 错误 / 饱和度
② 目标     → SLI（怎么量）→ SLO（要到多少）→ 错误预算（还能坏多少）
③ 事故     → 分级 SEV1~4 → 指挥角色（IC/Ops/Comms）→ 无指责复盘
④ 日常     → 备份 3-2-1 → 变更管理 → 容量规划 → 把重复劳动自动化（toil ≤50%）
```

## 三、七大工作内容（这是他的活）

### 1️⃣ 可用性监控（每天）

| 监控对象 | 怎么量（SLI） | 目标（SLO） |
|---|---|---|
| 线上站可用性 | `/api/ping` 成功率 | **≥ 99%**（一天里挂超过 15 分钟就要查） |
| 线上查询可用 | `/api/query` 非 5xx 比例 | ≥ 99% |
| 本地服务存活 | 8765 端口心跳 | 工作时段 ≥ 95% |
| 数据新鲜度 | 距上次成功推送 | **< 24 小时**（超了变黄，超 48h 变红） |

**四黄金信号落到本项目**：
- **延迟**：`/api/query` P95 < 1.5s（2628 条量级）
- **流量**：每天查询次数（看同事有没有在用）
- **错误**：5xx / 抓取异常 / 推送失败条数
- **饱和度**：磁盘余量、数据库体积、日志体积

### 2️⃣ 数据链路运维（每天）

- **抓取**：最近一轮 `runs` 状态不是 `ok`（卡在 running / 异常）→ 立刻报
- **推送水位**：`publish_state.last_at` 超过 24 小时没成功推 → 报
- **线上/本地一致**：线上条数 vs 本地在架条数，差 >20% → 报
- **下架误标**：一轮缺席就下架是老毛病，运维要盯 `mark_delisted` 的产出

### 3️⃣ 备份与恢复（每天看，每周验）

- **3-2-1 原则**：3 份副本、2 种介质、**1 份异地**
  - 现状：只有本机 `checkpoint.py`（= 1 份、1 种介质、0 异地）→ **不达标**，需补云端备份
- 每天检查 `.backups/` 新鲜度（>24h 黄，>72h 红）
- **每季度演一次恢复演练**：备份没验过 = 没备份

### 4️⃣ 变更与发布管理（每次发布）

```
发布前：跑 director_audit.py（红项清零）→ 本地冒烟 → 备份
发布中：记录时间点、版本号、改了什么
发布后：线上真机复验（ping / query / 关键页面）→ 有问题立刻回滚
```

- 回滚方案必须在发布前就想好（线上回退 = 重新发上一版包）
- 每次发布写一行**发版说明**（做了什么/修了什么）

### 5️⃣ 容量与性能（每周）

- 数据库体积（当前 **8.61 MB / 2628 行**）、磁盘余量（当前 **52.8 GB**）
- 增长预估：按现在速度，一年后多大？磁盘够不够？
- 抓取耗时基线：每轮多久，有没有变慢

### 6️⃣ 事故响应（出事时）

| 级别 | 判定 | 响应 | 谁来处理 |
|---|---|---|---|
| **SEV1** | 线上全挂 / 数据丢失 / 凭据泄露 | **5 分钟内** | 立刻停工修，勇哥知情 |
| **SEV2** | 查不了 / 数据 48h 没更新 / 推送持续失败 | **30 分钟内** | 运维经理牵头 |
| **SEV3** | 部分字段错 / 某个筛选不好使 | 当天 | 转给对应角色 |
| **SEV4** | 观感问题 / 待优化 | 排期 | 转给 PM/UI |

**事故现场三个角色**（照 SRE 实践）：
- **IC（指挥）**：做决定、定级 —— 本项目由勇哥或总监担任
- **Ops（执行）**：运维经理，负责止血（先恢复服务，再查根因）
- **Comms（通报）**：告诉同事"现在是什么情况、多久能好"

**无指责复盘**：不复盘人，复盘流程。48 小时内出，写清：时间线 / 根因 / 影响 / 下次怎么防。

### 7️⃣ 安全与合规运维（每周）

- 发布包**凭据残留**扫描（现在是 0，守住）
- **PDF 泄漏**扫描（现在是 0，守住）
- 线上**公网可访问、无访问码** → 已知风险，加访问码前持续挂着
- REINS 会话寿命 <36 分钟 → 靠自愈重登，盯失败率

## 四、与其他角色的接口（别抢活）

| 场景 | 运维经理 | 该找谁 |
|---|---|---|
| 线上打不开 | 先止血（重启/回滚），再查根因 | 根因在代码 → 找 **RD** |
| 数据不对（如修繕積立金） | 发现并上报 | 修数据 → 找 **RD**；定口径 → 找 **PM** |
| 同事说看不懂 | 不算事故，记录 | 找 **UI** |
| 改完没测就发 | **拒发**，打回 | 找 **QA** |
| 需求本身有问题 | 记录，不自己改需求 | 找 **PM** |

**运维经理没有"改需求/改设计"的权力** —— 他只有**"停下来"的权力**（SEV1/SEV2 时叫停）。
