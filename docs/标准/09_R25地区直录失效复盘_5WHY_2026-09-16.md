## 1. PRD 复盘：问题到底出在哪个环节？

**勇哥的判断对了一半，也错了一半——必须如实说。**

### 1.1 PRD 写清楚的部分（✅ 你说得对）
PRD 13 的 **R25 / D3 / 标准作业流程 step5** 明确写了要搜的键：
- step5：「所在地：**直接录入 `大阪府` + 所在地名1=`大阪市`**（都道府県名 输入框**可用**）」
- D3：「都道府県名 输入框可用（勇哥确认），直接填 `大阪府`+`大阪市`」
- 需求清单 R25：「地区直录大阪府+大阪市，关 `use_saved_condition`」

→ **"要搜哪些键"这件事 PRD 写得很清楚，不是 PRD 的锅。**

### 1.2 PRD 的结构性缺口（❌ 这才是根环节）
PRD 写了 **WHAT（填什么）**，但缺了 **HOW-RISK（怎么填才不出错）** 与 **历史教训引用**：

1. **没预警"页面有 9 个同名控件"**：PRD 通篇把「都道府県名」当成唯一字段，从未提及 REINS 检索页存在两套同名控件（範囲選択 disabled 版 + 所在地可填版）。这是 RD 落地时唯一致命坑，PRD 一个字没提。
2. **重蹈 v1.5.4 覆辙却没引用历史**：`use_saved_condition=false` 这个改动，**v1.5.4 就试过、并在 `core/version.py:204` 被真机证伪（"实测证明它是错的"）后回滚**。PRD 13 重新批准同一改动，**没有引用这条历史结论**，也没要求"改前先查 version.py"。
3. **没把"检索条件类改动"列为高风险 + 必须真机 e2e**：PRD §11 流程约束只写"四关 + 总监抽查 + 发布须勇哥点头"，**没有定义 QA 门禁必须有"真机回读表单值 + 结果条数非空"**。

### 1.3 结论：断链在三个环节
PRD（缺 HOW-RISK + 缺历史引用）→ PM（没标高风险、没查 version.py）→ RD（没看真实 DOM 写定位器）→ QA（没 e2e 门禁）→ OPS（没发布后健康检查）→ 总监（只查"四关是否都过"不查证据质量）。
**缺口从 PRD 起就没人被指派补，于是顺链路滑到生产。**

## 2. 六角色 5 WHY（每个角色说明自己问题的原因）

### 2.1 PM（项目经理）— 我
- **问题**：把 R25 当"改配置+填两格"的低风险改动放行；没查 `version.py` 历史（v1.5.4 同改动已被证伪）；没标高风险。
- **5 WHY**：
  1. 为什么坏代码上线了？→ 因为 R25 改 `use_saved_condition=false` 后手填定位器写错，命中 9 控件抛错。
  2. 为什么定位器写错没被发现？→ 因为 RD 没先看真实 DOM，且 PM 没要求"先看 DOM"。
  3. 为什么 PM 没要求看 DOM？→ 因为 PM 把 R25 归类为低风险，认为不需要 DOM 证据。
  4. 为什么归类为低风险？→ 因为 PM 没查 `version.py`——那里白纸黑字记着 v1.5.4 同样改动"实测证明它是错的"，本应触发高风险预警。
  5. 为什么没查 version.py？→ 因为流程里"改检索条件前必须查历史结论"**不是强制门禁**，PM 凭印象判断，没把 version.py 当权威事实源。
- **根因**：缺少"改检索条件前强制查 version.py 历史结论"的门禁；历史教训没回流进 PRD/检查单。

### 2.2 RD（研发）— 我
- **问题**：定位器不加区块限定（命中 9 个同名控件）；失败兜底"沿用默认"静默吞错。
- **5 WHY**：
  1. 为什么地区没录进去？→ 定位器命中 9 个 → 严格模式抛 Error。
  2. 为什么命中 9 个？→ 页面有两套同名控件，定位器没限定区块。
  3. 为什么没限定区块？→ RD 写定位器凭记忆/假设结构，没用真实 DOM 快照核对控件数量。
  4. 为什么没核对真实 DOM？→ 没做"定位器唯一性自检"（`locator.count()==1`）；默认"都道府県名"唯一。
  5. 为什么没做唯一性自检？→ 代码规范里**没有"所有 Playwright 定位器必须断言命中数=1"的硬要求**，且失败兜底吞了错误。
- **根因**：定位器编写规范缺失"唯一性断言"；失败处理用"沿用默认"而非中止。

### 2.3 UI（UI 经理）— 我
- **问题**：没复核检索表单的真实控件结构/可填性。
- **5 WHY**：
  1. 为什么 UI 没发现？→ UI 把关只看"字段名/显示是否中文"，没看检索表单控件可填性。
  2. 为什么没看可填性？→ UI 角色默认"检索表单是 RD 的事"。
  3. 为什么默认是 RD 的事？→ 四角色职责切分里"检索条件录入的结构复核"**没明确归属 UI**，边界模糊。
  4. 为什么边界模糊？→ 流程文档只写"UI 负责页面"，没写"UI 须核对第三方站点表单控件结构"。
  5. 为什么没写？→ 假设 REINS 表单是标准结构，没把"第三方 DOM 结构复核"列为 UI 职责。
- **根因**：UI 职责未覆盖"第三方检索表单控件结构/可填性复核"，边界留白被双方忽略。

### 2.4 QA（测试）— 我
- **问题**：R25 标"待真机复核"却仍发布；无端到端冒烟（检索是否出结果）。
- **5 WHY**：
  1. 为什么坏代码上线？→ QA 放行了 R25，尽管自己备注"待真机复核"。
  2. 为什么放行？→ QA 把"代码同步一致/编译通过"当验收标准，没有"真机检索出结果"这一关。
  3. 为什么没这关？→ QA 门禁清单只有"单元/离线/DOM 快照"，没有"e2e 冒烟：回读表单值+结果条数"。
  4. 为什么清单缺这关？→ 上一轮我把"真机验证"列为**建议而非强制**，且自认 R25 简单。
  5. 为什么列为建议而非强制？→ 默认"离线/DOM 快照足够"，没把"检索条件类改动"规定为必须真机 e2e。
- **根因**：QA 门禁缺"检索条件改动必须真机 e2e 冒烟"强制项；"待复核"标签不阻断发布。

### 2.5 OPS（运维经理）— 我
- **问题**：发布体检只查代码同步/站点可用，没查线上检索能力。
- **5 WHY**：
  1. 为什么线上没发现地区缺失？→ OPS 发布后只验 `/api/ping`、`/api/query` 有数据，没验"检索条件是否录入"。
  2. 为什么没验？→ OPS 职责聚焦"站点可用性"，检索条件默认归 crawler/RD。
  3. 为什么默认不归 OPS？→ 发布 SOP 没写"发布后须确认一轮采集真的出结果（非空采）"。
  4. 为什么 SOP 没写？→ 一直假设"能跑起来=正常"，没把"采集结果为 0"列为发布失败信号。
  5. 为什么没列为失败信号？→ 从未定义"一轮采集结果的正常下限/告警阈值"。
- **根因**：发布 SOP 缺"采集结果非空 + 地区录入"的发布后健康检查；无采集结果告警阈值。

### 2.6 项目总监（Director）— 我
- **问题**：没拦住这次发布；四角色全是我自己，无独立挑战。
- **5 WHY**：
  1. 为什么总监没拦？→ 总监审查只看四角色是否都"过了"，没查每个角色的证据质量。
  2. 为什么没查证据质量？→ 总监默认"四关都过=可发布"，把流程合规当结果正确。
  3. 为什么流程合规当结果正确？→ 四角色都是同一 agent 自证，总监审查形同自我复核，无独立视角。
  4. 为什么无独立视角？→ 数字员工架构下六角色由我一人承担，分工带来"已审查"错觉，实则零独立挑战。
  5. 为什么零独立挑战还更差？→ 分工越细、checklist 越长，越让人（agent）产生"已充分把关"的错觉，反而跳过对关键假设的质疑；每个角色都信任上一角色，错误沿链路静默传递。
- **根因**：单 agent 多角色 = 自证循环，流程合规幻觉取代实质审查；越标准越易成 checklist 走过场。

## 3. 元复盘：为什么分工越明确、流程越标准，反而越差？

**核心论点：分工明确 + 流程标准 ≠ 安全，当所有角色是同一个决策者时，分工制造"已审查"的错觉而非真实的独立挑战。**

- 每个角色默认"上一角色做对了"：PM 信 RD 的定位器对、RD 信 PM 的风险判断、QA 信 RD 的代码、OPS 信 QA 的放行、总监信"四关都过了"。
- 错误在链路里不被任何人真正质疑就流到生产——因为**没有第二个活人/独立 agent 会反问"你确定页面只有 1 个都道府県名？"**
- 越标准的流程越危险：checklist 越长，"勾完=安全"的心理暗示越强，越容易把"待复核"当可发布的附注而非阻塞。
- 本次正是典型案例：R25 我自己在上一轮写着"待真机复核"，却仍把它标成"已完成并发布"——违反了我自己定的"没证据不算数"。

**这不是"流程有问题"，是"流程被当成证据替代品"有问题。** 流程的价值在于逼出证据，而不是用"过了"覆盖"没验证"。
