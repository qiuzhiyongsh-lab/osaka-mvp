# 新增物件自动推送 · 产品方案 v0.1

> 大阪房源查询系统（本地版）· 产品方案稿（**仅方案，暂不实现**）
> 版本 v0.1 ｜ 2026-09-12 ｜ 目标：把「新增 / 变更」的房源，按订阅规则自动推送到**日本、中国香港、中国澳门、中国大陆**同事的日常工具里。

---

## 0. 一句话结论

**做一个「事件 → 规则 → 渠道适配器」的推送中台**：抓取端每检出「新增 / 降价 / 变更」就发一条事件，规则引擎按「谁、关心什么」匹配订阅，再由若干**渠道适配器**分别投递到各地同事最顺手的工具里。**不是只选一种推送方式，而是"一个内容、多个出口"**——因为四地同事的工具习惯完全不同，强行统一到一个 App 一定会有人不用。

**落地节奏建议：先做「邮件 + 企业微信群机器人」保底覆盖（零成本、零审核），再按地区补 WhatsApp（港澳）、LINE（日本）。**

---

## 1. 为什么做（目标 & 场景）

| 维度 | 现状 | 想要的结果 |
|---|---|---|
| 时效 | 数据落本机库，要**人主动**打开网页 / Excel 才看得到 | 新盘 / 降价**自动**推到手机，被动也能收到 |
| 覆盖 | 只有"跑这台机器的人"能看到 | 日本 / 中国香港 / 中国澳门 / 中国大陆同事**各自**收到 |
| 筛选 | 要靠人自己按条件查 | 按**订阅规则**（地区 / 物件種目 / 价位 / 关键词）自动分流 |
| 记忆 | 昨天的房源今天忘了 | 每天汇总一条日报，形成节奏 |

**核心场景**：大阪本地同事要"快"（新盘第一时间去带看）；中国香港 / 中国澳门 / 中国大陆同事要"准"（把合适的大阪房源推给国内客户，尤其**降价**和**稀缺物件**是最好卖点）。

---

## 2. 推给谁（受众分群）

| 分群 | 所在 | 语言 | 日常工具（决定渠道） | 关心什么 |
|---|---|---|---|---|
| A 日本同事 | 大阪 | 日文 | LINE / Chatwork / 邮件 | 全量新盘、带看便利性 |
| B 中国香港同事 | 中国香港 | 繁体中文 | **WhatsApp** / 邮件 | 价格带、投资回报、稀缺性 |
| C 中国澳门同事 | 中国澳门 | 繁体中文 | **WhatsApp** / 微信 | 同上 |
| D 中国大陆同事 | 中国大陆 | 简体中文 | **企业微信** / 飞书 / 钉钉 | 总价、面积、片区、可推荐性 |
| E 管理层 | 任意 | 简 / 繁 | 邮件 / 日报 | 今天新增多少、降价多少 |

> **分群的意义**：推送的「渠道」和「语言」由此决定，而不是由一个全局开关决定。同一个新盘，给日本同事推日文全文，给大陆同事推简体摘要。

---

## 3. 推什么（内容颗粒度）

| 类型 | 触发 | 卡片内容（首屏就要能判断"要不要跟进"） |
|---|---|---|
| 🟩 **新增** | 本轮首次入库 | 物件番号 · 地址/樓名 · 種目（新築/中古·戸建/公寓/土地）· 価格 · 面積 · 間取り · 最寄駅 · **図面 PDF 链接** · 详情页链接 |
| 🔴 **降价** | 价格下调 | 原价 → 现价 · **降价額** · **降价比例 %**（复用现有口径：降价額 ÷ 修改前金額）· 该房源卡片 |
| 🟦 **变更** | 面积 / 間取り / 築年月 等字段变化 | 变更了哪个字段 · 旧值 → 新值 · 该房源卡片 |
| 📋 **日报** | 每天定时 | 今天新增 N 套 / 降价 M 套（分地区/種目小计）+ 前 5 条亮点 |

> 关键：**推送卡片要做到"不用点开就敢下判断"**，点开只是补充。所以 PDF 链接 / 详情页链接必须带。

## 4. 用哪些渠道（全网盘点 · 四地工具习惯）

| 渠道 | 中国大陆 | 中国香港 | 中国澳门 | 日本 | 接入成本 | 审核 | 备注 |
|---|---|---|---|---|---|---|---|
| **企业微信群机器人** | ✅ 最顺 | △ 可用 | △ 可用 | ✕ | 极低（Webhook） | 无 | **首选保底**，5 分钟接通 |
| **飞书 / 钉钉机器人** | ✅ | △ | △ | △ | 低（Webhook） | 无 | 团队用哪个就接哪个 |
| **邮件（SMTP）** | ✅ | ✅ | ✅ | ✅ | 低 | 无 | **万能兜底**，一定有地址 |
| **WhatsApp Business API** | ✕ | ✅ 主流 | ✅ 主流 | ✕ | 中（Meta 商业账号） | **模板需审核、有费用** | 港澳首选，但要提前备案 |
| **LINE Messaging API** | ✕ | ✕ | ✕ | ✅ 主流 | 中 | 需官方账号 | ⚠️ LINE Notify 已停服，须走 Messaging API |
| Chatwork | ✕ | ✕ | ✕ | ✅ 常见 | 低（API Token） | 无 | 日本不动产行业常用 |
| Telegram | △ 需外网 | ✅ | ✅ | ✅ | 低（Bot API） | 无 | 跨区通吃，但大陆同事可能不便 |
| Slack | △ | △ | △ | △ | 低（Webhook） | 无 | 若团队已在用 |
| 短信 SMS | ✅ | ✅ | ✅ | ✅ | 中（运营商/云通信） | 需签名报备 | 只在"非常紧急"用，成本高 |
| 微信服务号模板消息 | ✅ | ✕ | ✕ | ✕ | 高（认证+审核） | 严格 | 触达客户可以，触达同事没必要 |

**结论：多渠道不是"可选项"，而是"必需项"。** 建议组合：

```
中国香港 / 中国澳门同事  →  WhatsApp Business API  +  邮件(兜底)
中国 大陆 同事           →  企业微信群机器人      +  邮件(兜底)
日本 同事                →  LINE Messaging API    +  Chatwork/邮件
全员日报                 →  邮件（一人一份，按语言）
```

## 5. 用什么架构模式（推荐：事件 → 规则 → 适配器）

```
        ┌───────────────── 抓取端（已在跑，无需改抓取逻辑）─────────────────┐
        │  pipeline.ingest ：检出 new / price_down / price_up / modified      │
        └───────────────────────────────┬──────────────────────────────────┘
                                        │  写一条事件（outbox 表）
                                        ▼
                              ┌──────────────────┐
                              │  events（事件表） │  property_no, type, payload, created_at, status
                              └────────┬─────────┘
                                       ▼
                        ┌────────────────────────────┐
                        │  规则引擎 Rule Engine       │  订阅：人/群 × 地区 × 種目 × 价位 × 关键词
                        │  决定「这件事该推给谁」      │  去重：同物件同变更只推一次
                        └────────┬───────────────────┘
                                 ▼
                    ┌──────────────────────────────┐
                    │  模板渲染 Render（多语言）     │  简 / 繁 / 日 / 英 + 本地时区
                    └────────┬─────────────────────┘
                             ▼
        ┌────────────────────┴─────────────────────┐
        ▼            ▼            ▼            ▼            ▼
     企业微信       WhatsApp      LINE         邮件       飞书/钉钉/Chatwork
     Adapter       Adapter      Adapter      Adapter      Adapter
        └────────────┴────────────┴────────────┴────────────┘
                             ▼
                    ┌──────────────────┐
                    │ 投递记录 + 失败重试 │  deliveries 表（成功/失败/重试次数）
                    └──────────────────┘
```

**为什么用这个模式（而不是"每个渠道写一遍")**
- **加渠道不改业务**：以后要加飞书 / Telegram，只写一个 Adapter，规则与模板不动。
- **换内容不改渠道**：卡片排版改一次，所有渠道同时生效。
- **可审计**：每条推送都有投递记录，谁收到了、失败重试几次，一查便知。
- **可回放**：事件表留着，渠道挂了恢复后可以补推（幂等，不重复）。

## 6. 什么时候推（节奏模式）

| 模式 | 说明 | 适合 | 风险 |
|---|---|---|---|
| **实时推** | 事件产生即刻发 | 日本同事（要快） | 夜里打扰、消息碎片化 |
| **批量推（日报）** | 每天固定 09:00 / 21:00 汇总 | 跨区同事 | 时效差一点 |
| **混合（推荐）** | 日本实时 + 跨区日报；**降价单独即时**（降价是最好的跟进理由） | 全部 | 规则稍复杂 |

**注意时区**：日本 JST(+9) / 中国香港·澳门 HKT(+8) / 中国大陆 CST(+8)。跨区推送要按**收件人本地时间**卡在 08:00–21:00，避免半夜弹窗。

## 7. 多语言与本地化

- 语言随**收件人地区**自动选：中国大陆=简体、中国香港/中国澳门=繁体、日本=日文、其他=英文。
- 复用系统已有的 4 语言（简 / 繁 / EN / 日）词典，同一套 key 渲染卡片。
- 单位本地化：价格保留「万円」原文口径 + 可选折算 **人民币 (CNY)**（国内同事看客户报价更直观）。
- 链接统一指向本机详情页 / PDF；若要给**外部**看，需另做"只读分享页"（见风险）。

## 8. 合规与风险（**这一节最重要，先看**）

| 风险 | 说明 | 对策 |
|---|---|---|
| 🔴 **REINS 数据二次使用** | REINS 的房源信息**明确限制对外转载 / 再发布**，推送到"客户群"或社媒属高风险 | **推送范围严格限定为「内部同事」**；禁止把 REINS 原始数据直接群发给终端客户；对外只发"我司自有整理/带看邀请" |
| 🔴 **日本個人情報保護法** | 涉及第三方提供需当事人同意 | 只推**物件信息**，不推客户个人信息；客户线索不下发到群 |
| 🟦 **中国大陆数据出境** | 数据出境合规、企微仅限内部使用 | 用企微机器人（内部）；跨境只传"摘要"，不传原始库 |
| 🟦 中国香港/中国澳门 PDPO | 个人资料保护 | 同上，只推物件、不推个人资料 |
| 🟡 WhatsApp / LINE 审核与费用 | 模板需审核、按条计费 | 提前申请账号；先邮件兜底 |
| 🟡 推送 ≠ 抓取 | 推送频率不能影响抓取节奏（防被判机器） | 推送与抓取解耦，推送走事件表异步 |
| 🟡 打扰 | 消息太多会被静音 | 订阅可关、日报可调，提供「免打扰时段」 |

> **一句话红线**：这套推送是**给同事用的内部雷达**，不是给客户的营销通道。客户触达要做成另一件事（且不直接转载 REINS 数据）。

## 9. 分步落地（MVP 建议）

| 里程碑 | 内容 | 周期量级 | 依赖 |
|---|---|---|---|
| **M1 · 保底覆盖** | 事件表 + 规则引擎（先硬编码订阅）+ **邮件 + 企业微信群机器人**；**每日日报** | 1 个迭代 | 企微群 Webhook（零审核） |
| **M2 · 港澳** | 接 **WhatsApp Business API**（繁中模板）；订阅列表可配置 | 1 个迭代 | Meta 商业账号 + 模板审核 |
| **M3 · 日本 + 实时** | 接 **LINE Messaging API / Chatwork**；新盘实时 + 降价即时；免打扰时段 | 1 个迭代 | LINE 官方账号 / API Token |
| **M4 · 自助订阅** | 软件内"推送设置"页：订阅规则 / 渠道开关 / 接收人管理 | 1 个迭代 | M1–M3 |

**M1 就能解决 80% 的问题**：邮件 + 企微群机器人覆盖中国大陆全部同事 + 所有地区兜底，零成本、零审核、当天就能跑通。

## 10. 待确认（需要你拍板）

1. **推送范围**：确认只推**内部同事**（合规红线），不接受"直接推给客户"？
2. **谁维护订阅**：现在你手工给；还是要做"推送设置"页让同事自填（M4）？
3. **推给个人还是群**：日本同事可能想"推到群"，港澳同事可能想"私发"——统一到群，还是支持个人？
4. **是否要人民币报价**：卡片要不要同时显示 **CNY 折算**（服务国内客户更直观）？
5. **频率偏好**：新盘要**实时**还是**每天两次汇总**就够？
6. **日报时间**：按各地本地时间几点推（建议日本 09:00 / 港澳大陆 09:00 & 21:00）？

## 11. 与现有能力的关系

- **抓取端不用改**：`changes` 表已经在记 new / price_down / price_up / modified，推送只要**消费**这些记录。
- **可复用现有定时能力**：本机已有"每天定时任务 + 汇报"的自动化框架（现用于 PRD 检查），推送调度可以走同一套。
- **软件侧新增**：一张 `events` 表、一个 `notify/` 适配器目录、一处配置（订阅 + 渠道凭证）、一个「推送设置」页（M4）。
