一、结论先行（给董事会的三句话）

1. 九天，从零做出一个可实跑的本地房源抓取与查询系统。覆盖 REINS（日本不动产流通机构）六大物件種目、两层下载（列表＋详情＋図面 PDF）、实时更新、变更语义对齐、对比、AI 解读、权限与访问码，版本从 v1.0.0 迭代到 v1.9.24。

2. 我搭的不只是功能，是一套产品治理体系。把"产品"与"研发"拆成两条线、立了六角色把关（PM/RD/UI/QA＋项目总监＋运维）、定了"先文档后代码、需求落两处"的铁律、并设了 8 条高风险硬门禁——让快速迭代的项目不会因改坏而失控。

3. 我的工作方式是"证据驱动的需求扩张"。用户报的是现象，我先查证根因再动手；大量需求是在查证中"长出来"的（例如"要更快"的真实目标是"别被平台封号"，"新增带降价"暴露的是"分类口径错"）。这正是董事会想看到的——产品经理怎么思考、怎么把模糊诉求变成可落地的产品。

二、维度一：时间轴（按研发阶段排序）

本维度按时间先后，呈现"用户在哪个阶段提出了什么、我怎么处理、落地到哪个版本"，并特别标出需求在过程中被扩张/深化的关键节点。

阶段 0 · 立项前史（09-11 上午）

此前 WorkBuddy 里的任务被清理软件清空，我用 4 天记忆 + 需求文档 + 会议逐字稿反推需求基线（教训：需求必须落成文件，这就是后来 PRD 稿存在的理由）。与梓榮（J Property）的会议逐字稿确认了核心场景：只推"点跟点之间新出来的物件"、后台持续比对、23:00 后 REINS 关闭时用本地按天页让同事半夜也能找房、担心被封号。同行机制（Telegram 机器人）仅作认知归档、不进本期需求——但"同行只推新增、我们要含变更/降价"这一条，后来演变成了 v1.1.10 的状态标与 09-13 的两轮大澄清。

阶段 1 · MVP 从 0 到可用（09-11 ～ 09-13，v1.0.0 → v1.2.6）

账号管理＋操作台（Fernet 加密、测试/真实下载四按钮，并立"绝不代输密码/不识别验证码/不换 IP"红线）；用 11 张真实 REINS 截图按真机校准选择器，跑通"取到数据＋下载到本地"最小链路（21/21 通过）；提速（2~3 秒→1~2 秒）；查询/对比/四语 i18n；指定日期下载、种目两级、数量对不上（查出"配额硬截断＋多条件共用配额＋種目一次只能填一个"三因叠加，上限抬到 5000 条）。

🔺 需求扩张典型案例 A（"要更快"）：用户说"间隔最好 1 秒左右"。我追问出真实目标是"尽可能像人操作、不被平台判违规"——结论是不能并发（并发最像机器、易封号）。需求从"提速"扩张为"真人化节奏 + 风控"。

🔺 需求扩张典型案例 B（"新增带降价"）：用户问"标新增为什么价格会降"。我查代码＋查库双证：本机 changes 表只看"是否首次入库"，没看平台 previous_price/change_date——分类口径错了。用户拍板"没记录过的应算变更而非新增"并追问"上一次数据何时、能否拉回"。需求从"视觉区分"扩张为"新增/变更 语义对齐平台"（v1.2.5，双信号判定＋存量回填）。可复用结论：显示层不一致，往往是分类口径本身有问题。

本阶段收尾立了两条铁律：版本管理与回滚（建 git 仓库，改坏随时回滚）、产品/研发双线归档（PRD 与代码分开演进、同一次检查点一起备份）。

阶段 2 · 需求正式化与治理升级（09-16 ～ 09-17，v1.5.19 → v1.8.9）

六角色治理立项：从单 Agent 四角色自证，升级为 PM/RD/UI/QA＋项目总监＋运维经理（OPS）独立把关；勇哥批准 8 条高风险硬门禁为永久标准，并要求用多个独立 Agent 分饰角色（信息隔离，杜绝"自己信自己"）。产出三份正式 PRD（查询条件与数据口径对齐 / v1.6 双版本方案 / 指定日期下载）。真修历史 bug：BUG-1（土地过滤匹配 0 行）、BUG-2（全量重传 2778 行修复 building_name/address 恒 NULL）、R25 地区直录 P0 事故（locator 命中 9 个同名元素→严格模式崩溃→检索恒空）。5WHY 复盘把 locator 唯一性断言、失败即 raise、待复核硬阻塞、总监反向挑战等写成发布前必过门禁。区间/对比/排序/对账/访问码全部落地；并堵住"凭据已进库"事故（三层配置合并 + 轮换 token）与一次 git stash 中断毁库事件（立"绝不用 git stash"铁律）。

阶段 3 · 健壮性 / 安全 / 发布闭环（09-18 ～ 09-19，v1.9.0 → v1.9.24）

安全加固：VULN-01/02/03（私密值污染入库、脱敏漏访问码、详情页 XSS）一并修复。抓取链路健壮性：直录超时重试、只跳该组不杀整轮、0 件页识别、更新周期重算＋上传独立定时器。番号検索改版：本页弹窗＋线上不另开窗口＋真键盘输入。交互细化（PRD 24）：查询页单行重设计（同类聚拢、重要向前、未展开即常驻"本地 PDF/详情页"两按钮）、详情页"AI 解读"章节移到"房源図面 PDF"下方。线上 PDF 安全展示（PRD 23）：PDF 必须上传到线上，但展示禁用明文（登录鉴权 + 受控接口）。

三、维度二：产品设计框架结构

本维度不按时间，而按我搭建的产品设计框架本身来组织——便于董事会看到"这个人是怎么搭产品体系的"。

3.1 双线架构（产品 / 研发 同仓分线）

维度产品线（docs/）研发线（core/ web/）
回答什么做成什么样、为什么怎么做出来的
读者业务方 / 产品 / 同事看代码的人
改动时机想法先落文档文档定了再改代码
备份与研发线同一次检查点一起备份同左

为什么一个仓库而不是两个：本项目"改需求顺带改代码"是常态（如 v1.2.5 同时改 PRD 与 4 个 .py）。拆两仓库回滚会变半截——代码退回、PRD 没退，下一个接手的人会照错的文档理解代码。约定"分开阅读、分开演进、同一个检查点一起备份"。

3.2 六角色治理框架

角色：PM（需求/口径/验收）· RD（实现）· UI（界面）· QA（测试/门禁）＋ 项目总监（只回头检查四角色有没有真把关，缺证据就打回）＋ 运维经理 OPS（上线/保存/迭代 SOP）。

硬门禁（8 条，发布前必过）：locator 命中数 == 1 断言、失败即 raise（绝不静默）、待复核功能硬阻塞发布、发布后健康检查、总监反向挑战、PRD 补历史教训引用＋实现风险等。

隔离原则：用多个独立 Agent 分饰角色，信息隔离 + 职责隔离 + 红队，切断"自己信自己"的自证循环。

3.3 需求 / PRD 写作范式

每一个需求落档都含六段：结论先行 → 需求表（优先级/状态） → 现状取证（代码/库/日志实证） → 方案候选 → 验收标准 → 待拍板项。配套四条维护约定：① 先文档、后代码；② 一个需求落两处（界面口径 + 业务口径）；③ 每轮沟通必须留痕（只增不删）；④ 不同步的东西标 ⏳，闭环后改 ✅ 并注版本。

3.5 沟通协作范式

结论先行，再展开细节；偏好结构化 checklist、表格对比、流水线式分工。缺信息时带提示追问关键缺口，无法补全才回退到预期范围。需要取舍时主动给结论 + 选项请业务方拍板，不被动等指令——对应勇哥原话"将来遇到需要交互的事，我需要产品经理来跟我交流"。不猜不蒙：凡未能确证的标 ⏳ 或写"要点"，绝不编造原话。

3.6 安全红线（产品价值观，全程未放开）

不代输账号密码、不识别验证码、不换 IP、会话失效即停机、凭证永不出本机、PDF 不传明文直链。这条线从第一天立下、九天没破。

四、需求演进的典型模式（我怎么工作）

整个项目的需求不是线性累加，而是"现象 → 查证 → 口径 → 需求扩张"的螺旋：

  1. 用户报的是现象，问题常在别处："登录失败"=服务死了；"下载成功但没数据"=没落库；"新增带降价"=分类口径错。先查证再动手，不按字面改 UI。
  2. 用户的字面目标 ≠ 真实目标："要更快"的真实目标是"别被封号"→ 不能并发。要问出真实目标。
  3. 用户对数字对不上极敏感，且业务专业：他举的"9/1 新增 1000 万 → 9/11 降价 800 万"在库里真实存在——直觉常先于数据被发现。
  4. 口径必须写在文档里，不能只存在代码里：同一词多套口径，写清楚比改样式重要。
  5. 显示层不一致，往往是分类口径本身有问题：v1.2.4 只做视觉区分是把问题当显示问题处理；用户一追问就推到数据语义层。
